# RAG — документы, OCR и чанкинг

> [!abstract] Суть
> Хороший RAG начинается не с векторной базы, а с аккуратного ingestion-пайплайна: извлечь текст, сохранить структуру документа, привязать метаданные, нарезать на осмысленные чанки и сделать процесс повторяемым для будущих обновлений.

## Ответ

### 1. Какие документы бывают на входе

Типовые источники:
- `PDF` с текстовым слоем: регламенты, инструкции, отчеты;
- сканы `PDF`/изображения: нужен OCR;
- `DOCX`: внутренние инструкции, шаблоны, договоры;
- `HTML`/Confluence/Wiki: страницы с заголовками, ссылками, таблицами;
- `Markdown`/`TXT`: уже близко к формату для RAG;
- `XLSX`/`CSV`: табличные данные;
- презентации, письма, тикеты, JSON-выгрузки.

Нормальный ingestion сохраняет несколько слоев данных:

1. **Raw-файл**: оригинал без изменений.
2. **Extracted text**: извлеченный текст, таблицы, подписи, OCR-результат.
3. **Normalized document**: единый промежуточный формат, часто `Markdown` или `JSONL`.
4. **Chunks**: фрагменты для поиска.
5. **Embeddings/index records**: то, что уходит в векторную БД и полнотекстовый индекс.

Для production важно хранить `source_id`, `version`, `checksum`, дату обновления, автора/раздел, права доступа, номера страниц и ссылки на исходный документ. Тогда можно инкрементально переиндексировать только измененные документы, удалять устаревшие чанки и объяснять пользователю, откуда взялся ответ.

### 2. Как строить pipeline для обновлений

Минимальная схема:

```text
source storage
  -> detect changed files by checksum/version
  -> parse/extract
  -> normalize to markdown/json
  -> quality checks
  -> chunk
  -> embed
  -> upsert to vector DB + full-text index
  -> mark old chunks as deleted/tombstoned
```

Что проверять:
- извлекся ли текст, не пустой ли документ;
- не пропали ли таблицы и заголовки;
- нет ли слишком коротких/слишком длинных чанков;
- совпадает ли число страниц/секций с ожиданиями;
- корректны ли ACL/права доступа;
- не изменился ли parser так, что весь индекс придется перестроить.

### 3. DOCX и таблицы

`python-docx` хорошо подходит для базового извлечения:
- параграфов;
- заголовков через стили;
- списков;
- таблиц как набора строк и ячеек.

Но `DOCX` — это не просто текстовый файл. В нем могут быть:
- таблицы с объединенными ячейками;
- вложенные таблицы;
- колонтитулы;
- footnotes/endnotes;
- комментарии;
- text boxes;
- картинки и подписи;
- визуальная верстка, которая не равна порядку XML-элементов.

Поэтому `python-docx` может сохранить содержимое таблицы, но не всегда идеально сохраняет визуальную структуру. Для RAG таблицу лучше превращать не в один сплошной абзац, а в один из форматов:

```markdown
| Параметр | Значение | Комментарий |
|---|---:|---|
| Лимит | 100000 | действует с 2025-01-01 |
```

или в структурированный JSON:

```json
{
  "table_id": "doc_42_page_7_table_2",
  "columns": ["Параметр", "Значение", "Комментарий"],
  "rows": [
    ["Лимит", "100000", "действует с 2025-01-01"]
  ]
}
```

Для сложных документов часто используют `pandoc`, `LibreOffice` conversion, `unstructured`, `docling` или layout-aware парсеры. Важная идея: если таблица нужна для точных ответов, ее надо хранить структурно, а не только как плоский текст.

### 4. Промежуточный формат перед чанкированием

Частый выбор — `Markdown`, потому что он сохраняет человеческую структуру:
- `#`, `##`, `###` для секций;
- списки;
- таблицы;
- ссылки;
- кодовые блоки;
- подписи.

Для production часто используют `JSONL`, где каждое логическое звено хранит текст и метаданные:

```json
{
  "doc_id": "credit_policy_2026",
  "section": "2.3 Проверка заемщика",
  "page": 12,
  "text": "Перед выдачей кредита необходимо проверить...",
  "source_url": "s3://bucket/credit_policy_2026.docx"
}
```

Markdown удобен для чтения и отладки, JSONL удобен для пайплайнов, повторяемости и batch-индексации.

### 5. OCR для PDF без текстового слоя

Если PDF является сканом, прямой `pdfplumber`/`pypdf` вернет пустой или мусорный текст. Тогда pipeline такой:

1. Проверить наличие текстового слоя.
2. Отрендерить страницы в изображения с нормальным DPI.
3. Сделать preprocessing: deskew, denoise, contrast, crop.
4. Прогнать OCR: Tesseract, PaddleOCR, EasyOCR или облачный OCR.
5. Восстановить layout: абзацы, заголовки, таблицы, колонки.
6. Сохранить confidence OCR и координаты блоков.
7. Отправить низкоуверенные страницы на ручную проверку.

Для таблиц одного OCR мало: нужен table detection/table structure recognition. Иначе числа попадут в текст, но связь "колонка -> значение" потеряется.

### 6. Методы чанкирования

**Fixed-size chunking**: режем по N токенов/символов. Просто, дешево, но может разрезать мысль посередине.

**Sliding window with overlap**: fixed-size плюс перекрытие. Уменьшает риск потерять ответ на границе, но плодит дубликаты.

**Recursive chunking**: сначала пробуем резать по крупным разделителям (`##`, абзацы), потом по предложениям, потом по словам. Хороший дефолт для Markdown/документов.

**Heading-aware chunking**: режем по структуре документа и добавляем путь секции в каждый чанк: `Регламент > Проверка заемщика > Документы`.

**Semantic chunking**: группируем предложения с близкой семантикой и режем там, где тема меняется.

**Parent-child chunking**: ищем по маленьким child chunks, а в контекст LLM кладем более крупный parent section. Это часто лучше, чем отдавать только микрофрагмент.

**Hierarchical chunking**: индексируем документ на нескольких уровнях: раздел, подраздел, абзац. Сначала ищем крупный раздел, потом уточняем внутри него.

**Table-aware chunking**: таблицу не режем произвольно. Храним заголовок таблицы, колонки, строки и, если нужно, делаем отдельные чанки по группам строк.

**Proposition/fact chunking**: извлекаем атомарные утверждения: "лимит X действует для сегмента Y". Удобно для точных QA, но дороже в подготовке.

### 7. Семантическое деление без LLM

LLM можно не использовать. Более дешевые варианты:

- sentence embeddings: считаем эмбеддинг каждого предложения и режем там, где cosine similarity между соседними окнами резко падает;
- TextTiling/C99: классические алгоритмы topic segmentation по лексической когезии;
- заголовки, стили и layout: часто структура документа уже задает лучшие границы;
- тематические ключевые слова: резать при смене набора терминов;
- кластеризация абзацев внутри документа;
- правила для таблиц, списков и кода.

На практике обычно начинают с recursive/heading-aware chunking, потом измеряют retrieval quality и только затем добавляют semantic splitting там, где простое разбиение реально ломает ответы.

## Формула / Схема

**Инкрементальное обновление индекса:**

$$\Large \text{reindex}(d) =
\begin{cases}
1, & \text{если } checksum(d) \ne checksum_{\text{old}}(d) \\
0, & \text{иначе}
\end{cases}$$

где:
- $d$ — документ;
- $checksum(d)$ — хэш текущей версии документа;
- $checksum_{\text{old}}(d)$ — хэш версии, которая уже была проиндексирована;
- `reindex = 1` означает, что документ надо заново распарсить, нарезать и переиндексировать.

## Короткий пример

Для базы регламентов в `DOCX` хороший pipeline такой: хранить raw `DOCX`, извлекать текст и таблицы, нормализовать в Markdown, сохранять `doc_id/section/page`, резать по заголовкам и абзацам, таблицы хранить отдельными структурированными чанками, а при обновлении документа переиндексировать только чанки с изменившимся `checksum`.

## Типичные ошибки

- Индексировать OCR-текст без проверки confidence.
- Превращать таблицы в плоский текст и терять связь колонок со значениями.
- Резать документы фиксированным размером, игнорируя заголовки и структуру.
- Не хранить `doc_id`, `page`, `section`, из-за чего потом нельзя дать ссылку на источник.
- Не делать инкрементальные обновления и каждый раз перестраивать весь индекс.
