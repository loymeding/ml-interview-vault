# Токенизация LLM — BPE и merge table

> [!abstract] Суть
> BPE-токенизация строит словарь не из целых слов, а из частых подсловных фрагментов. Это уменьшает OOV-проблему: частые слова становятся короткими токенами, а редкие слова, опечатки и новые термины раскладываются на более мелкие известные куски.

## Ответ

### 1. Зачем LLM нужна subword-токенизация

Если токенизировать текст целыми словами, словарь быстро разрастается: формы `модель`, `модели`, `моделями`, `моделирование` становятся разными единицами. При встрече нового слова модель вынуждена использовать `<unk>` и теряет почти весь смысл.

Если токенизировать по символам, OOV почти исчезает, но последовательности становятся слишком длинными: attention дорожает, а модели сложнее собирать смысл из отдельных букв.

Subword-подход, например BPE, даёт компромисс:
- частые слова и морфемы становятся отдельными токенами;
- редкие слова раскладываются на подслова;
- словарь остаётся конечным и управляемым;
- любой текст можно представить через базовые символы или bytes.

### 2. Как обучается BPE

Byte Pair Encoding стартует с базового алфавита: символов, байтов или заранее выбранных минимальных единиц. Затем алгоритм много раз повторяет один шаг: найти самую частую соседнюю пару токенов и слить её в новый токен.

Пример:

```text
низ кий
низ кая
низ кие
```

Если пара `н` + `и` встречается часто, она сливается в `ни`; затем `ни` + `з` может стать `низ`; затем `к` + `ий` может стать `кий`. В итоге модель получает полезные фрагменты, которые переиспользуются в разных словах.

Результат обучения токенизатора:
- словарь токенов;
- merge table — упорядоченный список слияний;
- правила нормализации текста;
- специальные токены вроде `<bos>`, `<eos>`, `<pad>`, `<unk>`.

### 3. Зачем нужна merge table

Словаря недостаточно. Нужно знать, в каком порядке разрешено склеивать пары. Merge table хранит пары вида `(token_i, token_j)` и их `rank`: чем меньше rank, тем раньше это слияние было найдено при обучении и тем выше его приоритет.

На inference токенизация детерминирована:
1. текст разбивается на базовые единицы;
2. среди соседних пар ищутся пары из merge table;
3. выбирается пара с минимальным rank;
4. пара склеивается;
5. локально обновляются соседние пары;
6. процесс повторяется, пока допустимых слияний больше нет.

Фактически токенизатор — это не только vocabulary, а `vocabulary + merge table + нормализация + special tokens`. Менять merge table после обучения модели нельзя: embedding-матрица модели уже привязана к конкретным ID токенов.

### 4. Почему BPE эффективнее слов и символов

По сравнению со словами:
- меньше OOV;
- лучше работа с редкими словами и неологизмами;
- меньше размер словаря при сохранении смысла частей слов.

По сравнению с символами:
- короче последовательность;
- attention дешевле;
- модель видит более смысловые единицы.

Главный компромисс — размер словаря. Маленький словарь делает последовательности длинными, большой словарь увеличивает embedding-матрицу и может хуже обрабатывать редкие словоформы.

## Формула / Схема

**Условная цель выбора очередного merge:**

$$\Large (a^\*, b^\*) = \arg\max_{(a,b)} \text{count}(a,b)$$

где:
- $(a,b)$ — соседняя пара текущих токенов в корпусе;
- $\text{count}(a,b)$ — сколько раз эта пара встречается;
- $(a^\*, b^\*)$ — пара, которую алгоритм сольёт на текущем шаге.

**Токенизатор как часть модели:**

$$\Large \text{Tokenizer} = \{\text{normalizer}, \text{vocab}, \text{merges}, \text{special tokens}\}$$

где:
- `normalizer` приводит текст к ожидаемому виду;
- `vocab` задаёт соответствие токенов и ID;
- `merges` задаёт порядок слияний;
- `special tokens` задают служебные границы и роли.

## Короткий пример

Слово `нейросетями` может не быть отдельным токеном. BPE может разложить его как:

```text
нейро + сет + ями
```

Если пользователь написал `нейросетями!!!`, хороший токенизатор не обязан превращать всё слово в `<unk>`: слово и пунктуация будут разложены на известные куски.

## Типичные ошибки

- **Думать, что BPE полностью понимает морфологию:** BPE оптимизирует частоты пар, а не лингвистические морфемы.
- **Менять словарь токенизатора без переобучения модели:** ID токенов связаны с embedding-матрицей. Новый словарь ломает соответствие входов и весов.
- **Сравнивать perplexity моделей с разными токенизаторами напрямую:** perplexity считается на токен, а токены могут иметь разную длину.
- **Путать BPE и FastText:** BPE меняет токенизацию входа, а FastText строит эмбеддинг слова из символьных n-грамм.

## Каверзные вопросы

> [!question] Почему одного словаря недостаточно для воспроизведения BPE?
> Потому что один и тот же набор токенов можно получить разными порядками слияния. Merge table фиксирует приоритеты слияний, поэтому новый текст разбивается так же, как тексты при обучении.

> [!question] Почему BPE снижает OOV-проблему, но не делает модель всезнающей?
> Модель сможет представить новое слово через подслова, но смысл этого слова всё равно должен быть выучен из контекста. Если слово новое концептуально, токенизация только сохраняет сигнал, а не добавляет знание.
