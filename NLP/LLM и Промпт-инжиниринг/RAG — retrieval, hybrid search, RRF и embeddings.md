# RAG — retrieval, hybrid search, RRF и embeddings

> [!abstract] Суть
> Retrieval в RAG — это не только "поиск по близости". В проде обычно комбинируют dense vector search, BM25/full-text, metadata filters, reranking и алгоритм слияния результатов вроде RRF.

## Ответ

### 1. Retrieval: общий принцип

Retrieval отвечает на вопрос: какие куски базы знаний стоит показать LLM перед генерацией ответа.

Типовой pipeline:

```text
query
  -> query preprocessing / rewrite / expansion
  -> dense vector search
  -> sparse full-text search
  -> metadata filtering
  -> merge results
  -> rerank
  -> context packing
```

Dense retrieval ищет близость эмбеддингов. Sparse retrieval ищет совпадение токенов, терминов и редких слов. Hybrid retrieval объединяет оба подхода.

Можно использовать не один retriever, а несколько:
- vector retriever;
- BM25 retriever;
- keyword/exact match retriever;
- metadata retriever;
- graph retriever;
- SQL/table retriever;
- multiquery retriever.

### 2. BM25 vs TF-IDF

`TF-IDF` взвешивает слово по частоте в документе и редкости в коллекции. Это хороший базовый sparse-подход, но он грубо работает с длиной документа и ростом частоты слова.

`BM25` можно считать улучшенным TF-IDF для поиска:
- насыщает вклад частоты слова: десятое повторение термина не должно быть в десять раз важнее первого;
- нормализует длину документа;
- хорошо работает для коротких пользовательских запросов.

Формула BM25 для запроса $q$ и документа $D$:

$$\Large \text{BM25}(q, D) = \sum_{t \in q} IDF(t) \cdot
\frac{f(t, D)(k_1 + 1)}
{f(t, D) + k_1 \left(1 - b + b \cdot \frac{|D|}{avgdl}\right)}$$

где:
- $t$ — термин из запроса;
- $IDF(t)$ — насколько термин редкий в коллекции;
- $f(t, D)$ — сколько раз термин встретился в документе;
- $|D|$ — длина документа;
- $avgdl$ — средняя длина документа в коллекции;
- $k_1$ — сила насыщения term frequency;
- $b$ — сила нормализации по длине документа.

Если добавить стемминг/лемматизацию или char n-grams, TF-IDF станет устойчивее к морфологии. Но BM25 все равно обычно лучше ранжирует из-за saturating TF и length normalization.

### 3. Выбор векторной базы

Критерии выбора:
- размер коллекции и скорость роста;
- latency и throughput;
- поддержка ANN-индексов: HNSW, IVF, PQ;
- качество metadata filtering;
- гибридный поиск: dense + sparse;
- updates/deletes/upserts;
- durability, backup, replication;
- multi-tenancy и ACL;
- стоимость эксплуатации;
- удобство локального/облачного деплоя.

Примеры: Qdrant, Milvus, Weaviate, pgvector, Elasticsearch/OpenSearch с vector search, FAISS как библиотека для локального индекса.

Выбор "почему именно эта база" лучше объяснять от ограничений: объем данных, необходимость фильтров, частота обновлений, требования к latency, команда и инфраструктура.

### 4. Hybrid search и слияние результатов

Dense search хорошо находит семантические переформулировки:

```text
"как закрыть карту" ~ "процедура блокировки банковской карты"
```

BM25 хорошо ловит точные термины:

```text
"форма 115-ФЗ", "код ошибки E042", "пункт 3.7"
```

Поэтому часто делают оба поиска и объединяют результаты:

```text
top_k_dense + top_k_bm25 -> merge -> rerank -> final top_k
```

Можно объединять по нормированным score, но score у разных retriever обычно несопоставимы. Поэтому удобен RRF.

### 5. RRF: Reciprocal Rank Fusion

RRF объединяет несколько ранжированных списков не по абсолютному score, а по позициям документов в списках.

$$\Large \text{RRF}(d) = \sum_{r \in R} \frac{1}{k + rank_r(d)}$$

где:
- $d$ — документ или chunk;
- $R$ — набор retriever/list sources;
- $rank_r(d)$ — позиция документа $d$ в списке retriever $r$;
- $k$ — сглаживающая константа, часто около 60;
- если документа нет в списке retriever, вклад этого retriever равен 0.

Интуиция: если chunk высоко в нескольких списках, он получает высокий итоговый score. Если chunk высоко только в одном списке, он тоже может пройти, но будет слабее документа, который стабильно найден разными retriever.

Пример:

| Chunk | BM25 rank | Vector rank | RRF score при k=60 |
|---|---:|---:|---:|
| A | 1 | 8 | $\frac{1}{61}+\frac{1}{68}$ |
| B | 20 | 1 | $\frac{1}{80}+\frac{1}{61}$ |
| C | 2 | нет | $\frac{1}{62}$ |

Так можно взять 40 кандидатов из оригинального запроса и трех paraphrases, удалить дубликаты, посчитать RRF и оставить итоговый top-10.

### 6. Multiquery search

Multiquery search генерирует несколько вариантов запроса:

```text
оригинал: "как закрыть договор?"
q1: "процедура расторжения договора"
q2: "какие документы нужны для закрытия договора"
q3: "условия прекращения договора"
```

Плюсы:
- лучше покрывает разные формулировки;
- помогает при коротких и неясных запросах;
- поднимает recall.

Минусы:
- больше latency и стоимости;
- перефразы могут уйти в сторону;
- появляются дубликаты;
- нужно аккуратно сливать результаты;
- больше шума для reranker.

На практике multiquery почти всегда требует deduplication, RRF или reranking.

### 7. Выбор embedding-модели

Смотреть нужно не только на общий leaderboard, а на задачу:
- язык: русский, английский, multilingual;
- домен: банки, медицина, код, юридические документы;
- тип retrieval: query-document или symmetric similarity;
- размер контекста embedding-модели;
- размерность эмбеддинга;
- скорость и batch throughput;
- лицензия;
- стоимость;
- качество на своем golden set.

Примеры multilingual embedding-семейств:
- `multilingual-e5`;
- `bge-m3`;
- `LaBSE`;
- `paraphrase-multilingual-MiniLM`;
- `jina-embeddings`;
- `gte-multilingual`;
- коммерческие embedding API.

Для RAG на русском нельзя выбирать модель только по английскому MTEB. Нужен хотя бы небольшой доменный набор пар `query -> relevant chunks` и offline retrieval metrics.

### 8. Ресурсы под embedding

Embedding-модель обычно сильно легче генеративной LLM:
- маленькие encoder-модели можно гонять на CPU батчами;
- GPU нужен для большой коллекции, частых переиндексаций и низкой latency;
- важны batch size, max sequence length и pooling;
- на inference не нужен KV-cache, поэтому память предсказуемее, чем у decoder-only LLM.

Если ресурсов мало:
- уменьшить max tokens на chunk;
- батчить запросы;
- выбрать меньшую embedding-модель;
- кэшировать эмбеддинги документов;
- пересчитывать только измененные документы.

### 9. RAG по Excel-таблицам

Для таблиц 50-100 тыс. строк и 10-20 колонок плохая идея — просто превратить все строки в текстовые чанки и надеяться на vector search.

Лучше:

1. Распознать схему таблицы: названия колонок, типы, единицы измерения.
2. Сохранить данные в DuckDB/PostgreSQL/Spark/Parquet.
3. Для вопросов про агрегации использовать SQL/Pandas tool, а не retrieval.
4. Для поиска по строкам сделать отдельный текстовый индекс по описательным колонкам.
5. Для каждой найденной строки хранить `row_id`, лист, диапазон ячеек, ключевые колонки.
6. Для LLM отдавать компактную выборку строк или агрегированный результат, а не всю таблицу.

Пример:

```text
Вопрос: "В каких регионах просрочка выше 5%?"
Tool: SQL over table
Result: region, overdue_rate, n_clients
LLM: объясняет результат и ссылается на таблицу
```

## Типичные ошибки

- Сравнивать raw scores BM25 и cosine similarity без нормализации.
- Использовать только vector search и терять точные артикулы, номера пунктов, коды ошибок.
- Использовать только BM25 и не находить переформулировки.
- Не делать deduplication после multiquery.
- Выбирать embedding-модель по общему бенчу без проверки на своем домене.
- Делать RAG по Excel как по обычному тексту, хотя вопрос требует SQL-агрегации.
