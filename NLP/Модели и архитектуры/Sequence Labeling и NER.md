# Sequence Labeling и NER

> [!abstract] Суть
> Sequence labeling — это задачи, где метка предсказывается для каждого токена, а не для всего текста. NER — частный случай: нужно найти именованные сущности и определить их типы, например `PERSON`, `ORG`, `LOC`.

> [!tip] Как держать тему в голове
> В обычной классификации мы отвечаем на вопрос: «какой класс у всего текста?». В sequence labeling вопрос другой: «какая роль у каждого токена внутри текста?». Поэтому важны не только отдельные предсказания, но и согласованность всей последовательности меток: где сущность начинается, где заканчивается, какой у неё тип и не нарушает ли модель правила разметки.

## Ответ

### 1. Что такое sequence labeling

В классификации текста модель выдаёт одну метку на весь документ:

```text
"фильм отличный" -> positive
```

В sequence labeling модель выдаёт метку на каждый токен:

```text
"Илон Маск основал SpaceX"
Илон -> B-PER
Маск -> I-PER
основал -> O
SpaceX -> B-ORG
```

Типичные задачи:
- NER;
- POS-tagging;
- chunking;
- slot filling в диалоговых системах;
- извлечение терминов.

То есть sequence labeling — это общий класс задач, где вход и выход имеют примерно одинаковую длину:

```text
x_1, x_2, x_3, ..., x_T
 ↓    ↓    ↓        ↓
y_1, y_2, y_3, ..., y_T
```

Где:
- $x_t$ — токен на позиции $t$;
- $y_t$ — метка для этого токена;
- $T$ — длина последовательности.

Главное отличие от обычной классификации: метки соседних токенов **сильно связаны**. Если токен получил метку `B-PER`, следующий токен с большой вероятностью может быть `I-PER`, но почти никогда не должен внезапно стать `I-ORG`. Поэтому в sequence labeling важно моделировать контекст и переходы между метками.

**Примеры задач sequence labeling:**

| Задача | Что предсказываем для каждого токена | Пример |
|---|---|---|
| **NER** | тип именованной сущности | `Илон/B-PER Маск/I-PER` |
| **POS-tagging** | часть речи | `кошка/NOUN спит/VERB` |
| **Chunking** | синтаксический фрагмент | начало/продолжение noun phrase |
| **Slot filling** | слот в пользовательском запросе | `завтра/B-DATE в/I-DATE Москве/B-CITY` |
| **Term extraction** | принадлежит ли токен термину | `градиентный/B-TERM бустинг/I-TERM` |

### 1.1. Что такое NER

**NER** (Named Entity Recognition) — это частный случай sequence labeling, где нужно найти в тексте именованные сущности и определить их тип.

Типовые классы сущностей:
- `PER` / `PERSON` — человек: `Андрей Карпаты`;
- `ORG` — организация: `Яндекс`, `OpenAI`, `Сбер`;
- `LOC` / `GPE` — место, город, страна: `Москва`, `Германия`;
- `DATE` — дата или период: `2026 год`, `вчера`, `12 мая`;
- `MONEY` — деньги: `500 рублей`, `$10M`;
- `PRODUCT` — продукт: `ChatGPT`, `iPhone`;
- `EVENT` — событие: `NeurIPS 2025`;
- `SKILL` / `TECH` — навык или технология в HR-задачах: `PyTorch`, `Spark`, `RAG`.

Важно: NER — это не просто «найти слова с большой буквы». В реальных текстах сущности бывают неоднозначными:

```text
"Apple выпустила новый чип"       -> Apple = ORG
"apple лежит на столе"            -> apple = не сущность
"Я работал в Газпромбанке"        -> Газпромбанке = ORG
"газпромбанк" в резюме без регистра -> всё равно ORG
```

Поэтому модели нужен контекст, а не только словарь известных имён.

### 2. BIO-разметка

BIO-кодирование показывает границы сущностей:
- `B-X` — начало сущности типа `X`;
- `I-X` — продолжение сущности типа `X`;
- `O` — токен вне сущности.

Это нужно, чтобы отличать соседние сущности одного типа и много токенов внутри одной сущности.

Без `B-` невозможно корректно различить две соседние сущности одного типа:

```text
"Иван Петров Пётр Сидоров"
Иван    -> B-PER
Петров  -> I-PER
Пётр    -> B-PER
Сидоров -> I-PER
```

Если бы мы писали только `PER PER PER PER`, было бы непонятно: это один человек с длинным именем или два разных человека.

**Пример BIO-разметки:**

```text
"Анна работает в Яндексе с 2021 года"

Анна      -> B-PER
работает  -> O
в         -> O
Яндексе   -> B-ORG
с         -> O
2021      -> B-DATE
года      -> I-DATE
```

### 2.1. BIO, BIOES и BILOU

Кроме BIO часто встречаются более подробные схемы разметки:

| Схема | Метки | Идея |
|---|---|---|
| **BIO** | `B`, `I`, `O` | начало, продолжение, вне сущности |
| **BIOES** | `B`, `I`, `O`, `E`, `S` | добавляет конец сущности и одиночную сущность |
| **BILOU** | `B`, `I`, `L`, `O`, `U` | `L` = last, `U` = unit, почти то же, что BIOES |

BIOES/BILOU дают модели больше информации о границах:

```text
"Илон Маск основал SpaceX"

BIO:
Илон   -> B-PER
Маск   -> I-PER
SpaceX -> B-ORG

BIOES:
Илон   -> B-PER
Маск   -> E-PER
SpaceX -> S-ORG

BILOU:
Илон   -> B-PER
Маск   -> L-PER
SpaceX -> U-ORG
```

**Интуиция:** в BIO метка `B-ORG` может означать и начало длинной сущности, и сущность из одного токена. В BIOES/BILOU одиночная сущность помечается отдельно (`S` или `U`), поэтому модели проще учить границы.

### 3. Модели для NER

Классический пайплайн:
- признаки токена и контекста;
- CRF, HMM или линейные модели.

Нейросетевой пайплайн:
- BiLSTM/GRU читает контекст слева и справа;
- CRF-слой сверху контролирует допустимые переходы меток;
- BERT/encoder-only transformer даёт контекстные embeddings токенов;
- token-classification head предсказывает метку каждого токена.

BiLSTM и BERT полезны, потому что тип сущности часто зависит от правого контекста:

```text
"Apple выпустила обновление" -> ORG
"apple лежит на столе" -> не ORG
```

Исторически NER развивался примерно так:

1. **Правила и словари**: регулярки, списки компаний, списки городов, шаблоны дат.
2. **Статистические модели**: HMM, MEMM, CRF с ручными признаками.
3. **Нейросетевые модели**: BiLSTM/BiGRU + embeddings + CRF.
4. **Transformer-модели**: BERT/RuBERT/XLM-R/DeBERTa + token classification head.
5. **LLM extraction**: большая модель получает текст и возвращает JSON со структурированными сущностями.

У каждого подхода есть trade-off:

| Подход | Плюсы | Минусы |
|---|---|---|
| Правила / regex | быстро, прозрачно, хорошо для дат и номеров | плохо переносится на язык и контекст |
| Словари / gazetteers | хорошо ловят известные сущности | не находят новые сущности, много ложных совпадений |
| CRF с признаками | учитывает последовательность меток | нужны ручные признаки |
| BiLSTM-CRF | хорошо работает на средних датасетах | хуже трансформеров на сложном контексте |
| BERT token classification | сильный baseline, учитывает контекст | нужны размеченные данные и аккуратная token alignment |
| LLM + structured output | удобно без обучения, гибко по схеме | дороже, медленнее, возможны галлюцинации |

### 3.1. Как выглядит BERT-пайплайн для NER

Современный supervised NER чаще всего выглядит так:

```text
Текст
  ↓
Токенизация
  ↓
Encoder-only transformer: BERT / RuBERT / XLM-R
  ↓
Контекстное представление каждого токена h_t
  ↓
Linear layer / token classification head
  ↓
Softmax по BIO-меткам
  ↓
Постобработка: собрать токены обратно в сущности
```

Например, для предложения:

```text
"Мария устроилась в Сбер"
```

модель выдаёт распределение по меткам для каждого токена:

```text
Мария      -> P(B-PER)=0.97, P(O)=0.01, ...
устроилась -> P(O)=0.99, ...
в          -> P(O)=0.98, ...
Сбер       -> P(B-ORG)=0.94, P(O)=0.03, ...
```

После этого мы берём наиболее вероятные метки и собираем сущности:

```text
[
  {"text": "Мария", "type": "PER"},
  {"text": "Сбер", "type": "ORG"}
]
```

### 4. Зачем CRF поверх BiLSTM/BERT

Если предсказывать метку каждого токена независимо, можно получить невозможную последовательность:

```text
O I-PER I-PER
```

`I-PER` не должен начинаться без `B-PER`. CRF учитывает переходы между соседними метками и выбирает наиболее правдоподобную последовательность целиком.

Без CRF модель обычно делает локальный выбор:

```text
для каждого токена отдельно выбираем argmax по меткам
```

Проблема: локально хорошая метка может быть плохой внутри всей последовательности. CRF добавляет матрицу переходов между метками:

```text
B-PER -> I-PER  хорошо
B-PER -> I-ORG  плохо
O     -> I-PER  плохо
O     -> B-PER  нормально
```

То есть CRF учит не только «какая метка подходит токену», но и «какая метка допустима после предыдущей».

**Интуиция CRF:**
- BERT/BiLSTM даёт score для каждой метки на каждой позиции;
- CRF добавляет score перехода между соседними метками;
- итоговый score последовательности = сумма token scores + сумма transition scores;
- на инференсе выбирается не лучший label для каждого токена отдельно, а лучшая цепочка меток целиком.

CRF можно воспринимать как небольшую **обучаемую метамодель / декодер поверх основной модели**. Основная модель, например BERT или BiLSTM, сначала выдаёт для каждого токена scores по всем возможным меткам. CRF берёт эти token-level scores, добавляет обучаемые scores переходов между метками и оценивает уже не отдельные токены, а всю последовательность целиком.

Важная практическая деталь: в CRF обычно подают не нормализованные вероятности после softmax, а сырые **logits / emission scores**. Это нужно потому, что CRF сам строит вероятность всей последовательности меток:

```text
BERT / BiLSTM
  ↓
logits для каждого токена и каждой метки
  ↓
CRF: logits + transition scores
  ↓
лучшая согласованная BIO/BILOU-последовательность
```

То есть CRF отвечает не на вопрос «какая метка локально самая вероятная для этого токена?», а на вопрос «какая цепочка меток целиком наиболее правдоподобна с учётом токенов и переходов между соседними метками?».

Для выбора лучшей последовательности обычно используют **алгоритм Витерби**. Он динамически перебирает возможные пути по меткам и находит цепочку с максимальным score без полного перебора всех вариантов.

Если длина текста $T$, а число меток $K$, то полный перебор дал бы $K^T$ вариантов. Витерби считает оптимальный путь за:

$$\Large O(T \cdot K^2)$$

где:
- $T$ — число токенов;
- $K$ — число возможных меток;
- $K^2$ появляется из-за перебора переходов из каждой предыдущей метки в каждую текущую.

### 5. Оценка качества

Для NER обычно считают entity-level Precision/Recall/F1: сущность засчитывается, только если правильно найдены и границы, и тип.

Token-level accuracy может быть обманчивой: большинство токенов имеют метку `O`, поэтому модель, которая всегда предсказывает `O`, может иметь высокую accuracy и нулевую пользу.

**Entity-level оценка** строже token-level оценки.

Допустим, эталон:

```text
Илон Маск -> PER
```

Модель предсказала:

```text
Илон -> PER
```

На уровне токенов модель частично права: `Илон` найден. Но на уровне сущностей это ошибка, потому что границы сущности неверные: нужно было найти `Илон Маск` целиком.

Формулы:

$$\Large Precision = \frac{TP}{TP + FP}$$

$$\Large Recall = \frac{TP}{TP + FN}$$

$$\Large F1 = 2 \cdot \frac{Precision \cdot Recall}{Precision + Recall}$$

где:
- $TP$ — сущность найдена полностью правильно: совпали границы и тип;
- $FP$ — модель предсказала лишнюю сущность или неверный тип/границы;
- $FN$ — сущность была в эталоне, но модель её не нашла;
- $Precision$ отвечает на вопрос: «какая доля найденных моделью сущностей действительно правильная?»;
- $Recall$ отвечает на вопрос: «какую долю всех настоящих сущностей модель нашла?»;
- $F1$ балансирует precision и recall.

**Пример:**

Эталон:

```text
[Илон Маск]PER основал [SpaceX]ORG в [2002 году]DATE
```

Предсказание:

```text
[Илон]PER основал [SpaceX]ORG
```

Тогда:
- `SpaceX` = правильная сущность → $TP = 1$;
- `Илон` вместо `Илон Маск` = неправильные границы → $FP = 1$;
- `Илон Маск` не найден целиком → $FN = 1$;
- `2002 году` не найден → $FN = 1$;
- итого: $Precision = 1 / (1 + 1) = 0.5$;
- $Recall = 1 / (1 + 2) \approx 0.33$.

Обычно для NER отдельно смотрят:
- **micro-F1** — агрегирует все сущности вместе, хорошо отражает общее качество;
- **macro-F1** — усредняет качество по типам сущностей, сильнее показывает провалы на редких классах;
- качество по каждому типу: `PER`, `ORG`, `LOC`, `DATE` и т.д.

## Формула / Схема

**Token classification:**

$$\Large \hat{y}_t = \text{softmax}(W h_t + b)$$

где:
- $h_t$ — контекстное представление токена $t$;
- $W,b$ — параметры классификационной головы;
- $\hat{y}_t$ — распределение по меткам для токена.

**CRF score последовательности:**

$$\Large s(x,y) = \sum_{t=1}^{T} A_{y_{t-1}, y_t} + \sum_{t=1}^{T} P_{t,y_t}$$

где:
- $A_{y_{t-1}, y_t}$ — score перехода между метками;
- $P_{t,y_t}$ — score метки $y_t$ для токена $t$;
- $T$ — длина последовательности.

**Вероятность последовательности в CRF:**

$$\Large P(y \mid x) = \frac{\exp(s(x,y))}{\sum_{\tilde{y} \in \mathcal{Y}(x)} \exp(s(x,\tilde{y}))}$$

где:
- $y$ — конкретная последовательность меток;
- $\tilde{y}$ — любая допустимая последовательность меток;
- $\mathcal{Y}(x)$ — множество всех возможных последовательностей меток для входа $x$;
- $s(x,y)$ — score последовательности;
- знаменатель нормирует scores по всем возможным цепочкам меток.

**Loss для CRF:**

$$\Large \mathcal{L} = -\log P(y^{true} \mid x)$$

где:
- $y^{true}$ — правильная последовательность BIO/BILOU-меток;
- модель штрафуется, если правильная последовательность получает низкую вероятность.

## Короткий пример

В резюме:

```text
"Работал в Яндексе с 2020 года"
Яндексе -> B-ORG
2020 -> B-DATE
```

Для downstream-задачи важно не просто понять тональность текста, а вытащить структурированные поля.

### 6. Subword-токенизация и выравнивание меток

В BERT-подобных моделях текст сначала разбивается не обязательно на слова, а на subword-токены. Например:

```text
"Газпромбанке" -> ["Газ", "##пром", "##банке"]
```

Но разметка обычно дана на уровне слов:

```text
Газпромбанке -> B-ORG
```

Нужно решить, как перенести label на subword-токены.

Основные стратегии:

| Стратегия | Как размечаем | Плюсы | Минусы |
|---|---|---|---|
| Только первый subword | `Газ -> B-ORG`, остальные `-100` | стандартно для BERT fine-tuning, не дублирует loss | модель учится явно только на первом subword |
| Копировать метку на все subword | все части получают `B/I-ORG` | больше обучающих сигналов | нужно аккуратно менять `B` на `I` для продолжений |
| Использовать word-level pooling | объединяем subword embeddings в слово | ближе к исходной разметке | сложнее реализация |

Частый практический вариант:

```text
Слово:      Газпромбанке
Subwords:   Газ      ##пром    ##банке
Labels:     B-ORG    -100      -100
```

`-100` в PyTorch/HuggingFace обычно означает: не учитывать этот токен в loss.

Если копировать метку на все subword, лучше делать так:

```text
Слово:      Газпромбанке
Subwords:   Газ      ##пром    ##банке
Labels:     B-ORG    I-ORG     I-ORG
```

А не `B-ORG B-ORG B-ORG`, иначе модель увидит три разные сущности вместо одной.

### 7. Практический пайплайн NER-задачи

В реальном проекте NER обычно решают не с модели, а со схемы данных:

1. **Определить сущности.** Например: `COMPANY`, `POSITION`, `SKILL`, `DATE`, `SALARY`.
2. **Написать guideline для разметчиков.** Что считать сущностью, где границы, как размечать спорные случаи.
3. **Разметить небольшой датасет.** Лучше начать с 200-500 документов и посмотреть, насколько задача вообще однозначна.
4. **Проверить качество разметки.** Если два человека размечают один и тот же текст по-разному, модель тоже будет путаться.
5. **Обучить baseline.** Например, `bert-base-multilingual-cased` или `rubert` + token classification.
6. **Посмотреть ошибки.** Не только общий F1, а конкретные провалы: границы, редкие классы, доменные термины.
7. **Доработать guideline и данные.** Часто качество сильнее растёт от хорошей разметки, чем от смены архитектуры.
8. **Добавить постобработку.** Нормализация дат, объединение сущностей, словари, правила.
9. **Проверить на production-like данных.** Модель может хорошо работать на чистой разметке и плохо на реальных документах.

**Пример для резюме:**

```text
"С 2021 по 2024 работал ML Engineer в Яндексе, использовал PyTorch и Spark"
```

Можно извлечь:

```json
{
  "dates": ["2021", "2024"],
  "position": ["ML Engineer"],
  "organization": ["Яндексе"],
  "skills": ["PyTorch", "Spark"]
}
```

После NER часто нужен ещё один шаг — **entity normalization**:

```text
Яндексе -> Яндекс
Pytorch -> PyTorch
питон -> Python
```

NER отвечает за извлечение, а нормализация приводит сущности к каноническому виду.

### 8. NER, LLM и RAG

В современных LLM/RAG-системах NER полезен не только как отдельная NLP-задача.

**Где применяется:**
- выделить компании, даты, продукты и людей из документов;
- построить metadata для чанков в RAG;
- фильтровать поиск по сущностям: `company = "Сбер"`, `year = 2024`;
- строить knowledge graph;
- проверять, не галлюцинирует ли LLM новые сущности;
- извлекать structured output из документов.

Например, перед загрузкой документов в векторную базу можно сделать:

```text
Документ -> чанки -> NER -> metadata -> vector DB
```

Тогда у чанка появятся метаданные:

```json
{
  "organizations": ["Сбер", "GigaChat"],
  "dates": ["2024"],
  "technologies": ["RAG", "BM25", "FAISS"]
}
```

И retrieval можно делать гибридным:
- semantic search по смыслу;
- BM25 по словам;
- metadata filters по сущностям.

LLM тоже может делать entity extraction через JSON/structured output, но supervised NER-модель часто выигрывает, когда нужны:
- низкая latency;
- дешёвый массовый прогон миллионов документов;
- стабильная схема классов;
- воспроизводимость;
- меньше галлюцинаций.

## Типичные ошибки

- **Считать token accuracy главной метрикой:** из-за доминирования `O` она часто завышена.
- **Не выравнивать labels после subword-токенизации:** слово может распасться на несколько subword-токенов, и нужно решить, как размечать части.
- **Использовать bidirectional модель для авторегрессионной генерации:** для NER это нормально, для генерации будущий контекст недоступен.
- **Путать NER и text classification:** NER извлекает сущности и их границы, а классификация текста выдаёт один или несколько классов на весь текст.
- **Оценивать только общий F1:** можно не заметить, что редкие сущности вроде `MONEY` или `EVENT` модель почти не находит.
- **Игнорировать guideline разметки:** если люди размечают границы по-разному, модель будет учиться на шумных целях.
- **Не делать нормализацию сущностей:** извлечь `Сбере`, `Сбербанк`, `ПАО Сбербанк` — это только половина задачи; часто нужно привести их к одному ID.
- **Ожидать, что словарь решит NER:** словари помогают, но не понимают контекст и дают ложные совпадения.

## Каверзные вопросы

> [!question] Почему BiLSTM можно использовать для NER, но нельзя для decoder генерации?
> В NER весь текст уже известен, поэтому правый контекст доступен. В авторегрессионной генерации будущих токенов ещё нет, смотреть справа налево нельзя.

> [!question] Почему CRF может улучшить качество поверх BERT?
> BERT даёт сильные token embeddings, но независимая softmax-голова не знает ограничений переходов меток. CRF добавляет последовательностную согласованность.

> [!question] Почему accuracy почти бесполезна для NER?
> Потому что большинство токенов обычно имеют метку `O`. Модель может почти всё размечать как `O`, получать высокую token accuracy и при этом не находить ни одной полезной сущности.

> [!question] Почему в NER важны границы сущности?
> Потому что downstream-система обычно ждёт конкретное поле. `Илон` вместо `Илон Маск` — это не просто «почти правильно», а другая извлечённая сущность.

> [!question] Когда CRF поверх BERT может не дать прироста?
> Если датасет большой, сущности простые, BERT уже хорошо выучил локальный контекст, а ошибки переходов редки. Тогда CRF усложнит обучение и инференс, но почти не улучшит F1.

> [!question] Чем NER через BERT отличается от NER через LLM prompt?
> BERT token classification обучается на фиксированную схему меток и быстро предсказывает label для каждого токена. LLM extraction гибче и может возвращать JSON без отдельного обучения, но дороже, медленнее и менее детерминированно.

## Как отвечать на собеседовании

> [!example] Короткий ответ
> NER — это sequence labeling задача: для каждого токена нужно предсказать метку, обычно в BIO/BILOU-схеме. Например, `B-PER` означает начало имени человека, `I-PER` — продолжение, `O` — токен вне сущности. Современный baseline — encoder-only transformer вроде BERT/RuBERT с token classification head. Иногда сверху добавляют CRF, чтобы учитывать допустимые переходы между метками и выбирать лучшую последовательность целиком. Качество лучше считать entity-level Precision/Recall/F1, потому что token accuracy завышается из-за большого числа `O`-токенов.

> [!example] Более сильный ответ
> Важные практические детали: нужно аккуратно выравнивать word-level labels с subword-токенами, следить за guideline разметки, смотреть ошибки по типам сущностей и отдельно проверять границы. Для production часто добавляют нормализацию сущностей и постобработку. В RAG NER можно использовать для метаданных чанков, фильтрации поиска и построения structured extraction pipeline.

## Проверка себя

- Чем BIO отличается от простой разметки типов сущностей?
- Почему entity-level F1 строже token accuracy?
- Как обработать слово, разбитое на несколько subword-токенов?
- Зачем нужны `B-` и `I-`, если тип сущности уже известен?
- Чем BIOES/BILOU информативнее BIO?
- Почему CRF выбирает последовательность целиком, а не метки независимо?
- Почему `Илон` вместо `Илон Маск` считается ошибкой на entity-level?
- Когда лучше использовать supervised NER, а когда LLM extraction?
