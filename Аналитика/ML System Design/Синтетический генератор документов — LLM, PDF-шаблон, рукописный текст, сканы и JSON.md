# Синтетический генератор документов — LLM, PDF-шаблон, рукописный текст, сканы и JSON

> [!abstract] Суть
> Для фиксированного заявления удобно разделить систему на четыре слоя: генерация согласованных значений, размещение этих значений в шаблоне, имитация реального скана и выпуск эталонного JSON. LLM нужна прежде всего для содержательно правдоподобных данных и текстовых полей. Координаты, форматирование, валидацию и воспроизводимость лучше держать в обычном коде.

## 1. Постановка задачи

Предположим, у нас есть PDF-шаблон заявления. В нём напечатаны постоянные элементы и пустые области:

```text
ФИО заявителя: ______________________________
Дата рождения: ______________
Среднемесячный доход: __________________ руб.
Причина заявления:
________________________________________________
________________________________________________
```

Клиент заполняет поля от руки, фотографирует или сканирует заявление. Нужно получить обучающий пример:

1. изображение или PDF заполненного и реалистично искажённого документа;
2. JSON с правильными значениями полей;
3. метаданные о шаблоне, seed, типе искажений и версии генератора.

Минимальный результат может выглядеть так:

```json
{
  "document_id": "synthetic-000001",
  "template_id": "application_v1",
  "fields": {
    "full_name": "Иванов Иван Сергеевич",
    "birth_date": "1988-04-17",
    "monthly_income": 145000,
    "reason": "Прошу рассмотреть заявление в связи с изменением семейных обстоятельств."
  }
}
```

В JSON нет координат, потому что в текущей задаче нужно только связать название поля и его значение. Но координаты всё равно понадобятся **внутри конфигурации рендерера**, чтобы понять, куда поставить каждое значение на шаблоне. Это не противоречие: координаты — техническая информация о шаблоне, а не часть целевой разметки.

## 2. Почему нельзя поручить всё LLM

Кажется естественным отправить PDF в GPT и попросить «придумать значения и заполнить документ». Для масштабируемого генератора это неудобно:

- модель может вернуть JSON с ошибкой формата;
- дата может быть невозможной или не совпадать с возрастом;
- доход может прийти строкой «примерно сто тысяч» вместо числа;
- причина заявления может выходить за пределы пустой области;
- одинаковые значения будут повторяться;
- LLM не гарантирует точное положение текста на странице;
- результат сложнее воспроизвести и проверить.

Надёжнее использовать такой конвейер:

```text
схема полей и ограничения
        ↓
генерация структурированных значений
        ↓
Pydantic-валидация и согласованность
        ↓
конфигурация координат фиксированного шаблона
        ↓
рендеринг печатного/рукописного текста
        ↓
аугментации реального скана
        ↓
проверка изображения и JSON
        ↓
PNG/JPEG + JSON (+ опциональный PDF)
```

LLM отвечает за то, что хорошо делает языковая модель: разнообразный естественный текст, согласованные сценарии, вариативность формулировок. Python отвечает за то, где и в каком формате это появится, и не даёт нарушить инварианты.

## 3. Схема данных и инварианты

### 3.1. Pydantic-модель

Сначала описываем не промпт, а контракт результата.

```python
from datetime import date
from typing import Annotated

from pydantic import BaseModel, Field, field_validator, model_validator


# Фиксируем дату, чтобы один и тот же seed давал одинаковый возраст и дату рождения
# даже при повторном запуске генератора через несколько месяцев.
REFERENCE_DATE = date(2026, 8, 27)


class ApplicationData(BaseModel):
    full_name: str = Field(min_length=5, max_length=80)
    birth_date: date
    monthly_income: Annotated[int, Field(ge=20_000, le=2_000_000)]
    reason: str = Field(min_length=20, max_length=240)

    @field_validator("full_name")
    @classmethod
    def full_name_has_several_parts(cls, value: str) -> str:
        parts = value.split()
        if len(parts) < 2:
            raise ValueError("ФИО должно содержать хотя бы фамилию и имя")
        return " ".join(parts)

    @field_validator("reason")
    @classmethod
    def normalize_reason(cls, value: str) -> str:
        return " ".join(value.split())

    @model_validator(mode="after")
    def check_birth_date(self):
        age = REFERENCE_DATE.year - self.birth_date.year
        if (REFERENCE_DATE.month, REFERENCE_DATE.day) < (self.birth_date.month, self.birth_date.day):
            age -= 1
        if not 18 <= age <= 90:
            raise ValueError("Возраст должен быть от 18 до 90 лет")
        return self
```

### 3.2. Какие ограничения стоит зафиксировать

Для каждого поля заранее описываем:

| Поле | Тип | Пример ограничения | Что проверяем |
|---|---|---|---|
| `full_name` | строка | 2–3 слова, русские буквы | длина, алфавит, отсутствие служебных слов |
| `birth_date` | дата | возраст 18–90 лет | календарная корректность, формат |
| `monthly_income` | целое | 20 000–2 000 000 | диапазон, отсутствие дробной строки |
| `reason` | текст | 20–240 символов | длина, отсутствие выдуманных реквизитов |

Кроме локальных правил нужны **межполевая согласованность** и сценарные ограничения. Например, можно заранее выбрать сценарий `income_level = "low"`, а затем попросить генератор подобрать доход из диапазона 20–80 тысяч и причину, которая не противоречит этому сценарию. Это лучше, чем надеяться, что LLM сама согласует десять полей.

## 4. Какие значения генерировать через LLM, а какие — обычным кодом

### 4.1. ФИО

ФИО можно генерировать через LLM, но для разнообразия и контроля лучше использовать `Faker` с локалью `ru_RU` или собственные списки фамилий, имён и отчеств. LLM может придумать редкое, стилистически странное или смешанное имя. Она нужна, если требуется особая демография, региональный стиль или согласование текста с персонажем.

### 4.2. Дата рождения

Генерируем в Python. Это гарантирует корректный календарь и управляемое распределение возрастов. LLM здесь не даёт преимуществ.

### 4.3. Уровень дохода

Числовое значение лучше генерировать из заданного распределения, а не просить модель случайно придумать число. Например, сделать 50% заявителей с доходом 40–100 тысяч, 35% — 100–250 тысяч и 15% — выше 250 тысяч. Так датасет будет похож на целевую популяцию, а не на равномерный набор.

### 4.4. Причина заявления

Это хороший кандидат для LLM: нужно получить много естественных, но контролируемых вариантов рукописного текста. Модель можно ограничить списком классов причин и требованием не добавлять несуществующие номера документов, адреса и суммы.

### 4.5. Гибридная рекомендация

Практическое правило:

- простые числовые и календарные поля — Python;
- имена — Faker/словари, при необходимости LLM для специальных сценариев;
- длинный естественный текст — LLM;
- согласованность и итоговая проверка — Python;
- изображение и координаты — Python и конфигурация шаблона.

## 5. Генерация значений через GPT API

### 5.1. LLM-адаптер с абстрактным интерфейсом

Чтобы генератор не зависел от конкретного поставщика, задаём простой интерфейс:

```python
from typing import Protocol


class TextScenarioGenerator(Protocol):
    def generate_reason(
        self,
        *,
        age: int,
        income: int,
        scenario: str,
        language: str = "ru",
    ) -> str:
        ...
```

Рендерер и валидатор не должны знать, GPT это, YandexGPT или локальная модель. Меняется только адаптер.

### 5.2. Пример адаптера GPT со структурированным ответом

Если через API генерируем сразу весь сценарий, просим модель вернуть объект по Pydantic-схеме. В Python SDK OpenAI это можно оформить так:

```python
from datetime import date
from openai import OpenAI


client = OpenAI()  # ключ берётся из переменной окружения OPENAI_API_KEY


class LLMReason(BaseModel):
    reason: str = Field(min_length=20, max_length=240)


def generate_reason_with_gpt(
    *,
    age: int,
    income: int,
    scenario: str,
) -> str:
    prompt = f"""
Сгенерируй естественную краткую причину заявления на русском языке.
Условия:
- возраст заявителя: {age} лет;
- среднемесячный доход: {income} рублей;
- сценарий: {scenario};
- длина текста: от 20 до 180 символов;
- не добавляй паспортные данные, адрес, номера документов и факты,
  которых нет во входных условиях;
- текст должен выглядеть как обычное объяснение клиента, без заголовка.
"""

    completion = client.chat.completions.parse(
        model="gpt-4o-mini",
        temperature=0.9,
        messages=[
            {
                "role": "system",
                "content": "Ты генерируешь только синтетические данные для тестового датасета.",
            },
            {"role": "user", "content": prompt},
        ],
        response_format=LLMReason,
    )
    parsed = completion.choices[0].message.parsed
    if parsed is None:
        raise RuntimeError("GPT не вернула структурированный ответ")
    return parsed.reason
```

Название модели в примере условное: в рабочем проекте выбираем доступную модель с поддержкой структурированного вывода и проверяем её ограничения. Важно не надеяться на JSON, который модель просто написала текстом: нужен режим, в котором SDK валидирует ответ по схеме.

### 5.3. Генерация всего объекта одним вызовом

Если важна согласованность нескольких текстовых полей, можно передать модели уже сгенерированные детерминированные поля и попросить вернуть только зависимые значения:

```python
class GeneratedTextFields(BaseModel):
    full_name: str = Field(min_length=5, max_length=80)
    reason: str = Field(min_length=20, max_length=240)


def generate_text_fields(age: int, income: int, scenario: str) -> GeneratedTextFields:
    completion = client.chat.completions.parse(
        model="gpt-4o-mini",
        temperature=0.9,
        messages=[
            {
                "role": "system",
                "content": (
                    "Генерируй только синтетические русскоязычные данные. "
                    "Не используй реальные персональные данные и не добавляй новые поля."
                ),
            },
            {
                "role": "user",
                "content": (
                    f"Возраст: {age}. Доход: {income}. Сценарий: {scenario}. "
                    "Верни ФИО и естественную причину заявления."
                ),
            },
        ],
        response_format=GeneratedTextFields,
    )
    result = completion.choices[0].message.parsed
    if result is None:
        raise RuntimeError("Пустой ответ GPT")
    return result
```

Но даже структурированный ответ нужно прогнать через собственную валидацию. API-проверка формата не знает, помещается ли причина в конкретный прямоугольник на PDF и соответствует ли распределение значений вашей целевой популяции.

### 5.4. Ограничение повторов и стоимости

При больших объёмах не следует делать отдельный вызов LLM для каждой даты, имени и числа. Практичнее:

- генерировать числовые поля локально;
- отправлять в LLM только текстовые поля;
- кэшировать ответы по хешу входного сценария;
- использовать пакетные запросы, если API это поддерживает;
- ограничивать повторные попытки и иметь fallback на локальный шаблон текста;
- логировать `request_id`, версию промпта и модель без сохранения секретного ключа.

Для синтетических данных нельзя отправлять в API реальные ФИО или документы клиентов. В запросе должны быть только искусственные значения и сценарии.

## 6. Генерация связанного примера

```python
import random
from datetime import date, timedelta

from faker import Faker


fake = Faker("ru_RU")


def random_birth_date(rng: random.Random) -> date:
    # Упрощённое распределение: возраст от 18 до 90 лет.
    age = rng.randint(18, 90)
    start = REFERENCE_DATE - timedelta(days=(age + 1) * 365)
    end = REFERENCE_DATE - timedelta(days=age * 365)
    return start + timedelta(days=rng.randint(0, max(1, (end - start).days)))


def sample_income(rng: random.Random) -> int:
    bucket = rng.choices(
        ["low", "middle", "high"],
        weights=[0.50, 0.35, 0.15],
        k=1,
    )[0]
    ranges = {
        "low": (20_000, 80_000),
        "middle": (80_001, 250_000),
        "high": (250_001, 2_000_000),
    }
    lo, hi = ranges[bucket]
    return rng.randrange(lo, hi + 1, 1_000)


def generate_base_record(seed: int) -> tuple[int, date, int, str]:
    rng = random.Random(seed)
    birth_date = random_birth_date(rng)
    income = sample_income(rng)
    age = REFERENCE_DATE.year - birth_date.year
    scenario = rng.choice(
        [
            "изменение семейных обстоятельств",
            "временное снижение дохода",
            "необходимость пересмотра условий",
            "переезд в другой регион",
        ]
    )
    return age, birth_date, income, scenario
```

Здесь LLM может сформировать ФИО и причину, но дата и доход полностью воспроизводимы по seed. В датасете сохраняем именно seed, чтобы можно было повторить проблемный пример.

## 7. Как узнать, куда вставлять значения в PDF

### 7.1. Главное правило для фиксированного шаблона

Для одного стабильного шаблона самый надёжный способ — **один раз измерить прямоугольники полей и сохранить их в конфигурации**. Не нужно каждый раз просить LLM угадывать координаты.

```yaml
template_id: application_v1
page: 0
coordinate_system: pdf_points
fields:
  full_name:
    rect: [185, 198, 510, 224]
    mode: handwriting
    max_font_size: 20
    min_font_size: 10
  birth_date:
    rect: [185, 244, 330, 269]
    mode: handwriting
    max_font_size: 18
    min_font_size: 10
  monthly_income:
    rect: [185, 287, 350, 312]
    mode: handwriting
    max_font_size: 18
    min_font_size: 10
  reason:
    rect: [95, 355, 520, 445]
    mode: handwriting_multiline
    max_font_size: 17
    min_font_size: 9
    line_spacing: 1.15
```

Координаты в PDF обычно задаются в пунктах (1/72 дюйма), а начало координат в PyMuPDF находится сверху страницы. Если библиотека использует нижний левый угол, нужно один раз явно преобразовать систему координат. Ошибки в начале координат — частая причина, почему текст оказывается вверх ногами или на другой части страницы.

### 7.2. Полуавтоматическое получение координат по напечатанным labels

Если PDF содержит текстовый слой, PyMuPDF может вернуть слова и их прямоугольники. Мы ищем напечатанную подпись и строим поле с известным смещением:

```python
import fitz  # PyMuPDF


def find_word_rect(page: fitz.Page, target: str) -> fitz.Rect:
    for x0, y0, x1, y1, word, *_ in page.get_text("words"):
        if word.strip().lower() == target.lower():
            return fitz.Rect(x0, y0, x1, y1)
    raise ValueError(f"Не нашли label: {target}")


def field_after_label(page: fitz.Page, label: str, width: float, height: float) -> list[float]:
    label_rect = find_word_rect(page, label)
    return [label_rect.x1 + 8, label_rect.y0 - 3, label_rect.x1 + 8 + width, label_rect.y0 - 3 + height]
```

Это работает, если подпись — одно слово и шаблон стабилен. Для «Дата рождения» нужно искать последовательность слов или использовать ручную конфигурацию. Если PDF — скан без текстового слоя, сначала нужен OCR, например Tesseract или другой движок, но координаты OCR всё равно проверяем вручную на эталонном шаблоне.

### 7.3. Почему не стоит использовать VLM для координат в каждом документе

VLM может приблизительно найти поле, но для фиксированного шаблона это добавляет нестабильность и расход API. Если шаблон меняется часто, можно использовать VLM/OCR только на этапе регистрации новой версии шаблона: модель предлагает координаты, человек подтверждает их, затем они сохраняются в YAML. Рендеринг каждого синтетического документа должен быть детерминированным.

### 7.4. Координата поля — это прямоугольник, а не одна точка

Для вставки текста нам нужна не «координата ФИО», а допустимая область:

```text
field_box = (x0, y0, x1, y1)
             └─ левый верхний угол
                     └─ правый нижний угол
```

Сначала определяем этот прямоугольник одним из способов:

1. **Вручную на эталонном шаблоне.** Для одного фиксированного PDF это обычно самый надёжный способ: открыть страницу в редакторе, измерить границы пустого места и сохранить их в YAML.
2. **От напечатанной подписи.** Находим текст `ФИО заявителя` через `page.get_text("words")` или OCR и задаём область справа от подписи с известным отступом.
3. **По линии-подчёркиванию.** Для скана можно найти горизонтальный отрезок через OpenCV и взять прямоугольник над ним. Это удобно для простых форм, но ломается на фоне, тенях и пересекающихся линиях.
4. **С помощью VLM/OCR при регистрации новой версии шаблона.** Модель может предложить области, но человек должен подтвердить их один раз. Запрашивать координаты у VLM для каждого синтетического документа не нужно.

После этого случайное размещение делаем не случайным выбором произвольной точки, а выбором **начала текста из безопасного диапазона**. Если ширина поля равна `W`, а ширина конкретной строки — `w`, то координата левого края должна лежать в диапазоне:

```text
x ∈ [x0 + margin, x1 − margin − w]
```

Аналогично для вертикали:

```text
y ∈ [y0 + margin, y1 − margin − h]
```

где `h` — фактическая высота текста, а `margin` — небольшой запас. Поэтому длинная строка автоматически получает более узкий диапазон случайного смещения, а короткая может «гулять» сильнее.

```python
from PIL import Image, ImageDraw, ImageFont
import random


def sample_text_origin(
    text: str,
    field_box: tuple[int, int, int, int],
    font: ImageFont.FreeTypeFont,
    rng: random.Random,
    margin_ratio: float = 0.08,
) -> tuple[int, int]:
    """Выбрать безопасную точку рисования, не выходя за field_box."""
    x0, y0, x1, y1 = field_box
    probe = Image.new("L", (1, 1))
    draw = ImageDraw.Draw(probe)
    # bbox учитывает внутренний отступ шрифта: это важно для букв с выносными
    # элементами и для кириллицы.
    left, top, right, bottom = draw.textbbox((0, 0), text, font=font)
    text_width = right - left
    text_height = bottom - top
    margin = max(2, int(min(x1 - x0, y1 - y0) * margin_ratio))

    min_x = x0 + margin - left
    max_x = x1 - margin - text_width - left
    min_y = y0 + margin - top
    max_y = y1 - margin - text_height - top
    if min_x > max_x or min_y > max_y:
        raise ValueError("Текст не помещается в область поля даже с минимальным отступом")

    return rng.randint(min_x, max_x), rng.randint(min_y, max_y)
```

Для строки причины делаем это для всего блока, а не для каждой строки отдельно. Иначе строки начнут «плавать» и перестанут выглядеть как один рукописный ответ. Внутри блока можно добавить очень небольшой jitter (случайный сдвиг каждой строки на 1–2 пикселя), но сначала проверяем общую высоту блока.

Если после размещения добавляем поворот, оставляем дополнительный запас по краям. Чем больше угол, тем больше должен быть запас. Для строгой гарантии можно рисовать текст на локальном прозрачном слое, повернуть этот слой и проверить его фактический `alpha`-bounding box перед вставкой в страницу. Если слой выходит за field_box, уменьшаем угол или перегенерируем seed.

## 8. Нужно ли сначала рендерить PDF

Зависит от того, что будет входом для будущей модели.

### Если модель обучается на изображениях сканов

Да, нужно получить растровое изображение — PNG или JPEG. Чистый векторный PDF слишком аккуратный и не похож на фотографию или скан. Кроме того, в PDF может остаться текстовый слой, который даст модели или OCR нечесткую подсказку.

### Если продакшен принимает PDF

Сохраняем и PDF-ветку, но проверяем, что текстовый слой удалён или недоступен, если в реальности документы приходят как сканы. Иначе offline-оценка будет завышена: система использует не изображение, а скрытый текст.

### Практическая рекомендация

Хранить три артефакта:

```text
document.pdf       — опциональная производственная форма
document.png       — канонический растровый скан для обучения/оценки
document.json      — эталонные значения
```

PDF удобно использовать как геометрическую основу, а PNG/JPEG — как реальный вход для OCR/VLM. Один и тот же JSON связан с обоими представлениями.

## 9. Рендеринг заполненного шаблона

### 9.1. Рендерим PDF-страницу в изображение

```python
from pathlib import Path

import fitz
from PIL import Image


def render_pdf_page(pdf_path: str | Path, dpi: int = 300) -> Image.Image:
    document = fitz.open(pdf_path)
    page = document[0]
    scale = dpi / 72
    pixmap = page.get_pixmap(
        matrix=fitz.Matrix(scale, scale),
        alpha=False,
        colorspace=fitz.csRGB,
    )
    image = Image.frombytes("RGB", [pixmap.width, pixmap.height], pixmap.samples)
    document.close()
    return image
```

300 DPI — разумная отправная точка для мелкого печатного и рукописного текста. Для первого эксперимента можно хранить 200–300 DPI, а затем проверить, как размер влияет на качество и стоимость хранения.

### 9.2. Перевод прямоугольника из PDF в пиксели

```python
def pdf_rect_to_pixels(rect: list[float], dpi: int) -> tuple[int, int, int, int]:
    scale = dpi / 72
    x0, y0, x1, y1 = rect
    return tuple(round(v * scale) for v in (x0, y0, x1, y1))
```

### 9.3. Подбор шрифта под поле

Для имитации рукописи используем шрифт с разрешённой лицензией, например локально установленный вариант из семейства handwriting. В продакшене нельзя случайно включать шрифт, который запрещает коммерческое использование.

```python
from PIL import ImageFont


def fit_font(text: str, box: tuple[int, int, int, int], font_path: str,
             max_size: int, min_size: int) -> ImageFont.FreeTypeFont:
    x0, y0, x1, y1 = box
    width, height = x1 - x0, y1 - y0
    for size in range(max_size, min_size - 1, -1):
        font = ImageFont.truetype(font_path, size=size)
        bbox = font.getbbox(text)
        if bbox[2] - bbox[0] <= width and bbox[3] - bbox[1] <= height:
            return font
    return ImageFont.truetype(font_path, size=min_size)
```

Если даже минимальный шрифт не помещается, это не повод молча обрезать строку. Нужно либо сократить текст отдельным валидатором, либо отправить пример на ручной контроль/перегенерацию.

### 9.4. Печать одной строки с небольшой вариативностью

```python
import random
from PIL import Image, ImageDraw, ImageFont


def draw_handwritten_line(
    image: Image.Image,
    text: str,
    box: tuple[int, int, int, int],
    font_path: str,
    rng: random.Random,
    max_size: int = 60,
    min_size: int = 28,
) -> None:
    x0, y0, x1, y1 = box
    font = fit_font(text, box, font_path, max_size, min_size)

    # Отдельный прозрачный слой позволяет слегка повернуть всю строку.
    layer = Image.new("RGBA", image.size, (0, 0, 0, 0))
    draw = ImageDraw.Draw(layer)
    # Не центрируем все примеры одинаково: выбираем допустимое начало строки
    # с учётом фактического bbox текста и небольшого внутреннего поля.
    x, y = sample_text_origin(text, box, font, rng)
    ink = (28 + rng.randint(-8, 8), 35 + rng.randint(-8, 8), 48 + rng.randint(-8, 8), 215)
    draw.text((x, y), text, font=font, fill=ink)

    angle = rng.uniform(-2.0, 2.0)
    center = ((x0 + x1) / 2, (y0 + y1) / 2)
    layer = layer.rotate(angle, resample=Image.Resampling.BICUBIC, center=center)
    image.paste(layer, (0, 0), layer)
```

Один и тот же шрифт, одинаковый угол и одинаковая толщина быстро выдадут синтетику. Поэтому варьируем seed, шрифт, размер, наклон, насыщенность чернил и положение внутри допустимого поля. Но вариативность должна оставаться реалистичной: слишком сильный наклон или хаотичное смещение создадут данные, которых не бывает в продакшене.

### 9.5. Перенос длинной причины на несколько строк

```python
def wrap_text_to_box(text: str, font: ImageFont.FreeTypeFont, max_width: int) -> list[str]:
    words = text.split()
    lines: list[str] = []
    current = ""
    dummy = Image.new("RGB", (1, 1))
    draw = ImageDraw.Draw(dummy)

    for word in words:
        candidate = f"{current} {word}".strip()
        width = draw.textbbox((0, 0), candidate, font=font)[2]
        if width <= max_width or not current:
            current = candidate
        else:
            lines.append(current)
            current = word
    if current:
        lines.append(current)
    return lines


def draw_multiline_reason(
    image: Image.Image,
    text: str,
    box: tuple[int, int, int, int],
    font_path: str,
    rng: random.Random,
) -> bool:
    x0, y0, x1, y1 = box
    for size in range(56, 20, -1):
        font = ImageFont.truetype(font_path, size=size)
        lines = wrap_text_to_box(text, font, x1 - x0)
        line_height = int(size * 1.15)
        if len(lines) * line_height <= y1 - y0:
            layer = Image.new("RGBA", image.size, (0, 0, 0, 0))
            draw = ImageDraw.Draw(layer)
            for i, line in enumerate(lines):
                dx = rng.randint(-2, 2)
                dy = rng.randint(-1, 1)
                draw.text((x0 + dx, y0 + i * line_height + dy), line, font=font,
                          fill=(30, 37, 50, 215))
            image.paste(layer, (0, 0), layer)
            return True
    return False
```

Возвращаем `False`, если текст не поместился. Такой пример нужно перегенерировать или явно пометить как `needs_review`, а не записывать обрезанную причину и ложный JSON.

## 10. Имитация настоящего скана

После вставки рукописного текста изображение всё ещё выглядит слишком чистым. Реальный скан или фотография содержит несколько независимых искажений.

### 10.1. Базовые искажения

- небольшой поворот и сдвиг;
- перспективное искажение углов листа;
- неравномерное освещение и тени;
- размытие из-за движения или фокуса;
- JPEG-сжатие;
- мелкий сенсорный шум;
- потеря контраста и выцветание чернил;
- локальные пятна, просвечивание или тени от сгиба.

Нельзя применять каждый эффект с максимальной силой. Лучше задать распределение вероятностей и диапазоны, полученные из реальных примеров.

### 10.2. Поворот, шум и JPEG-сжатие

```python
import io
import numpy as np
from PIL import Image, ImageFilter, ImageEnhance


def add_scan_noise(image: Image.Image, rng: np.random.Generator) -> Image.Image:
    image = image.convert("RGB")
    angle = float(rng.uniform(-2.5, 2.5))
    image = image.rotate(angle, resample=Image.Resampling.BICUBIC, expand=False, fillcolor=(245, 245, 243))

    if rng.random() < 0.65:
        radius = float(rng.uniform(0.2, 1.2))
        image = image.filter(ImageFilter.GaussianBlur(radius=radius))

    if rng.random() < 0.75:
        image = ImageEnhance.Contrast(image).enhance(float(rng.uniform(0.82, 1.08)))
        image = ImageEnhance.Brightness(image).enhance(float(rng.uniform(0.88, 1.08)))

    arr = np.asarray(image).astype(np.float32)
    noise = rng.normal(0, rng.uniform(1.0, 5.0), size=arr.shape[:2] + (1,))
    arr = np.clip(arr + noise, 0, 255).astype(np.uint8)
    image = Image.fromarray(arr, mode="RGB")

    if rng.random() < 0.8:
        buffer = io.BytesIO()
        quality = int(rng.integers(45, 96))
        image.save(buffer, format="JPEG", quality=quality)
        image = Image.open(buffer).convert("RGB")
    return image
```

### 10.3. Перспективное искажение

Для фотографии документа можно использовать OpenCV `getPerspectiveTransform` и `warpPerspective`. Важно менять четыре угла умеренно, иначе синтетика станет слишком экстремальной.

```python
import cv2


def perspective_warp(image: Image.Image, rng: np.random.Generator) -> Image.Image:
    arr = np.asarray(image)
    h, w = arr.shape[:2]
    margin = min(h, w) * 0.04
    source = np.float32([[0, 0], [w - 1, 0], [w - 1, h - 1], [0, h - 1]])
    target = source + rng.uniform(-margin, margin, size=(4, 2)).astype(np.float32)
    matrix = cv2.getPerspectiveTransform(source, target)
    warped = cv2.warpPerspective(arr, matrix, (w, h), borderValue=(245, 245, 243))
    # arr хранится в порядке каналов RGB, поэтому дополнительная конвертация не нужна.
    return Image.fromarray(warped)
```

Для реального проекта лучше добавить тени и неравномерное освещение, используя маску с плавным градиентом. Это сильнее влияет на OCR, чем обычный равномерный шум.

## 11. Полный генератор одного документа

Ниже схема, а не скрытый магический вызов: каждый этап можно отдельно тестировать и переигрывать.

```python
import json
from pathlib import Path


def build_document(
    *,
    template_pdf: str,
    template_config: dict,
    output_dir: str,
    document_id: str,
    seed: int,
    font_path: str,
) -> None:
    py_rng = random.Random(seed)
    np_rng = np.random.default_rng(seed)

    age, birth_date, income, scenario = generate_base_record(seed)
    text_fields = generate_text_fields(age=age, income=income, scenario=scenario)

    data = ApplicationData(
        full_name=text_fields.full_name,
        birth_date=birth_date,
        monthly_income=income,
        reason=text_fields.reason,
    )

    image = render_pdf_page(template_pdf, dpi=300)
    dpi = 300
    field_cfg = template_config["fields"]

    fields_for_render = {
        "full_name": data.full_name,
        "birth_date": data.birth_date.strftime("%d.%m.%Y"),
        "monthly_income": f"{data.monthly_income:,}".replace(",", " "),
        "reason": data.reason,
    }

    for field_name, value in fields_for_render.items():
        box = pdf_rect_to_pixels(field_cfg[field_name]["rect"], dpi)
        if field_name == "reason":
            ok = draw_multiline_reason(image, value, box, font_path, py_rng)
        else:
            draw_handwritten_line(image, value, box, font_path, py_rng)
            ok = True
        if not ok:
            raise ValueError(f"Поле {field_name} не помещается в шаблон")

    image = add_scan_noise(image, np_rng)
    if np_rng.random() < 0.45:
        image = perspective_warp(image, np_rng)

    out = Path(output_dir)
    out.mkdir(parents=True, exist_ok=True)
    image_path = out / f"{document_id}.png"
    json_path = out / f"{document_id}.json"
    image.save(image_path, format="PNG", optimize=True)
    json_path.write_text(
        json.dumps(
            {
                "document_id": document_id,
                "template_id": template_config["template_id"],
                "seed": seed,
                "fields": data.model_dump(mode="json"),
                "generation": {"renderer_version": "1.0.0", "dpi": dpi},
            },
            ensure_ascii=False,
            indent=2,
        ),
        encoding="utf-8",
    )
```

В настоящем проекте вызов LLM лучше вынести из функции рендеринга и запускать отдельным этапом. Тогда можно повторно отрендерить документ с другим шрифтом или шумом, не оплачивая новый API-вызов.

## 12. Нужен ли отдельный PDF-рендерер

Есть три разумных варианта.

### Вариант A. PDF как фон, Pillow/OpenCV как итог

1. PyMuPDF рендерит чистую страницу в PNG.
2. Pillow рисует рукописный текст.
3. OpenCV/Pillow добавляют искажения.
4. PNG становится основным входом для OCR/VLM.

Это самый удобный вариант для синтетических сканов.

### Вариант B. Наложение текста в PDF

Можно создать прозрачный overlay через ReportLab или вставить текст через PyMuPDF, объединить его с исходной страницей и сохранить PDF. Это полезно, если нужно тестировать именно PDF-пайплайн. Но после этого всё равно стоит сделать растровую копию и проверить, что в ней нет скрытого текстового слоя.

### Вариант C. PDF только как промежуточный формат

Шаблон хранится как PDF, но наружу отдаём только PNG/JPEG и JSON. Этот вариант проще, если будущая модель принимает изображения.

**Рекомендация:** сохранять PDF для отладки геометрии и PNG/JPEG для обучения. Не считать PDF обязательным результатом, если production-система распознаёт фотографии и сканы.

Если нужен PDF-артефакт из уже подготовленного изображения, его можно сохранить отдельно:

```python
from pathlib import Path
from PIL import Image


def save_scan_as_pdf(image: Image.Image, path: str | Path, dpi: int = 300) -> None:
    # PDF должен быть RGB, иначе некоторые просмотрщики некорректно сохраняют альфа-канал.
    image.convert("RGB").save(path, format="PDF", resolution=dpi)
```

Такой PDF содержит растровую страницу. Это удобно для тестирования загрузки PDF, но не возвращает исходный редактируемый текстовый слой — именно этого и нужно избегать, если хотим честно проверять распознавание скана.

## 13. Проверка, что изображение соответствует JSON

Самая опасная ошибка синтетического датасета — JSON правильный, но на картинке другое значение или поле обрезано.

### 13.1. Геометрическая проверка

- текст не выходит за прямоугольник поля;
- все обязательные поля имеют ненулевую высоту и ширину;
- строка причины не обрезалась;
- документ не повернулся так, что часть листа исчезла;
- после аугментации поле осталось в пределах страницы.

### 13.2. OCR-проверка

Для части примеров прогоняем итоговый PNG через OCR и сравниваем нормализованные значения:

- дату сравниваем после приведения к ISO-формату;
- доход — после удаления пробелов и валютного символа;
- ФИО — после нормализации пробелов и регистра;
- причину — по символьному или токенному сходству.

OCR не должен быть единственным арбитром: рукописный текст он тоже может прочитать с ошибкой. Но резкое падение OCR-match показывает проблемы рендера или слишком сильные искажения.

### 13.3. VLM/LLM как дополнительный контроль

Небольшую выборку можно отдавать VLM с просьбой извлечь четыре поля по фиксированной схеме. Это не заменяет эталонный JSON, потому что модель может ошибаться, но помогает обнаружить систематические проблемы: слишком мелкий шрифт, плохой контраст, перепутанные поля.

### 13.4. Инварианты датасета

Автоматически проверяем:

- долю пустых и слишком похожих причин;
- распределение возраста и дохода;
- долю каждого сценария;
- каждый шрифт, угол, тип шума и качество JPEG;
- отсутствие реальных персональных данных;
- отсутствие одинакового seed у разных `document_id` без намерения;
- баланс шаблонов и типов дефектов.

## 14. Реалистичность и опасность «идеальной синтетики»

Синтетика полезна, но не гарантирует перенос на реальные сканы. Основные риски:

- рукопись выглядит как один и тот же шрифт;
- шумы слишком математические и не похожи на камеру;
- причины заявлений написаны слишком грамотно;
- все поля заполнены, хотя в реальности бывают пропуски;
- значения равномерно распределены и не похожи на бизнес-данные;
- нет новых шаблонов, обрезанных страниц, печатей и плохого освещения;
- модель запоминает позицию поля вместо понимания текста.

Поэтому нужно иметь небольшой набор настоящих обезличенных документов для проверки и сравнивать synthetic-to-real gap: как меняются OCR/VLM-метрики на синтетике и на реальных данных. Если синтетика даёт 99%, а реальные сканы 65%, генератор слишком простой или распределение не совпадает.

### Что варьировать

- 3–5 разрешённых рукописных шрифтов плюс разные размеры;
- наклон, плотность и цвет чернил;
- короткие и длинные причины;
- пропущенные необязательные поля;
- качество скана и фото;
- разные принтеры/бумагу/фон, если это соответствует продукту;
- распределение возраста и дохода;
- региональные и языковые варианты, если они встречаются в проде.

Разбиение train/validation/test делаем не только случайно по документам. Часть шрифтов, seed-диапазонов, уровней шума или вариантов шаблона нужно оставить только в тесте, чтобы проверить обобщение, а не запоминание генератора.

## 15. Архитектура для массовой генерации

```text
Template Registry
  ├─ PDF-шаблон
  ├─ YAML с полями и координатами
  └─ версия шаблона
          ↓
Scenario Sampler
  ├─ seed
  ├─ возраст/доход/сценарий
  └─ распределения и пропуски
          ↓
LLM Adapter (только нужные текстовые поля)
          ↓
Validator + Deduplicator
          ↓
Renderer
          ↓
Augmentation Pipeline
          ↓
QA: geometry + OCR + distributions
          ↓
Object Storage: image/pdf/json/metadata
```

Практические требования:

- **идемпотентность:** повторный запуск для `(template_id, seed, version)` выдаёт тот же пример или явно новую версию;
- **кэширование:** не генерировать повторно одинаковую причину;
- **rate limit/retry:** ограничивать запросы к LLM и повторять только временные ошибки;
- **версионирование:** хранить prompt version, model version, renderer version и augmentation config;
- **наблюдаемость:** логировать количество отбраковок, причины ошибок, стоимость LLM и распределение полей;
- **безопасность:** не использовать реальные персональные данные и не отправлять реальные документы во внешний API без отдельного разрешения.

## 16. Как выбрать роль LLM в этом пайплайне

### Если полей мало и текст шаблонный

LLM может быть не нужна. Faker, шаблоны фраз и локальные правила дешевле, быстрее и воспроизводимее. LLM можно добавить для расширения разнообразия причин.

### Если причина заявления свободная и разнообразная

LLM полезна, но ограничиваем её сценариями, длиной, языком и схемой. После генерации прогоняем текст через проверку и при необходимости просим переформулировать.

### Если появляется много шаблонов

LLM/VLM может помочь зарегистрировать новую форму: найти подписи, предложить карту полей и показать неоднозначные места. Но координаты подтверждает человек, а массовый рендеринг использует зафиксированную конфигурацию.

### Если нужен максимально реалистичный почерк

Шрифт — лишь приближение. Для серьёзного качества понадобятся реальные обезличенные образцы почерка, генеративная модель изображения или библиотека синтеза рукописи, а также строгая проверка лицензий и приватности. Не стоит обещать, что один GPT-промпт создаст правдоподобный почерк.

## 17. Как объяснить решение на ML System Design интервью

> «Я бы разделил генератор на данные, геометрию и визуальные искажения. Сначала зафиксировал бы схему полей и распределения. Числовые и календарные значения генерировал бы детерминированно в Python, а LLM использовал бы для разнообразных текстовых полей — например, причины заявления — через структурированный вывод и Pydantic-валидацию. Для фиксированного PDF один раз сохранил бы координаты полей в конфигурации; не стал бы каждый документ заново просить VLM искать их. Затем отрендерил бы страницу в PNG с разрешением около 300 DPI, добавил рукописный текст разрешённым шрифтом и имитировал поворот, перспективу, шум, тени, размытие и JPEG-сжатие. Основным входом для OCR/VLM сделал бы растровый скан, а PDF сохранил бы как дополнительный артефакт. Каждый пример получил бы JSON, seed и версии генератора. После рендера проверил бы, что текст помещается, а на выборке сравнил бы OCR/VLM-извлечение с эталонным JSON и сверил распределения синтетики с обезличенными реальными сканами. Только после этого масштабировал бы генерацию».

## 18. Частые вопросы

> [!question] Почему координаты не включены в JSON, если они всё равно нужны?
> Потому что это разные задачи. JSON описывает целевую семантику — какое значение относится к полю. Координаты описывают геометрию конкретного шаблона и хранятся в его конфигурации. Если позже понадобится обучать детектор полей, можно выпустить отдельный JSON с bounding boxes, не меняя основной контракт.

> [!question] Можно ли попросить GPT сразу вернуть PDF?
> GPT генерирует текст и структуру, но не должна отвечать за точную геометрию шаблона и повторяемый рендеринг. Надёжнее получить структурированные значения и вставить их в PDF/PNG специализированным кодом.

> [!question] Почему не генерировать все поля только через Faker?
> Faker отлично даёт имена, даты и числа, но плохо создаёт разнообразный связный свободный текст. Для причины заявления разумна гибридная схема: Faker/правила для контролируемых значений и LLM для ограниченного естественного языка.

> [!question] Зачем сохранять seed?
> Чтобы воспроизвести спорный документ, сравнить версии рендера и понять, какой набор случайных искажений привёл к ошибке. Без seed отладка синтетики превращается в поиск «примерно похожего» изображения.

> [!question] Как понять, что синтетика достаточно реалистична?
> Сравнивать не только визуально. Нужны распределения полей, доля пропусков, OCR/VLM-метрики на синтетике и небольшом реальном обезличенном наборе, а также ручная оценка примеров. Главный критерий — переносимость на реальные документы, а не высокая метрика на данных, созданных тем же генератором.

> [!question] Нужно ли делать PDF, если VLM принимает картинку?
> Нет, PDF не обязателен. Он удобен как исходный шаблон и дополнительный артефакт, но для обучения на сканах нужен PNG/JPEG. Если оставляем PDF, проверяем, что скрытый текстовый слой не даёт модели нечестную подсказку.

## 19. Чек-лист готовности генератора

- [ ] Есть версия шаблона и проверенная карта полей.
- [ ] Для всех полей определены тип, диапазон, длина и обязательность.
- [ ] Числовые и календарные значения генерируются воспроизводимо.
- [ ] LLM возвращает структурированный ответ по схеме.
- [ ] После LLM выполняется независимая Pydantic-валидация.
- [ ] Текст не обрезается при размещении в поле.
- [ ] Сохраняются seed, версии модели, промпта и рендера.
- [ ] Есть PNG/JPEG, JSON и при необходимости PDF.
- [ ] Скан содержит реалистичные, но контролируемые искажения.
- [ ] Включена проверка OCR/VLM на выборке.
- [ ] Распределения синтетических значений сравниваются с реальными.
- [ ] Реальные персональные данные не отправляются во внешний LLM API.
- [ ] Есть отчёт по отбракованным примерам и причинам отказа.
