# Качество данных — дубликаты, пропуски, late events, часовые пояса и join explosion

> [!abstract] Суть
> Проверка качества данных — часть анализа, а не отдельная работа платформенной команды. До интерпретации метрики нужно доказать, что строки полны, уникальны, своевременны и соответствуют одному и тому же бизнес-определению.

## Почему плохие данные опаснее явной ошибки

Если запрос падает, проблему видно. Если JOIN незаметно удвоил 7% заказов, дашборд выглядит убедительно и команда принимает неверное решение.

Полезно проверять шесть измерений:

| Измерение | Вопрос |
|---|---|
| Completeness | Все ли ожидаемые события и поля пришли? |
| Uniqueness | Нет ли повторов одного бизнес-факта? |
| Validity | Значения находятся в допустимых диапазонах и форматах? |
| Consistency | Не противоречат ли таблицы и статусы друг другу? |
| Timeliness | Данные свежие и окно созрело? |
| Referential integrity | Все foreign keys находят родителя? |

## Дубликаты

Причины:

- client retry без idempotency key;
- at-least-once delivery в очереди;
- повторная загрузка partition;
- JOIN one-to-many;
- событие отправляется и клиентом, и сервером;
- один бизнес-факт имеет несколько status events.

Проверка:

```sql
SELECT event_id, COUNT(*) AS cnt
FROM events
GROUP BY event_id
HAVING COUNT(*) > 1;
```

Если `event_id` нет, нужен бизнес-ключ, но комбинация `(user_id, event_name, second)` может случайно объединить честные повторные действия. Дедупликация — предметное решение.

Сохранить последнюю версию:

```sql
WITH ranked AS (
    SELECT *,
           ROW_NUMBER() OVER (
               PARTITION BY event_id
               ORDER BY ingested_at DESC
           ) AS rn
    FROM events
)
SELECT *
FROM ranked
WHERE rn = 1;
```

## Пропуски

NULL может означать:

- значение неизвестно;
- неприменимо;
- событие старой версии не имело поля;
- enrichment не сработал;
- пользователь запретил tracking;
- JOIN не нашёл соответствие.

Поэтому `COALESCE(country, 'unknown')` удобно, но смешивает разные механизмы. В расследовании полезно хранить отдельные категории `missing_due_to_old_schema`, `not_applicable`, `join_miss`.

### Missingness не всегда случайна

Если latency отсутствует именно у упавших запросов, средняя latency успешных запросов выглядит лучше при деградации. Missingness зависит от outcome — простое удаление строк создаёт bias.

## Late events и созревание

Данные за вчера часто неполны. Постройте ingestion delay:

```sql
SELECT
    EXTRACT(EPOCH FROM (ingested_at - event_time)) / 60 AS delay_minutes,
    COUNT(*)
FROM events
GROUP BY 1;
```

Практически смотрят p50/p95/p99 delay и долю событий, пришедших за 1 час, 24 часа, 7 дней.

Для ежедневного дашборда возможны:

- watermark: считать день финальным после допустимой задержки;
- backfill последних N partitions;
- показывать «предварительные данные»;
- корректировать ожидаемую полноту по delay curve;
- разделять operational real-time и financial finalized metrics.

Нельзя сравнивать недозревший сегодняшний revenue с полностью дозревшим прошлым вторником.

## Часовые пояса

Хранить timestamp лучше в UTC, но продуктовые сутки могут быть локальными.

Проблемы:

- пользователь пересёк timezone;
- DST создаёт сутки 23 или 25 часов;
- серверная дата не совпадает с локальным поведением;
- monthly boundary различается;
- строка timestamp без timezone интерпретируется по session setting БД.

На интервью уточните: метрика глобальная по UTC или «локальный день пользователя»? Для DAU глобального продукта оба определения возможны, но дают разные числа.

## Join explosion

До JOIN проверьте кардинальность:

```sql
SELECT
    COUNT(*) AS rows,
    COUNT(DISTINCT order_id) AS orders
FROM orders;
```

После JOIN повторите. Если число уникальных заказов прежнее, а строки выросли, это может быть ожидаемый one-to-many, но order-level суммы теперь нельзя агрегировать напрямую.

Полезные приёмы:

- агрегировать каждую таблицу до нужного grain до JOIN;
- использовать `EXISTS` вместо JOIN для фильтра по наличию;
- валидировать uniqueness ключа dimension;
- считать unmatched keys;
- использовать explicit join conditions, а не случайный `NATURAL JOIN`;
- проверять row count и суммы до/после.

## Slowly changing dimensions и leakage

Если пользователь сменил страну или тариф, обычный JOIN к текущему профилю перепишет историю. Нужен as-of join по интервалу действия.

Также нельзя строить ML-feature «число покупок за 30 дней» включая события после prediction time. Для каждой строки нужен cutoff $t_0$:

```sql
WHERE event_time < prediction_time
  AND event_time >= prediction_time - INTERVAL '30 days'
```

Граница `<` или `<=` должна быть сознательной. Feature, недоступная в момент решения, — leakage, даже если физически лежит в таблице.

## Изменение схемы и semantics drift

Столбец может называться так же, но смысл измениться:

- `purchase` раньше отправлялся после оплаты, теперь после создания заказа;
- `active_user` стал включать background opens;
- цена перешла из рублей в копейки;
- новый SDK отправляет несколько impressions;
- enum status получил новое значение.

Нужны schema version, data contracts, changelog и тесты распределений. Аномалия ровно с даты релиза часто является semantics drift.

## Минимальный набор data checks

Перед серьёзным анализом:

1. Row count по времени и источникам.
2. Уникальность ключей.
3. Null rate ключевых полей.
4. Допустимые ranges/categories.
5. Referential integrity.
6. Freshness и ingestion delay.
7. Сверка независимых источников: события vs платежи.
8. Баланс платформ/версий/регионов.
9. Row-count и metric checksum до/после JOIN.
10. Несколько raw user journeys вручную.

Последний пункт недооценён: пять реальных цепочек часто показывают ошибку, которую агрегаты скрывают.

## Пример: «упала конверсия iOS»

В новой iOS-версии event `checkout_started` отправляется дважды, а `payment_success` — один раз. Если конверсия считается `success events / checkout events`, она искусственно падает почти вдвое.

Если считать пользователей, эффект может исчезнуть, но это не значит, что проблема неважна: дубли загрязняют event-level модели и стоимость хранения. Нужно исправить instrumentation и backfill/semantic versioning.

## Как ответить на интервью

> [!question] Как проверите внезапное падение метрики?
> Сравню raw counts и coverage по источникам, freshness и delay, schema/app versions, null и duplicate rates. Проверю numerator/denominator отдельно, независимый источник истины и несколько user journeys. После JOIN сверю grain, row counts и контрольные суммы. Только когда исключу instrumentation issue, перейду к продуктовым причинам.

> [!question] Что делать с late events?
> Оценить распределение задержки, выбрать watermark и maturity policy. Для оперативного дашборда маркировать недозрелые значения или корректировать их, а финальные метрики пересчитывать backfill. Сравнивать периоды нужно при одинаковой степени зрелости.

> [!question] Почему `DISTINCT` — опасное исправление?
> Он может случайно скрыть размножение, удалить реальные одинаковые события и не исправить суммы. Нужно определить уникальный бизнес-факт, причину дубля и правильный grain, а затем дедуплицировать по ключу и версии.

## Типичные ошибки

- Считать NULL нулём без понимания механизма.
- Сравнивать preliminary и finalized periods.
- Хранить локальное время без timezone.
- Лечить JOIN explosion `SUM(DISTINCT amount)`.
- Не версионировать semantics событий.
- Использовать будущее значение dimension или feature.
- Проверять только агрегаты и никогда raw journeys.

- Какие шесть измерений качества данных вы назовёте?

- Почему average latency может улучшиться при росте ошибок?
