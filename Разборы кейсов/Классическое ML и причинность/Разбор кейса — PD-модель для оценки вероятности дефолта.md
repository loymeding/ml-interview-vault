# Разбор кейса — PD-модель для оценки вероятности дефолта

> [!abstract] Условие
> Банк хочет оценивать вероятность дефолта клиента в течение 12 месяцев и использовать её для одобрения кредита и выбора лимита. У вас есть заявки, история платежей и решения прошлого скоринга.

## 1. Уточняем риск и горизонт

Определяю default event, observation point и правила censored cases (когда клиент ещё не прожил полный горизонт). Спрашиваю, надо ли предсказывать риск при заявке или обновлять его каждый месяц, и что происходит с отказанными заявками.

## 2. Данные и leakage

Формирую признаки на дату заявки: доход, долговая нагрузка, просрочки до заявки, число активных кредитов и стабильность дохода. Удаляю признаки, появившиеся после выдачи. Разделяю данные по времени и проверяю новые экономические периоды.

Главный риск смещения — target наблюдается только у одобренных клиентов. Для отказанных нет факта будущего платежа; это обсуждается как reject inference, а не замалчивается.

## 3. Модель и калибровка

Начинаю с логистической регрессии/scorecard, затем сравниваю с бустингом. Важно сохранить monotonicity и объяснимость там, где требования это предполагают. После ranking-модели калибрую вероятности на отдельной validation-когорте.

## 4. Метрики и policy

Смотрю AUC/KS для разделения и Brier/calibration для вероятности. Далее связываю PD с LGD/EAD и ожидаемым убытком. Порог одобрения выбираю по марже, допустимому риску и мощности ручной проверки. Отдельно контролирую fairness и стабильность по сегментам.

## 5. Запуск

Shadow на заявках, сравнение с текущим скорингом, ограниченный rollout. Guardrails: bad rate, доля одобрений, expected loss, latency, missing features и drift score. Для неизвестных значений используем безопасный fallback и не подменяем пропуск нулём без анализа смысла.

## Эталонный ответ

> «Я зафиксирую дефолт и 12-месячный горизонт, построю признаки только на дату заявки и временно разделю когорты. Начну с объяснимого baseline, затем проверю бустинг, но отдельно оценю калибровку. Модель — часть policy: PD вместе с LGD/EAD определяет ожидаемый убыток. Из-за selection bias у одобренных заявок явно обозначу reject inference. Перед rollout проведу shadow, затем A/B/ограниченный запуск с мониторингом bad rate, calibration, drift и expected loss».
