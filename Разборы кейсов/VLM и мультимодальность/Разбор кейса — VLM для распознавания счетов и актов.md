# Разбор кейса — VLM для распознавания счетов и актов

> [!abstract] Условие
> Компания хочет автоматически извлекать из фотографий счетов и актов номер документа, дату, ИНН, итоговую сумму, НДС и строки товаров. Ошибка в сумме может привести к неправильной оплате. Нужно предложить ML-систему и план её проверки.

## 1. Как не попасть в ловушку «давайте VLM»

Сначала уточняю поля, шаблоны, качество фото, языки, долю рукописных документов, объём и SLA. Критичные суммы и идентификаторы требуют evidence (области изображения) и проверки. Поэтому выбираю каскад, а не одну генеративную модель.

## 2. Архитектура

```text
image quality check
→ OCR с координатами
→ layout/field extractor
→ нормализация дат, валют и чисел
→ арифметический checker
→ confidence threshold
→ VLM для нестандартных случаев
→ человек для критичных low-confidence документов
```

OCR+правила — baseline. Layout-модель учитывает расположение слов. VLM полезна для новых форм, таблиц и объяснения, но её JSON не принимаем без схемы и валидаторов.

## 3. Какие данные нужны

Для каждого документа размечаю:

- поля и их нормализованные значения;
- bounding boxes (координаты областей);
- страницу и тип шаблона;
- отсутствующее поле как отдельный класс;
- качество изображения и причину отказа.

Деление по случайным картинкам опасно: один и тот же шаблон может попасть в train и test. Для проверки обобщения выделяю поставщиков, периоды и новые шаблоны целиком.

## 4. Метрики и решение о ручной проверке

Главная метрика — document-level critical-field accuracy: доля документов, где все обязательные поля верны. Дополнительно считаю F1 по каждому полю, CER для OCR, JSON validity, координатное совпадение и долю документов, обработанных без человека.

Порог выбираю не по максимальному coverage, а по стоимости ошибки. Сумму с confidence 0,82 и нарушенной арифметикой отправляю человеку, даже если средний threshold 0,7.

## 5. Добивающие вопросы

**«VLM стала лучше по F1, выпускаем?»** — нет, сначала проверю critical fields, шаблоны и арифметику. Улучшение на необязательном поле не компенсирует ошибку суммы.

**«Что делать при смене формы счёта?»** — мониторить долю low-confidence и новые layout-кластеры, собрать targeted разметку, сначала включить fallback OCR/ручной review.

**«Как поймать галлюцинацию?»** — проверять, что значение найдено в OCR/evidence, согласуется с типом и контрольными правилами, а при отсутствии поля модель возвращает null, а не выдумывает.

## Эталонный ответ

> «Поставлю OCR+правила как baseline, затем добавлю layout-aware extractor и VLM только для нестандартных документов. В датасете сохраню значения, координаты, шаблон и качество изображения; test разделю по поставщикам и времени. Основной gate — правильность критичных полей на уровне документа, плюс arithmetic checks, confidence и доля ручного review. Запуск начну с теневого режима и ручной проверки, с откатом на baseline при росте ошибок суммы или новых шаблонов».
