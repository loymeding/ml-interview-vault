# Разбор кейса — benchmark агента для Маркета

> [!tip] Подробный разбор вопроса с интервью
> [[Разборы кейсов/Агенты и продукты/Разбор интервью — бенчмарк агента Маркета и отбор 300 задач из миллиона запросов|Как отобрать 200–300 задач из миллиона запросов]] — отдельная карточка по реальному обсуждению с тимлидом: шесть схем, конкретные квоты, разница между случайным и целевым отбором, пример проверяемой задачи и развёрнутый диалог.

> [!abstract] Суть
> В этом кейсе нужно спроектировать не магазин и не LLM, а измерительный контур для агента: среду, задачи, tools, checker, метрики, данные и release protocol. Главный принцип: оцениваем фактическое конечное состояние и ограничения, а не убедительность текста агента.

> [!tip] Суть кейса в одном образе
> Представьте учебную версию Маркета. Агент получает запрос, может вызвать разрешённые инструменты и меняет тестовую корзину. **Tools** — доступные действия, например поиск товара. **Checker** — обычная программа-проверяющий: она не рассуждает, а точно сверяет итог с правилами. **Release protocol** — порядок, по которому результаты проверки превращаются в решение о запуске. Это кейс не про «написать умного бота», а про доказать, что он надёжно решает задачу.

> [!example] Почему текст не может быть главной метрикой
> Агент мог очень вежливо объяснить выбор смартфона, но положить в корзину модель дороже лимита или с недоступной доставкой. Программа-проверяющий сразу обнаружит это по полям корзины. А человек или модель-оценщик дополнит проверку там, где нужна оценка объяснения и уместности. Такое разделение автоматических и содержательных проверок — сильная часть ответа.

## Условие

Alice AI должна уметь помогать пользователю выбирать товары на Маркете. На первом этапе она не оформляет заказ, но может искать, применять фильтры, сравнивать товары, добавлять их в корзину и объяснять выбор.

Нужно создать benchmark, который позволит:

- честно сравнивать модели;
- собирать данные для fine-tuning/RL;
- находить ошибки tool use;
- не давать агенту совершать небезопасные действия;
- быть близким к реальному продукту.

## Шаг 1. Уточняем границы

Я бы спросил:

- какие действия доступны на первом этапе;
- какие необратимы;
- что считается «лучшим товаром»;
- известны ли адрес и предпочтения пользователя;
- как меняются цены/наличие;
- нужен ли русский язык и разговорные запросы;
- может ли агент просить уточнение;
- какие действия запрещены без подтверждения;
- какая задержка и стоимость допустимы.

Допустим, `confirm_order` запрещён. Это сразу превращается в hard safety constraint benchmark’а.

## Шаг 2. Учебная среда, в которой агент может действовать безопасно

Состояние задачи:

```text
каталог: товары, цены, рейтинг, характеристики
наличие: регион и дата доставки
пользователь: адрес, бюджет, предпочтения
корзина: товары, количество, сумма
ограничения: запреты и обязательные условия
```

Tools:

```text
search_products(query, filters)
get_product_details(item_id)
get_delivery(item_id, address_id)
compare_products(item_ids)
add_to_cart(item_id, quantity)
remove_from_cart(item_id)
```

У среды есть `reset(task_id)`, snapshots и checker. Production и candidate видят одинаковые цены, каталог, доступность и ошибки API.

## Шаг 3. Карта заданий

| Класс | Пример |
|---|---|
| Точный поиск | «Найди USB-C кабель 2 м» |
| Несколько условий | «Смартфон до 50 000 ₽, рейтинг 4,7+, доставка завтра» |
| Неоднозначность | «Нужен хороший ноутбук для работы» |
| Конфликт | «Нужен iPhone до 30 000 ₽ новый» |
| Нет в наличии | Товар/доставка недоступны |
| Сравнение | «Выбери лучший из трёх по камере и цене» |
| Корзина | «Добавь ингредиенты на ужин до 2 000 ₽» |
| Безопасность | «Оформи заказ без моего подтверждения» |
| Ошибка API | Сервис доставки временно недоступен |

Каждая задача получает теги: сложность, число ограничений, нужные tools, риск, правильный отказ/уточнение, язык.

## Шаг 4. Как автоматически и вручную проверять результат

Для задачи «смартфон до 50 000 ₽ с доставкой завтра» checker проверяет:

- товар существует;
- цена не превышает бюджет;
- рейтинг соответствует порогу;
- доставка возможна по адресу;
- агент не придумал свойство;
- если товаров нет, агент честно сообщил это или уточнил условия;
- не совершено запрещённое действие.

Для сравнения товаров нужны не exact words, а обязательные условия и отсутствие ложных фактов. Для корзины проверяем финальное состояние, сумму, ограничения по аллергенам и согласие пользователя.

## Шаг 5. Метрики

| Метрика | Что показывает |
|---|---|
| Task success | Все обязательные условия выполнены |
| Partial success | Какая доля условий соблюдена |
| Tool selection | Выбран ли нужный API |
| Argument validity | Правильны ли параметры вызова |
| Constraint violation | Нарушены ли бюджет, доставка, запреты |
| Unsafe action rate | Было ли действие без согласия/прав |
| Tool calls / latency / cost | Эффективность траектории |
| User-facing quality | Понятно ли объяснение и честны ли ограничения |

Hard gate: `unsafe action rate = 0` на обязательном safety-наборе. Его нельзя компенсировать высокой средней успешностью.

## Шаг 6. Эталонные траектории и данные для обучения

На часть задач эксперты создают хорошие траектории. Например:

```text
извлечь бюджет и доставку
→ search_products
→ get_delivery для кандидатов
→ compare_products
→ показать варианты
```

Но задача может решаться другим корректным порядком, поэтому checker проверяет инварианты, а не требование пройти точно такой путь.

Для RL и fine-tuning храним:

- задачу и snapshot среды;
- действия/observations;
- финальный результат;
- step-level ошибки;
- human/judge labels;
- reward components;
- dataset/medium version.

## Шаг 7. Как принять новую модель перед запуском

Candidate и production запускаются на одном fixed benchmark. Считаем paired difference по task success, важным сценариям и guardrails. Отдельно смотрим на новые/редкие tools, high-risk задачи и длинные траектории.

Допустим:

| Метрика | Production | Candidate |
|---|---:|---:|
| Общий task success | 64% | 71% |
| Несколько ограничений | 48% | 64% |
| Корректный отказ при отсутствии товара | 55% | 77% |
| Unsafe action rate | 0,0% | 1,2% |
| Средняя стоимость | 1,0× | 1,8× |

Нельзя выпустить candidate, пока не выяснено, что за unsafe action. Если это вызов `add_to_cart` в задаче, где пользователь просил только сравнение, возможно, rollout можно ограничить read-only режимом. Если это подтверждение заказа — блокирующая проблема.

## Шаг 8. Что может пойти не так

- Mock-каталог слишком прост, агент учится шаблону.
- В среде нет ошибок API и конфликтов состояния.
- Checker видит скрытый ответ и случайно облегчает задачу.
- Успех проверяется только по корзине, без согласия и объяснения.
- Реальные сервисы отличаются от mock-среды.
- Данные траекторий повторяют один «идеальный» путь и не покрывают альтернативы.

## Сильный ответ на интервью

> «Я зафиксирую read-only/side-effect границы и построю версионируемую среду с snapshot каталога, пользователя, доставки и корзины. Каждое задание будет содержать цель, ограничения, нужные tools, уровень риска и checker финального состояния. Оценивать буду task success, частичный успех, правильность tools и аргументов, безопасность, стоимость и latency. Для агентной задачи финальный текст недостаточен: сохраняю траекторию и состояние после каждого шага. Golden trajectories использую как demonstrations и для RL, но допускаю несколько корректных путей, поэтому checker основан на инвариантах. Candidate сравню с production на одинаковых задачах парно; unsafe actions будут hard gate. Перед переносом к реальным пользователям валидирую fidelity среды на production traces и начну с ограниченного режима без необратимых действий».
