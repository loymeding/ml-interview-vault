# Python — Декораторы и Функциональное программирование

> [!abstract] Суть
> Декораторы — это инструмент для изменения поведения функций или классов без прямого вмешательства в их исходный код. Лямбда-функции — это способ создания кратких анонимных функций для решения локальных задач «на лету».

## Простыми словами

*   **Декоратор** — это «обертка». Представьте, что у вас есть функция, которая просто делает кофе. Вы можете надеть на неё «декоратор-сахар» и «декоратор-сливки». Сама кофемашина не изменится, но на выходе вы получите напиток с новыми свойствами. В коде это позволяет, например, добавить логирование или проверку прав доступа к любой функции одной строчкой `@`.
*   **Лямбда** — это «функция-однодневка». Вместо того чтобы заводить целую кухонную машину для нарезки одного огурца, вы просто берете нож, делаете дело и кладете его на место.

> [!tip] Быстрое повторение
> Декоратор — это функция, которая получает функцию и возвращает новую функцию с дополнительным поведением. Знак @ — только удобный синтаксис присваивания результата декоратора исходной функции.
>
> Хороший production-декоратор сохраняет метаданные через functools.wraps, не меняет контракт функции неожиданно и явно описывает, какие исключения перехватывает.
>
> Lambda подходит для короткого выражения. Если код требует условий, логирования или нескольких шагов, обычная функция обычно понятнее.

## Ответ

**Формальное определение и концепции**

1.  **Декораторы**
    Это функции высшего порядка, которые принимают другую функцию как аргумент, добавляют ей функционал и возвращают новую функцию.
    *   *Примеры из стандартной библиотеки*: `@property` (для геттеров), `@functools.lru_cache` (кеширование), `@contextlib.contextmanager` (создание контекстных менеджеров).

2.  **@classmethod vs @staticmethod**
    *   **@classmethod**: Принимает ссылку на сам класс (`cls`) первым аргументом. Используется для методов, которые работают с логикой всего класса (например, фабричные методы для создания объектов).
    *   **@staticmethod**: Не принимает ни `self`, ни `cls`. Это просто функция, которая логически связана с классом, но не нуждается в доступе к его состоянию.

3.  **Лямбда-функции**
    *   **Синтаксис**: `lambda аргументы: выражение`.
    *   **Зачем нужны**: Для передачи короткого кода в функции типа `map()`, `filter()` или `sort(key=...)`.
    *   **Чего не может быть внутри**: В лямбдах запрещены многострочные блоки, циклы (кроме списковых включений), операторы `return`, `yield`, `pass`, `assert`.

**Разбор кейсов (из файла вопросов)**

**Изменение приватных методов через декоратор**
Хотя в Python методы с двойным подчеркиванием (`__method`) подвергаются искажению имен (name mangling), декоратор всё равно может к ним обращаться. Декоратор, навешенный на класс или другой метод, может вызвать `_ClassName__private_method()`. Однако чаще декораторы используют для управления доступом к таким методам или их автоматического логирования.

## Примеры

```python
# Пример простого декоратора
def debug(func):
    def wrapper(*args, **kwargs):
        print(f"Вызываем {func.__name__}")
        return func(*args, **kwargs)
    return wrapper

@debug
def say_hello():
    print("Привет!")

# Лямбда для сортировки списка кортежей по второму элементу
data = [(1, 'b'), (2, 'a')]
data.sort(key=lambda x: x[1]) # Сортировка по буквам
```

## Как декоратор работает по шагам

Рассмотрим:

~~~python
@debug
def load_data(path):
    return read(path)
~~~

Python воспринимает это примерно так:

~~~python
def load_data(path):
    return read(path)


load_data = debug(load_data)
~~~

После этого имя load_data указывает уже на wrapper. Внутри wrapper обычно вызывается исходная функция.

~~~python
import functools


def debug(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        print("before")
        result = func(*args, **kwargs)
        print("after")
        return result

    return wrapper
~~~

Функция с *args и **kwargs может принимать произвольную сигнатуру, но в сложном API иногда лучше сохранить явные аргументы для читаемости и статического анализа.

## Декоратор с параметрами

Если декоратору нужны настройки, появляется дополнительный уровень вложенности:

~~~python
import functools


def repeat(times):
    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            result = None
            for _ in range(times):
                result = func(*args, **kwargs)
            return result

        return wrapper

    return decorator
~~~

Здесь repeat(3) сначала возвращает decorator, затем decorator получает функцию, а wrapper выполняется при вызове функции.

## Декоратор для async-функции

Обычный wrapper нельзя бездумно применять к coroutine:

~~~python
import functools


def log_async(func):
    @functools.wraps(func)
    async def wrapper(*args, **kwargs):
        print("before")
        result = await func(*args, **kwargs)
        print("after")
        return result

    return wrapper
~~~

Ключевое отличие — wrapper тоже async и ждёт исходную функцию через await. Если забыть await, можно вернуть объект-корутину вместо результата.

## Когда декоратор полезен, а когда нет

Хорошие случаи:

- единое логирование;
- измерение времени;
- авторизация;
- retry только для явно разрешённых ошибок;
- кэширование чистой функции;
- регистрация обработчиков.

Плохие случаи:

- скрытая бизнес-логика;
- несколько неочевидных сетевых запросов;
- изменение результата без документирования;
- глушение исключений;
- декоратор, который невозможно отключить в тестах.

Иногда обычная функция или объект-сервис лучше декоратора: зависимости и порядок действий становятся видимыми.

## Кэширование: важная оговорка

functools.lru_cache подходит для функций, результат которых определяется аргументами и у которых нет неожидаемых побочных эффектов.

Не стоит кэшировать:

- функции, зависящие от текущего времени;
- запросы, данные которых быстро меняются;
- функции с изменяемыми аргументами;
- операции, которые должны каждый раз обращаться к сервису.

Нужно заранее решить, когда кэш устаревает и как очищать его.

## Функциональные приёмы

map преобразует каждый элемент, filter оставляет элементы по условию, reduce сворачивает последовательность в одно значение. В production-коде списковые включения часто читаются лучше, чем цепочка map и filter:

~~~python
positive = [x * 2 for x in values if x > 0]
~~~

Lambda удобна для ключа сортировки:

~~~python
users.sort(key=lambda user: user["age"])
~~~

Если выражение стало длинным, вынесите его в именованную функцию. Имя объясняет намерение и облегчает тестирование.

## Типичные ошибки

*   **Потеря метаданных**: Если не использовать `@functools.wraps(func)` внутри декоратора, оригинальная функция «забудет» своё имя (`__name__`) и документацию.
*   **Злоупотребление лямбдами**: Если лямбда становится сложной для чтения, её всегда лучше заменить на обычную функцию через `def`.

## Каверзные вопросы

> [!question] Можно ли декорировать класс?
> Да. Декоратор класса принимает класс и возвращает либо его измененную версию, либо совершенно другой объект. Это часто используется для регистрации классов в системе или добавления им методов.

> [!question] Что возвращает лямбда-функция, если в ней нет оператора return?
> Лямбда всегда автоматически возвращает результат вычисления своего единственного выражения. Писать `return` внутри лямбды запрещено синтаксисом.

## Вопросы для собеседования

> [!question] Что вернёт декоратор?
> Обычно новую функцию-wrapper. Имя исходной функции после декорирования указывает на wrapper, поэтому нужны functools.wraps и понятная документация.

> [!question] В каком порядке выполняются два декоратора?
> Декораторы применяются снизу вверх, а вызываются wrapper-ы снаружи внутрь. Важно проговорить это на конкретном примере, потому что порядок логирования, авторизации и retry может менять поведение.

> [!question] Почему замыкание важно для декораторов?
> Вложенный wrapper запоминает func и настройки внешней функции после завершения внешнего вызова. Это позволяет сделать фабрику декораторов с параметрами.

> [!question] Почему кэширование не является универсальным?
> Кэш безопасен только при стабильном результате для одних и тех же аргументов и понятной политике устаревания. Иначе можно вернуть пользователю старые или неверные данные.
