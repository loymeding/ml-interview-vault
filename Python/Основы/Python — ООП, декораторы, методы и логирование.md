# Python — ООП, декораторы, методы и логирование

> [!abstract] Суть
> В Python методы — это функции, которые при обращении через объект получают первый аргумент автоматически. `self` указывает на экземпляр, `cls` — на класс, `super()` следует MRO, декораторы оборачивают функции, а logging заменяет `print` в production-коде.

> [!tip] Быстрое повторение перед собеседованием
> - **self** — конкретный экземпляр, **cls** — класс.
> - **staticmethod** не получает объект или класс автоматически; **classmethod** получает класс.
> - **super()** идёт к следующему классу в MRO, а не обязательно к непосредственному родителю.
> - Декоратор принимает объект и возвращает обёрнутый объект; **functools.wraps** сохраняет метаданные.
> - В Python инкапсуляция основана на соглашениях: _name защищён от случайного использования, двойное подчёркивание включает name mangling, **property** позволяет контролировать доступ.

## Ответ

### 1. ООП, `self` и `super()`

`self` — это ссылка на конкретный экземпляр класса. Python передаёт её в instance method автоматически:

```python
class User:
    def __init__(self, name):
        self.name = name

    def greet(self):
        return f"Hi, {self.name}"
```

Вызов `user.greet()` фактически превращается в `User.greet(user)`.

`super()` возвращает proxy-объект, который ищет следующий метод по MRO (method resolution order). Это особенно важно при множественном наследовании: `super()` не просто "родитель", а следующий класс в линейном порядке разрешения методов.

### 2. Instance, static и class methods

| Тип метода | Первый аргумент | Когда использовать |
|---|---|---|
| instance method | `self` | нужен доступ к состоянию объекта |
| `@classmethod` | `cls` | альтернативные конструкторы, работа с классом |
| `@staticmethod` | ничего автоматически | функция логически связана с классом, но не требует `self/cls` |

Пример:

```python
class User:
    def __init__(self, name):
        self.name = name

    @classmethod
    def from_email(cls, email):
        return cls(name=email.split("@")[0])

    @staticmethod
    def is_valid_email(email):
        return "@" in email
```

`classmethod` хорошо работает с наследованием: если вызвать метод у подкласса, `cls` будет подклассом.

### 2.1. Инкапсуляция и property

В Python нет строгих private-полей как в Java или C++. Обычно разработчик показывает намерение именем:

- name — публичный интерфейс;
- _name — внутреннее поле, которое не стоит использовать напрямую;
- __name — имя будет преобразовано в _ClassName__name, чтобы снизить риск конфликта в наследовании.

Для проверки и изменения значения удобно использовать property:

~~~python
class Account:
    def __init__(self, balance):
        self.balance = balance

    @property
    def balance(self):
        return self._balance

    @balance.setter
    def balance(self, value):
        if value < 0:
            raise ValueError("balance cannot be negative")
        self._balance = value
~~~

Пользователь класса работает с account.balance как с атрибутом, но код класса контролирует допустимые значения. Это полезнее, чем открыто менять внутреннее поле из любого места программы.

### 2.2. Наследование или композиция

Наследование подходит для отношения «является разновидностью»: Cat является Animal. Композиция подходит для отношения «содержит» или «использует»: сервис содержит клиент API.

~~~python
class ReportService:
    def __init__(self, storage):
        self.storage = storage

    def save(self, report):
        self.storage.write(report)
~~~

Композиция обычно проще для тестирования: в тест можно передать поддельное хранилище. Не стоит создавать глубокую иерархию классов только ради повторного использования нескольких строк.

### 2.3. Магические методы как контракт

Магические методы подключают объект к стандартным операциям Python:

| Метод | Что позволяет |
|---|---|
| __init__ | инициализация экземпляра |
| __repr__ | отладочное представление |
| __str__ | человекочитаемый вывод |
| __eq__ | сравнение по значению |
| __hash__ | использование в dict и set |
| __iter__ | обход в for |
| __len__ | вызов len |
| __call__ | вызов экземпляра как функции |

Реализуя магический метод, нужно соблюдать ожидаемый контракт. Например, если объект изменяемый, не следует делать его хешируемым без веской причины.

### 3. Декораторы

Декоратор — функция, которая принимает функцию и возвращает новую функцию-обёртку.

```python
import functools

def log_calls(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        print(f"calling {func.__name__}")
        return func(*args, **kwargs)
    return wrapper
```

`functools.wraps` сохраняет имя, docstring и metadata исходной функции. Без него отладка и introspection становятся неприятными.

Типовые декораторы:
- кэширование: `functools.lru_cache`;
- retry: повторить операцию при временной ошибке;
- логирование: записать вход/выход/исключение;
- auth/permissions;
- timing/profiling.

### 4. Retry-декоратор

```python
import functools
import time

def retry(times=3, delay=0.2, exceptions=(Exception,)):
    def deco(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            last_error = None
            for _ in range(times):
                try:
                    return func(*args, **kwargs)
                except exceptions as exc:
                    last_error = exc
                    time.sleep(delay)
            raise last_error
        return wrapper
    return deco
```

Важно не ловить слишком широкий класс исключений без необходимости и не скрывать исходную ошибку.

### 5. Логирование

`logging` лучше `print`, потому что у него есть:
- уровни важности;
- handlers для консоли, файла, stderr, внешних систем;
- форматирование;
- иерархия логгеров;
- возможность включать/выключать детализацию без изменения кода.

Уровни:

| Уровень | Когда использовать |
|---|---|
| `DEBUG` | подробности для отладки |
| `INFO` | нормальные бизнес-события |
| `WARNING` | странно, но работа продолжается |
| `ERROR` | операция упала |
| `CRITICAL` | система в критическом состоянии |

Пример:

```python
import logging

logger = logging.getLogger(__name__)

def load_data(path):
    logger.info("loading data from %s", path)
    try:
        ...
    except OSError:
        logger.exception("failed to load data")
        raise
```

`logger.exception()` вызывают внутри `except`: он добавляет traceback.

### 6. __name__ == "__main__"

При запуске файла напрямую Python выставляет специальную переменную модуля:

```python
__name__ = "__main__"
```

Поэтому блок выполнится:

```python
if __name__ == "__main__":
    main()
```

Если этот же файл импортировать как модуль, `__name__` будет именем модуля, и блок не выполнится. Это нужно, чтобы файл можно было и запускать как скрипт, и безопасно импортировать без побочных эффектов.

### 7. Когда MRO нельзя построить

Python использует C3 linearization. Обычно MRO строится автоматически, но при конфликтующих требованиях порядка наследования Python не сможет сформировать линейный порядок и выбросит `TypeError`.

```python
class A: ...
class B(A): ...
class C(A): ...

class X(B, C): ...
class Y(C, B): ...

class Z(X, Y): ...  # TypeError: Cannot create a consistent method resolution order
```

Причина: `X` требует порядок `B` перед `C`, а `Y` требует `C` перед `B`. Одновременно выполнить оба требования невозможно.

## Формула / Схема

**MRO можно посмотреть так:**

```python
ClassName.__mro__
```

**Декораторная эквивалентность:**

```python
@decorator
def f():
    ...

# то же самое
def f():
    ...
f = decorator(f)
```

## Короткий пример

Если метод не использует ни объект, ни класс, лучше вынести его в функцию модуля или сделать `staticmethod`, если он действительно часть публичного API класса.

Если нужен альтернативный конструктор вроде `User.from_json(...)`, чаще подходит `classmethod`, потому что он вернёт экземпляр правильного подкласса.

## Как рассуждать при code review

Если дали незнакомый класс или декоратор, сначала проверьте:

1. Кто владеет состоянием и кто его меняет?
2. Что произойдёт при наследовании?
3. Не скрывает ли декоратор исключения или изменение сигнатуры?
4. Можно ли заменить зависимость на тестовую?
5. Что попадёт в логи и не содержатся ли там персональные данные?
6. Что случится при повторном вызове, таймауте или частично выполненной операции?

Для production-кода полезно отделять бизнес-логику от логирования, авторизации и повторных попыток. Декоратор подходит для сквозного поведения, но не должен превращать функцию в непрозрачную цепочку скрытых действий.

## Типичные ошибки

- **Думать, что `self` — ключевое слово:** это обычное имя параметра, но соглашение обязательно для читаемости.
- **Использовать `staticmethod` вместо функции модуля без причины:** класс не должен быть свалкой функций.
- **Писать декоратор без `functools.wraps`:** ломаются имя, docstring, help, часть tooling.
- **Логировать через f-string в горячем DEBUG-коде:** лучше `logger.debug("value=%s", value)`, чтобы форматирование было ленивым.
- **Глушить исключения в retry:** retry должен либо вернуть результат, либо пробросить понятную ошибку.
- **Писать исполняемый код на уровне модуля:** при импорте он выполнится. Для скриптов лучше оборачивать запуск в `if __name__ == "__main__"`.

## Каверзные вопросы

> [!question] Что именно делает `super()` при множественном наследовании?
> Он идёт не к "родителю вообще", а к следующему классу в MRO. Поэтому классы в иерархии должны кооперативно вызывать `super()`.

> [!question] Когда `classmethod` лучше `staticmethod`?
> Когда метод должен знать, от какого класса его вызвали: альтернативные конструкторы, фабрики, настройка поведения в наследниках.
