# Python — SOLID-принципы на практике

> [!abstract] Коротко
> SOLID — это пять ориентиров для проектирования классов и модулей так, чтобы код было проще менять, тестировать и расширять. Это не набор обязательных шаблонов и не требование превращать каждый скрипт в сложную архитектуру. Главный вопрос: «Что изменится в коде, если изменится требование, и сколько несвязанных мест придётся переписать?»

## Быстрое повторение

| Буква | Принцип | Простая идея |
|---|---|---|
| S | Single Responsibility | У класса одна основная причина для изменения. |
| O | Open/Closed | Новое поведение добавляем расширением, а не переписыванием стабильного кода. |
| L | Liskov Substitution | Подтип можно безопасно подставить вместо базового типа. |
| I | Interface Segregation | Клиент не зависит от методов, которыми он не пользуется. |
| D | Dependency Inversion | Бизнес-логика зависит от абстракции, а детали подключаются снаружи. |

> [!tip] Как отвечать на интервью
> Не ограничивайтесь расшифровкой букв. Для каждого принципа скажите: какую проблему он предотвращает, покажите небольшой пример, назовите компромисс и объясните, когда принцип не стоит применять.

## 1. Зачем вообще нужны SOLID

Представьте небольшой сервис, который получает заказ, проверяет остатки, считает скидку, пишет в базу и отправляет письмо. В начале удобно положить всё в один класс. Через несколько месяцев появляются новые способы оплаты, несколько баз данных, асинхронные уведомления и тесты. Любое изменение начинает задевать всё сразу.

SOLID помогает разделить причины изменений:

- бизнес-правило скидки меняется независимо от способа хранения;
- отправка письма меняется независимо от расчёта цены;
- тест может подставить заглушку базы вместо настоящего соединения;
- новый способ оплаты добавляется отдельной реализацией.

Это уменьшает связанность (сколько частей знают друг о друге) и повышает связность внутри модуля (насколько его код относится к одной задаче).

## 2. S — Single Responsibility Principle

### Что означает

Принцип единственной ответственности часто ошибочно пересказывают как «в классе должен быть один метод». Правильнее: у класса или модуля должна быть одна основная причина для изменения. Причина обычно связана с одним типом бизнес-правил или одним заинтересованным владельцем.

Если класс одновременно меняется из-за правил скидок, схемы базы и текста письма, у него несколько ответственностей.

### Плохой пример

~~~python
class OrderService:
    def create_order(self, user_id: int, items: list[dict]) -> int:
        total = 0
        for item in items:
            total += item["price"] * item["quantity"]

        if total > 10_000:
            total *= 0.9

        order_id = save_to_postgres(user_id, items, total)
        send_email(user_id, f"Заказ {order_id} создан")
        return order_id
~~~

Здесь смешаны расчёт цены, сохранение и уведомление. Если изменится скидка, база или почтовый провайдер, мы трогаем один и тот же класс.

### Более устойчивый вариант

~~~python
from dataclasses import dataclass
from typing import Protocol


@dataclass(frozen=True)
class Order:
    user_id: int
    items: list[dict]
    total: float


class PriceCalculator(Protocol):
    def calculate(self, items: list[dict]) -> float: ...


class OrderRepository(Protocol):
    def save(self, order: Order) -> int: ...


class Notifier(Protocol):
    def send(self, user_id: int, text: str) -> None: ...


class OrderService:
    def __init__(
        self,
        calculator: PriceCalculator,
        repository: OrderRepository,
        notifier: Notifier,
    ) -> None:
        self.calculator = calculator
        self.repository = repository
        self.notifier = notifier

    def create_order(self, user_id: int, items: list[dict]) -> int:
        total = self.calculator.calculate(items)
        order_id = self.repository.save(Order(user_id, items, total))
        self.notifier.send(user_id, f"Заказ {order_id} создан")
        return order_id
~~~

OrderService теперь координирует сценарий, а детали вынесены в отдельные компоненты.

### Как понять, что нарушен S

Задайте вопросы:

- Нужно ли классу обращаться к нескольким внешним системам?
- Меняется ли он по просьбам разных команд или владельцев?
- Сложно ли назвать его одной фразой без союза «и»?
- В тесте приходится поднимать базу, почту и файловую систему, хотя проверяется одна формула?
- При изменении одной части приходится перечитывать весь класс?

### Нюанс и компромисс

Слишком мелкое дробление тоже вредно. Класс из одного метода и отдельного файла на каждую строку не делает систему лучше. Сначала отделяйте самостоятельные причины изменения и границы внешних зависимостей, а не механически делите всё на микроклассы.

### Пример для ML

В ML-сервисе не стоит смешивать в одном классе чтение фичей, предсказание модели, бизнес-порог, логирование и отправку ответа. Удобнее иметь FeatureProvider, Predictor, DecisionPolicy и PredictionLogger, а orchestration оставить в одном use-case сервисе.

## 3. O — Open/Closed Principle

### Что означает

Модуль должен быть открыт для добавления нового поведения, но закрыт для постоянного переписывания проверенного кода. Это не означает «никогда не изменять код». Речь о местах, где новые варианты появляются регулярно и заранее понятен способ расширения.

### Плохой пример с if/elif

~~~python
def calculate_delivery_price(kind: str, distance_km: float) -> float:
    if kind == "courier":
        return 300 + distance_km * 20
    if kind == "pickup":
        return 0
    if kind == "express":
        return 500 + distance_km * 35
    raise ValueError("Unknown delivery kind")
~~~

Каждый новый способ доставки требует менять и повторно тестировать одну функцию.

### Расширение через стратегии и реестр

~~~python
from typing import Protocol


class DeliveryPricing(Protocol):
    def price(self, distance_km: float) -> float: ...


class CourierPricing:
    def price(self, distance_km: float) -> float:
        return 300 + distance_km * 20


class PickupPricing:
    def price(self, distance_km: float) -> float:
        return 0


class ExpressPricing:
    def price(self, distance_km: float) -> float:
        return 500 + distance_km * 35


PRICING: dict[str, DeliveryPricing] = {
    "courier": CourierPricing(),
    "pickup": PickupPricing(),
    "express": ExpressPricing(),
}


def calculate_delivery_price(kind: str, distance_km: float) -> float:
    try:
        strategy = PRICING[kind]
    except KeyError as exc:
        raise ValueError(f"Unknown delivery kind: {kind}") from exc
    return strategy.price(distance_km)
~~~

Новый вариант можно зарегистрировать отдельным классом. Основной расчёт не меняется.

### Где O полезен

- способы оплаты, доставки и авторизации;
- разные модели или провайдеры внешнего API;
- стратегии ранжирования;
- форматы экспорта;
- правила валидации по типу документа;
- обработчики событий.

### Где O может быть лишним

Если вариантов всего два и они не будут расширяться, простой if часто понятнее. Не надо создавать фабрики и десяток классов ради гипотетического третьего варианта. Это место для осознанного решения, а не догма.

### В ML-коде

Можно определить общий контракт Predictor и подключать LogisticPredictor, TorchPredictor или RemotePredictor. Но не нужно создавать абстракцию, если модель навсегда одна, а изменение будет только заменой файла конфигурации.

## 4. L — Liskov Substitution Principle

### Что означает

Если функция ожидает базовый тип, любой его подтип должен работать без неожиданных сюрпризов. Подтип может быть реализован иначе, но обязан сохранять контракт:

- принимать допустимые входы базового типа;
- возвращать обещанный результат;
- не усиливать неожиданные ограничения;
- не нарушать инварианты объекта;
- не менять смысл уже существующей операции.

### Классический пример нарушения

~~~python
class Bird:
    def fly(self) -> None:
        print("flying")


class Penguin(Bird):
    def fly(self) -> None:
        raise NotImplementedError("Penguins cannot fly")
~~~

Код, который получил Bird, вправе вызвать fly. Penguin формально наследуется, но не может заменить Bird.

Проблема не в том, что пингвин не летает. Проблема в неверной абстракции: «птица» не означает «объект, у которого обязательно есть fly».

### Более точная модель

~~~python
from typing import Protocol


class Flyable(Protocol):
    def fly(self) -> None: ...


class Bird:
    pass


class Eagle(Bird):
    def fly(self) -> None:
        print("flying")


class Penguin(Bird):
    pass
~~~

Теперь функция, которой нужен полёт, принимает Flyable, а не любую Bird.

### Практический пример с хранилищем

Если базовый Storage обещает read и write, нельзя сделать подтип ReadOnlyStorage, который неожиданно выбрасывает исключение на write, если потребители ожидают полноценное хранилище. Лучше разделить контракты на Reader и Writer.

### Что проверять на интервью

- Какие предусловия подтип усиливает?
- Может ли подтип вернуть другой тип или нарушить формат?
- Не меняет ли он смысл исключений?
- Не требует ли он дополнительных скрытых условий?
- Сохраняются ли важные инварианты?

### Связь с Python

Утиная типизация позволяет объекту подходить по поведению без общего предка. Но это не отменяет Liskov: если объект имеет метод с нужным именем, он всё равно должен вести себя по ожидаемому контракту.

## 5. I — Interface Segregation Principle

### Что означает

Клиент не должен зависеть от методов, которыми он не пользуется. Большой интерфейс заставляет простой компонент реализовывать лишние методы, ставить заглушки и тянуть ненужные зависимости.

### Плохой пример

~~~python
from abc import ABC, abstractmethod


class OfficeDevice(ABC):
    @abstractmethod
    def print(self, text: str) -> None: ...

    @abstractmethod
    def scan(self) -> bytes: ...

    @abstractmethod
    def fax(self, number: str, document: bytes) -> None: ...
~~~

Простой принтер вынужден реализовывать scan и fax или выбрасывать NotImplementedError.

### Разделяем интерфейсы

~~~python
from typing import Protocol


class Printer(Protocol):
    def print(self, text: str) -> None: ...


class Scanner(Protocol):
    def scan(self) -> bytes: ...


class SimplePrinter:
    def print(self, text: str) -> None:
        print(text)


def print_report(device: Printer, report: str) -> None:
    device.print(report)
~~~

Функция print_report знает только о печати. Ей не нужен scanner, а тесту можно передать маленькую заглушку.

### Как это выглядит в ML-сервисе

Не передавайте всему пайплайну огромный объект ModelPlatform с методами загрузки модели, записи в feature store, отправки метрик и управления GPU. Компоненту оценки нужен маленький Predictor, а компоненту мониторинга — MetricsSink.

### Компромисс

Дробить интерфейс надо по реальным клиентам, а не по каждой строке. Если два метода всегда используются вместе и имеют один жизненный цикл, разделение может только усложнить код.

## 6. D — Dependency Inversion Principle

### Что означает

Высокоуровневая бизнес-логика не должна напрямую зависеть от деталей вроде requests, PostgreSQL или конкретного SDK. И бизнес-правила, и детали должны зависеть от абстракции. Деталь подключается снаружи.

Это часто называют dependency injection: объект получает свои зависимости через конструктор или функцию, а не создаёт их внутри себя.

### Плохой пример

~~~python
import requests


class WeatherRecommendation:
    def recommend(self, city: str) -> str:
        response = requests.get(
            "https://weather.example/api",
            params={"city": city},
            timeout=2,
        )
        temperature = response.json()["temperature"]
        return "take a coat" if temperature < 10 else "light clothes"
~~~

Класс трудно тестировать: каждый тест зависит от сети. Смена API потребует менять бизнес-логику.

### Dependency injection через Protocol

~~~python
from typing import Protocol


class WeatherClient(Protocol):
    def temperature(self, city: str) -> float: ...


class WeatherRecommendation:
    def __init__(self, weather: WeatherClient) -> None:
        self.weather = weather

    def recommend(self, city: str) -> str:
        temperature = self.weather.temperature(city)
        return "take a coat" if temperature < 10 else "light clothes"


class FakeWeather:
    def __init__(self, value: float) -> None:
        self.value = value

    def temperature(self, city: str) -> float:
        return self.value


service = WeatherRecommendation(FakeWeather(5))
assert service.recommend("Kazan") == "take a coat"
~~~

Production-код передаст HTTP-клиент, тест — FakeWeather. Бизнес-правило не знает, откуда пришла температура.

### Способы внедрения зависимостей

- параметр функции;
- конструктор класса;
- фабрика или composition root — место, где собирается приложение;
- dependency container, если проект действительно большой.

В небольшом Python-сервисе явный конструктор чаще понятнее магического контейнера.

### В ML-коде

Передавайте Predictor, FeatureStore, Clock, RandomGenerator и MetricsSink снаружи. Это позволяет в тесте зафиксировать время, seed, ответы API и модель, а в production подключить реальные реализации.

## 7. Как принципы работают вместе

SOLID — не пять независимых галочек.

Рассмотрим сервис оценки документа:

1. S отделяет OCR, нормализацию, бизнес-проверки и сохранение результата.
2. O позволяет добавить новый OCR-провайдер или новый тип документа отдельным обработчиком.
3. L гарантирует, что любой OCR-провайдер соблюдает общий контракт результата и ошибок.
4. I даёт разные маленькие интерфейсы: распознать, проверить, сохранить.
5. D позволяет use case зависеть от абстракций, а не от конкретного SDK.

Вместе это даёт возможность заменить OCR или базу, не переписывая сценарий проверки.

### Пример сборки зависимостей

~~~python
def build_application() -> DocumentService:
    ocr = YandexOcrClient(api_key=load_secret("OCR_KEY"))
    validator = InvoiceValidator()
    repository = PostgresDocumentRepository(dsn=load_secret("DB_DSN"))
    return DocumentService(ocr, validator, repository)
~~~

Место, где выбираются конкретные реализации, называют composition root. Остальной код работает с их контрактами.

## 8. SOLID и другие принципы

### SOLID не заменяет KISS

KISS означает «делай проще, если простоты достаточно». Для одноразового скрипта, маленькой функции или стабильного формата сложная иерархия классов может быть хуже прямого кода.

### SOLID не равен DRY

DRY борется с ненужным дублированием, SOLID — с плохими границами ответственности и зависимостями. Иногда небольшое дублирование лучше, чем ранняя общая абстракция.

### SOLID не требует наследования

В Python чаще подходят композиция, функции и Protocol. Наследование полезно, когда действительно существует отношение «является» и соблюдается Liskov.

### YAGNI

You Aren't Gonna Need It — не добавляйте точки расширения, которыми пока никто не пользуется. Сначала найдите реальную ось изменений и только затем вводите абстракцию.

## 9. Частые нарушения в production-коде

### God object

Один класс знает про HTTP, базу, ML-модель, конфигурацию, retries и бизнес-правила. Обычно нарушены S и D. Начинайте исправление с выделения внешних зависимостей и use case, а не с механической нарезки файлов.

### Абстракция ради абстракции

Интерфейс IThingFactoryProviderRepository на одну реализацию усложняет чтение. Абстракция оправдана, когда есть сменяемая деталь, независимый тест или несколько реализаций.

### Наследование для повторного использования кода

Если классы просто делят несколько строк, лучше вынести функцию или использовать композицию. Наследование создаёт контракт и ограничения на будущее.

### Универсальный интерфейс

Методы, которые большинство реализаций не поддерживает, — сигнал нарушенного ISP или плохой предметной модели.

### Скрытые зависимости

Вызов глобального клиента, чтение текущего времени и случайности внутри бизнес-метода усложняют тесты. Передавайте Clock и генератор случайных чисел, если это влияет на результат.

## 10. Как проверять SOLID код-ревью

Перед одобрением изменения спросите:

1. Какая причина изменения у нового класса?
2. Как добавить второй вариант без переписывания стабильного use case?
3. Можно ли подменить зависимость в тесте?
4. Не заставляет ли интерфейс реализацию поддерживать лишнее?
5. Сохраняет ли новый подтип контракт?
6. Не введена ли абстракция раньше реальной потребности?
7. Где находится сборка production-зависимостей?

Важно смотреть не на количество классов, а на направление зависимостей и стоимость изменения.

## 11. Практический пример для агентной системы

Пусть агент должен найти товар и добавить его в корзину.

- AgentOrchestrator управляет циклом и лимитом шагов — S.
- SearchTool, CartTool и DeliveryTool реализуют маленькие контракты — I.
- Оркестратор зависит от ToolRegistry и Policy, а не от конкретного HTTP SDK — D.
- Новый способ доставки добавляется отдельным tool или strategy — O.
- Любой CartTool обязан одинаково соблюдать контракт идемпотентности и ошибок — L.

Checker и policy остаются отдельными компонентами. Нельзя прятать проверку безопасности внутри одного конкретного инструмента, иначе другой tool обойдёт её.

## 12. Что сказать на интервью

> «SOLID — это эвристики, которые уменьшают стоимость изменений. Single Responsibility означает одну причину изменения, а не один метод. Open/Closed полезен для устойчивых точек расширения, например стратегий доставки, но не оправдывает фабрику на два варианта. Liskov требует, чтобы подтип не ломал контракт базового типа. Interface Segregation подсказывает делать маленькие Protocol под конкретных клиентов. Dependency Inversion означает, что бизнес-логика получает внешние зависимости снаружи и не знает о requests или PostgreSQL. В Python я чаще использую композицию, Protocol и явный dependency injection; для маленького скрипта предпочту простой код без лишней архитектуры».

## Практическое задание

Возьмите класс, который одновременно читает CSV, валидирует данные, вызывает модель и пишет результат в базу.

1. Выпишите причины, по которым он может измениться.
2. Разделите внешние зависимости через Protocol.
3. Сделайте бизнес-правило вызываемым без файловой системы и сети.
4. Добавьте две реализации одной зависимости и тестовую заглушку.
5. Проверьте, не стали ли классы слишком мелкими.
6. Сформулируйте, какой новый вариант можно добавить без изменения use case.
