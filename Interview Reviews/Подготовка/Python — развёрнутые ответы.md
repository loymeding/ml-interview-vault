# 🐍 Python — развёрнутые ответы

> [!abstract] Логика хорошего ответа
> В Python на собеседовании обычно проверяют не знание синтаксиса, а понимание ссылочной модели, асимптотик и того, где ограничения рантайма важны для production-кода.

---

## 1. Почему Python используют в ML и разработке

Python популярен не потому, что быстрее всех исполняет циклы, а потому что он резко снижает время разработки: простой читаемый синтаксис, богатая стандартная библиотека, зрелая экосистема веба и очень сильный стек для данных - NumPy, pandas, scikit-learn, PyTorch, TensorFlow. В ML он ещё и выполняет роль общего языка между исследованием, подготовкой данных, обучением, сервисом и MLOps. Для команды это уменьшает стоимость передачи контекста и число технологических границ.

При этом Python часто выступает как «клей»: тяжёлая арифметика исполняется в C/C++/Fortran/CUDA внутри библиотек, а Python управляет пайплайном. Поэтому NumPy и PyTorch быстры, когда работа идёт крупными векторизованными операциями или на GPU; медленный Python-цикл вокруг миллионов элементов, наоборот, становится bottleneck. Главные минусы языка - более высокая CPU-стоимость, GIL в CPython, динамическая типизация, неидеальная предсказуемость latency и заметное потребление памяти. В критичном участке помогают профилирование, векторизация, компиляция/расширения, batch processing или перенос части сервиса на другой язык, а не преждевременная перепись всего проекта.

## 2. Объекты, ссылки, mutability и equality

В Python переменная хранит ссылку на объект. Immutable-объект нельзя изменить на месте: `int`, `float`, `str`, `tuple`, `frozenset`, `bytes` при «изменении» создают новый объект и имя начинает ссылаться на него. Поэтому `a = 3; a = 4` - переназначение имени, а не мутация числа. Mutable-объекты (`list`, `dict`, `set`, большинство экземпляров классов) меняют внутреннее состояние, и все ссылки увидят эффект. `tuple` остаётся immutable, даже если внутри лежит `list`: нельзя заменить элемент tuple, но можно изменить сам вложенный список.

`==` сравнивает значения по смыслу, а `is` - идентичность, то есть один ли это объект в памяти. Для пользовательского класса равенство определяет `__eq__`; если объект должен быть ключом словаря, также важен согласованный `__hash__`: равные объекты обязаны иметь одинаковый hash. Нельзя строить логику на interning строк или маленьких чисел: это деталь реализации CPython. Поверхностная копия копирует внешний контейнер, но разделяет вложенные объекты; `deepcopy` рекурсивно копирует вложенность. Из-за разделяемого состояния mutable default-аргумент создают один раз при определении функции, поэтому вместо `items=[]` безопаснее писать `items=None` и создать список внутри.

## 3. `dict`, `set`, хэш-таблицы и асимптотика

`dict` и `set` построены на хэш-таблице. Для ключа вычисляется `hash`, затем по нему ищется слот; у `dict` в слоте хранится пара key-value, а у `set` - только key. В среднем доступ, `in`, вставка и удаление занимают `O(1)`, потому что не нужно просматривать все элементы. При коллизии, когда разные ключи дали одно и то же место, реализация ищет следующий подходящий слот; в других реализациях бывает chaining, то есть список элементов в корзине. В худшем случае операции могут стать `O(n)`, например при патологических коллизиях, но CPython использует защитные механизмы и хорошую стратегию пробирования.

Ключ должен быть hashable: иметь стабильный hash в течение жизни в словаре и корректное равенство. Поэтому числа, строки и tuple из immutable элементов подходят, а `list`, `dict`, `set` - нет: изменение ключа после вставки сделало бы его недоступным по старому hash. Для `set` операции `union`, `intersection`, `difference` зависят от размеров множеств, но `in/add/remove` в среднем `O(1)`. Современный `dict` сохраняет порядок вставки как гарантию языка, но не является отсортированной структурой: сортировка ключей требует отдельной операции и другой семантики.

## 4. ООП, `self`, `super()` и MRO

`self` - явная ссылка на экземпляр, которую Python подставляет при вызове `obj.method()`. Instance method работает с состоянием конкретного объекта; `@classmethod` получает класс `cls` и подходит для альтернативных конструкторов или логики уровня класса; `@staticmethod` не получает ни `self`, ни `cls` и уместен, когда функция просто тематически живёт рядом с классом. Инкапсуляция в Python основана на соглашениях: `_field` означает «внутреннее API», `__field` включает name mangling, а `@property` позволяет сохранить удобный атрибутный интерфейс, добавив проверку или вычисление.

`super()` не означает «вызови именно родителя», а ищет следующий метод в MRO - линейном порядке разрешения методов. Это критично при множественном наследовании: cooperative classes вызывают `super()` и получают корректную цепочку, если MRO можно построить по алгоритму C3. Бывают несовместимые иерархии, в которых порядок противоречив, тогда Python не создаст класс. В прикладном коде часто лучше композиция: объект получает нужную зависимость как поле, а не наследует несвязанный набор поведения. Методы `__repr__`, `__str__`, `__len__`, `__iter__` реализуют протоколы Python и делают объект естественным в логах, `len()` и циклах.

## 5. Память, reference counting и GC

В CPython основа управления памятью - reference counting: у объекта есть число сильных ссылок; когда оно стало нулём, объект обычно освобождается сразу. `del name` удаляет имя или ссылку, а не «объект вообще»; если ссылки остались в другом контейнере, объект продолжит жить. Это объясняет и предсказуемое освобождение ресурсов, и то, почему нельзя судить о жизни объекта только по одной переменной.

Reference counting не справляется с циклом `a -> b -> a`: внешних ссылок нет, но внутренние не дают счётчикам стать нулём. Для этого есть cyclic garbage collector; generational GC чаще проверяет молодые объекты, потому что краткоживущего мусора обычно много, а старые объекты сканирует реже. `__del__` лучше не использовать как механизм освобождения ресурса: порядок финализации и циклы усложняют поведение. Для файлов и соединений надёжнее `with`; утечки ищут через профилировщики, `tracemalloc`, метрики роста RSS и анализ живых ссылок.

## 6. Контекстные менеджеры и `with`

Контекстный менеджер формализует шаблон «взять ресурс - выполнить код - гарантированно освободить ресурс». `with open(...) as f:` вызывает `__enter__`, передаёт его результат в `as f`, а затем вызывает `__exit__` даже при исключении. Поэтому тот же паттерн естественно работает с файлами, соединениями, транзакциями, lock-ами и временными ресурсами. `__exit__(exc_type, exc, traceback)` может обработать исключение, вернув `True`; обычно он освобождает ресурс и возвращает `False`, чтобы ошибка не была скрыта.

Свой менеджер можно написать классом с `__enter__`/`__exit__` или через `@contextmanager` и `yield`. Класс удобен, когда нужно хранить состояние и явно управлять несколькими фазами; генераторный вариант компактнее для одного acquire/release. На интервью важно сказать, что `with` - это прежде всего гарантия cleanup, а не специальный синтаксис только для файлов.

## 7. Декораторы и логирование

Декоратор принимает функцию или класс и возвращает обёртку с дополнительным поведением. Синтаксис `@decorator` - это запись `func = decorator(func)`. Так подключают логирование, измерение времени, кэширование, авторизацию и retry, не смешивая этот код с бизнес-логикой. Обёртка должна принимать `*args, **kwargs`, а `functools.wraps` сохраняет имя, docstring и другие метаданные исходной функции - это важно для дебага, документации и фреймворков.

Декоратор с параметрами - ещё один уровень функции: внешняя функция принимает конфиг, возвращает сам декоратор, а тот - wrapper. У retry нужно определить, какие исключения повторять, число попыток, backoff и идемпотентность операции; без этого можно многократно списать деньги или создать дубликат. В production вместо `print` используют `logging`: logger создаёт событие, handler отправляет его в stdout/файл/систему наблюдаемости, formatter задаёт структуру. Уровни `DEBUG`, `INFO`, `WARNING`, `ERROR`, `CRITICAL` позволяют фильтровать шум, а `logger.exception()` внутри `except` пишет stack trace. Секреты и персональные данные в логи не попадают: их маскируют и задают правила доступа/retention.

## 8. GIL, threading, multiprocessing и asyncio

В CPython GIL позволяет исполнять Python bytecode только одному потоку одновременно в одном процессе. Это упрощает внутреннее управление памятью, но не ускоряет CPU-bound чистый Python-код несколькими потоками. `threading` остаётся хорош для I/O-bound работы: пока поток ждёт сеть, диск или БД, другой может выполняться; кроме того, нативная библиотека может временно отпускать GIL. Для CPU-bound задач обычно используют `multiprocessing`, распределённые вычисления или нативные/GPU-библиотеки: процессы имеют отдельные интерпретаторы и память, но требуют сериализации данных и несут IPC-overhead.

`asyncio` - кооперативная concurrency-модель: корутина в точке `await` добровольно отдаёт управление event loop, который обслуживает другие I/O-задачи. Она особенно эффективна для множества сетевых запросов, но не ускоряет тяжёлый CPU-код: блокирующая функция остановит event loop, пока её не вынести в executor/процесс. Потоки разделяют память и требуют locks вокруг общего mutable state; процессы изолированы и безопаснее от гонок, но дороже. Для GPU Python-потоки сами по себе не делают матричные операции параллельными: там важнее очередь GPU-операций, batching и освобождение CPU от подготовки данных.

## 9. `list`, `deque`, linked list и амортизация

Python `list` - dynamic array: элементы лежат в непрерывном массиве ссылок, поэтому доступ по индексу `O(1)`, а append обычно `O(1)`. Когда capacity заканчивается, Python выделяет больший массив и копирует ссылки, и один append становится `O(n)`. Но расширения происходят редко, поэтому последовательность из многих append занимает `O(n)`, а средняя стоимость одного append - амортизированное `O(1)`. Вставка/удаление в начале или середине стоят `O(n)`, потому что хвост надо сдвигать.

Linked list хранит узлы со ссылками друг на друга: вставка при известном узле может быть `O(1)`, но поиск и доступ по индексу `O(n)`, а каждый узел расходует дополнительную память и плохо дружит с CPU cache. Поэтому в Python чаще берут `list`, а для дешёвого добавления/извлечения с обоих концов - `collections.deque`. `deque.popleft()` имеет `O(1)`, тогда как `list.pop(0)` - `O(n)`. Average-case описывает обычное распределение входов, worst-case - максимальную цену одного запуска, а amortized - среднюю цену операции в длинной последовательности, включая редкие дорогие расширения.

## 10. Big O, сортировка и выбор подхода

`O(1)`, `O(log n)`, `O(n)`, `O(n log n)`, `O(n^2)` описывают, как растёт верхняя оценка ресурса с размером входа. У двух вложенных циклов, каждый по `n`, обычно `O(n^2)`, но вложенность сама по себе не приговор: два указателя могут суммарно сдвинуться не более `n` раз и дать `O(n)`. Бинарный поиск работает за `O(log n)` только на данных с монотонным порядком, потому что каждый шаг отбрасывает половину диапазона.

Хэш-таблица часто даёт `O(n)` решение для поиска пар или подсчётов, а сортировка - `O(n log n)`. Сортировка всё равно может быть лучше: нужен упорядоченный результат, память ограничена, важна детерминированность, требуется диапазонный обход или hash-операции дороги. Python использует Timsort: это стабильный алгоритм с worst-case `O(n log n)`, который умеет находить уже отсортированные «runs» и потому очень хорош на реальных частично упорядоченных данных. Рекурсивный алгоритм оценивают по числу подзадач и глубине; также всегда проговаривают trade-off времени и памяти, например hash map ускоряет поиск ценой `O(n)` дополнительной памяти.
