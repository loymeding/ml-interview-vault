# 🟣 Ozon - развёрнутые ответы: RAG, LLM и ML

> [!abstract] Как отвечать на интервью
> В этом наборе почти за каждым определением стоит практический вопрос: «как бы ты это измерил», «что сломается в production» и «какое действие сделаешь по результату метрики». Поэтому в ответе полезен порядок: **цель → механизм → метрика → trade-off → следующий шаг**.

## 1. 🧩 RAG: от поиска к честному ответу

**RAG, Retrieval-Augmented Generation**, отвечает не только из параметров LLM, а сначала находит внешние документы, затем передаёт выбранные фрагменты вместе с вопросом в генеративную модель. Базовый pipeline: ingestion документов, очистка и chunking, embedding и индекс, query embedding/retrieval, при необходимости hybrid search и reranker, сбор контекста, prompt для LLM и post-processing с цитатами/guardrails. Смысл RAG - обновлять знания без полного fine-tuning, давать ответ с опорой на источник и уменьшать галлюцинации, но сам по себе он не гарантирует ни полноту поиска, ни factuality генерации.

Embedding-модель выбираю не по абстрактному MTEB, а по целевому языку, домену, длине chunk, типу запросов, Recall@k/nDCG на внутреннем golden set, latency на нужном железе, размерности векторов, лицензии и стоимости индекса. Для генеративной LLM дополнительно важны instruction following, русский язык, context window, structured output/tool calling, latency первого токена и decode, стабильность, безопасность, цена и возможность self-hosting. Хорошая production-схема часто использует небольшую быструю embedding-модель, отдельный cross-encoder reranker и LLM нужного размера, а не одну максимально большую модель на всё.

Golden dataset для retrieval должен состоять из реальных пользовательских формулировок и размеченных релевантных фрагментов, включать многодокументные вопросы, синонимы, опечатки, редкие темы, отрицательные запросы и документы с похожей лексикой, но неверным смыслом. Recall@k показывает, попал ли хотя бы один нужный фрагмент в верхние $k$; Precision@k - какую долю верхних $k$ составляют релевантные; MRR сильнее вознаграждает ранний первый правильный результат:

$$\Large MRR=\frac{1}{|Q|}\sum_{q\in Q}\frac{1}{rank_q}$$

$|Q|$ - число запросов, $rank_q$ - позиция первого релевантного документа. Поэтому MRR может быть высоким, если один правильный chunk почти всегда первый, но остальные необходимые части ответа не найдены; для coverage смотрю Recall@k и nDCG. Качество генерации отдельно измеряю faithfulness/groundedness к контексту, answer relevance, completeness, корректность цитат и human rubric. Если retrieval плох, нельзя «вылечить» его промптом; если retrieval хорош, но faithfulness низкий, проблема в контексте/prompt/LLM/postprocessing.

Hybrid retrieval объединяет lexical BM25 и semantic vector search. BM25 опирается на совпадение терминов, частоты и длину документа - он особенно хорош для артикулов, имён, кодов и точных формулировок; vector search находит смысловые перефразы, но может пропустить редкий идентификатор. RRF объединяет уже ранжированные списки без приведения score к единой шкале:

$$\Large RRF(d)=\sum_{s\in S}\frac{1}{k+rank_s(d)}$$

$d$ - документ, $S$ - поисковые системы или query variants, $rank_s(d)$ - позиция документа в системе $s$, $k$ - сглаживающая константа. После RRF полезен reranker, который внимательно сравнивает query и несколько десятков кандидатов. Query rewrite, multi-query, HyDE, decomposition и извлечение metadata полезны, но добавляют latency и могут исказить исходное намерение; их включают по метрикам и по типу запроса, а не всегда.

При жалобе на галлюцинации я сначала строю taxonomy: документ не найден, найден нерелевантный, правильный фрагмент обрезан, контекст переполнен/противоречив, LLM игнорирует контекст или ответ формально верный, но без нужного источника. Затем измеряю это на размеченных кейсах и исправляю слабое звено: chunking/metadata/hybrid/rerank при низком retrieval, prompt с явным правилом «отвечай только по контексту», citation verification, abstention и меньшая температура при generation issue. Запрещённые темы и PII нельзя блокировать только стоп-словами: нужны классификаторы/policy до retrieval, фильтрация документов по ACL/metadata, PII-redaction/tokenization, content moderation до и после генерации и запрет tool calls вне разрешённой схемы. При передаче во внешнюю LLM применяют data minimization, шифрование in transit и at rest, секреты вне prompt, redaction/pseudonymization, договорные гарантии обработки и audit trail; шифровать можно transport, но провайдеру для inference обычно нужен уже расшифрованный, поэтому главная защита - не отправлять лишнее.

Few-shot - это примеры «вопрос → желаемый ответ/формат», положенные в prompt во время inference; веса модели при этом не меняются. Fine-tuning меняет параметры на многих обучающих примерах. Structured output ограничивает ответ схемой JSON/Pydantic/grammar; надёжнее всего schema-constrained decoding или native structured output API, затем обязательная валидация и retry. Простая инструкция «ответь JSON» не гарантирует корректность в production.

## 2. 📏 Классификация и clustering: метрика следует за решением

**Классификация** назначает объекту один класс (binary/multiclass) или несколько независимых меток (multilabel). В binary case модель обычно предсказывает вероятность $p=P(y=1\mid x)$, а базовый loss - binary cross-entropy:

$$\Large \mathcal{L}=-\frac{1}{n}\sum_{i=1}^{n}\left[y_i\log p_i+(1-y_i)\log(1-p_i)\right]$$

$y_i\in\{0,1\}$ - истинная метка, $p_i$ - предсказанная вероятность, $n$ - число объектов. Для нескольких взаимоисключающих классов используют categorical cross-entropy с softmax; focal loss добавляет больший вес трудным/редким примерам. Из алгоритмов уместно назвать logistic regression, деревья/gradient boosting, SVM, нейросети и transformer encoder для текста; выбор зависит от данных, интерпретируемости, latency и объёма разметки.

Accuracy годится только при сопоставимой цене ошибок и не слишком сильном дисбалансе. Precision отвечает «какая доля выданных позитивов верна», Recall - «какую долю реальных позитивов нашли», ROC-AUC - способность ранжировать positive выше negative по всем порогам, PR-AUC полезнее на редком позитиве, LogLoss проверяет вероятности. Формулы:

$$\Large Precision=\frac{TP}{TP+FP},\qquad Recall=\frac{TP}{TP+FN},\qquad F_1=2\cdot\frac{Precision\cdot Recall}{Precision+Recall}$$

Гармоническое среднее F1 почти не даёт высокой оценки, если одна из двух величин провалилась: при Precision=1 и Recall=0 F1=0, в отличие от арифметического среднего 0.5. Если Precision важнее Recall, беру $\beta<1$ в $F_\beta$; если важнее Recall - $\beta>1$:

$$\Large F_\beta=(1+\beta^2)\frac{Precision\cdot Recall}{\beta^2\cdot Precision+Recall}$$

Для прогноза торнадо чаще критичнее Recall: пропустить реальную угрозу дорого. Но это не автоматический ответ: если после каждого алерта останавливают производство или эвакуируют город, очень низкий Precision разрушит доверие и создаст огромную цену ложных тревог. Я бы задал стоимость FP/FN, выбрал рабочую точку по expected cost и оставил guardrail на число алертов. AUC 0.7 лучше AUC 0.5 как ранжировщик, AUC 0.5 эквивалентен случайному; AUC 0.1 хуже случайного, но его можно инвертировать и получить 0.9, если действительно перепутано направление score.

В multiclass метрики считают one-vs-rest для каждого класса и усредняют. Micro суммирует все TP/FP/FN и доминируется частыми классами; macro даёт каждому классу равный вес и показывает качество на редких; weighted macro взвешивает по support. При важных редких классах смотрю per-class и macro, а не успокаиваюсь высоким micro. 

Кластеризация группирует объекты без готовых меток. k-means минимизирует сумму квадратов расстояний до центроидов и предполагает примерно сферические кластеры похожей плотности; он быстрый, но требует задать $k$, чувствителен к scale/outliers и плохо видит сложную форму. DBSCAN ищет плотные области, умеет помечать шум и не требует числа кластеров, но чувствителен к $\varepsilon$/`min_samples`, плохо переносит разную плотность и высокую размерность. $k$ в k-means выбираю по elbow/inertia, silhouette, стабильности на bootstrap, интерпретируемости и полезности downstream-задачи, а не только по красивому изгибу графика. Silhouette для точки сравнивает близость к своему кластеру $a$ и ближайшему чужому $b$: $\Large s=(b-a)/\max(a,b)$. Без разметки смотрю silhouette, Davies-Bouldin и стабильность; с эталонными группами - ARI/NMI, но кластер может быть полезен и без совпадения с заранее заданными классами.

## 3. 🔎 Векторизация и embeddings

Эволюция представлений текста идёт от one-hot и Bag-of-Words к TF-IDF, static word embeddings и contextual sentence embeddings. BoW считает, сколько раз токен встретился в документе, игнорирует порядок и обычно даёт большой разреженный вектор. TF-IDF понижает вес частых во всём корпусе слов:

$$\Large TFIDF(t,d)=TF(t,d)\cdot\log\frac{N}{DF(t)}$$

$TF(t,d)$ - частота термина $t$ в документе $d$, $DF(t)$ - число документов с термином, $N$ - число документов. Это сильный прозрачный baseline, но он не знает синонимов и смысла контекста.

Word2Vec учит плотные векторы на локальном контексте. CBOW по окружающим словам предсказывает центральное слово; Skip-gram по центральному слову предсказывает соседей. На больших словарях часто используют negative sampling: положительные пары «слово-контекст» должны иметь высокий dot product, случайные отрицательные - низкий. FastText представляет слово суммой символьных n-грамм, поэтому строит embedding для OOV и лучше переносит опечатки/морфологию. Современные BERT-like encoder дают contextual token embeddings, а bi-encoder/sentence-transformer обучают один embedding всего текста для поиска.

Cosine similarity измеряет угол, а не длину векторов:

$$\Large \cos(a,b)=\frac{a\cdot b}{\|a\|\|b\|}$$

Значение 1 означает одно направление, 0 - ортогональность, -1 - противоположные направления. Для L2-normalized embeddings cosine ranking эквивалентен ranking по dot product; Euclidean distance полезна, когда абсолютная геометрия и норма значимы, Manhattan - когда нужна устойчивость к отдельным большим отклонениям. Метрику выбирают согласованно с тем, как модель обучалась: нельзя без проверки заменить cosine на L2 в индексе.

Для retrieval sentence embeddings обучают contrastive objective: положительная пара должна быть близкой, in-batch/hard negatives - далёкими. Triplet loss задаёт anchor $a$, релевантный positive $p$, нерелевантный negative $n$ и margin:

$$\Large \mathcal{L}=\max(0, d(a,p)-d(a,n)+m)$$

$d$ - расстояние, $m$ - требуемый зазор. Если negative уже дальше positive минимум на $m$, loss нулевой; hard negatives особенно полезны, но ложный negative может повредить обучению. На практике качество embedding-модели проверяю retrieval-метриками на query-document парах, а не только красивым scatter plot.

## 4. 🧠 Transformer и decoding LLM

Transformer состоит из attention-блоков, feed-forward network, residual connections и normalization. Encoder читает всю входную последовательность bidirectionally и подходит для понимания/embeddings; decoder генерирует слева направо и использует causal mask; encoder-decoder T5 сначала кодирует вход, а decoder генерирует выход с cross-attention к encoder. В self-attention из скрытых состояний $H$ получают три линейные проекции: Query - что токен ищет, Key - по чему другие находят токен, Value - какую информацию он передаёт:

$$\Large Attention(Q,K,V)=softmax\left(\frac{QK^T}{\sqrt{d_k}}+M\right)V$$

$d_k$ - размерность key, деление удерживает logits в рабочем диапазоне softmax; $M$ - mask, например $-\infty$ для будущих токенов. Multi-head attention делает несколько независимых проекций, чтобы разные головы могли ловить разные типы связей. Полный attention имеет $O(n^2)$ времени и памяти по длине $n$ из-за матрицы всех пар токенов, поэтому длинный контекст дорог.

Без positional information self-attention инвариантен к перестановке входных токенов. Бывают learned absolute таблицы, фиксированные sinusoidal encodings, относительные схемы и RoPE/ALiBi. В RoPE пары координат Q и K вращают на угол, зависящий от позиции; в скалярном произведении остаётся зависимость от разности позиций. V обычно не вращают. Это даёт удобную относительную геометрию и совместимость с KV-cache; для длинного контекста частоты могут масштабировать методами вроде NTK/YaRN, но экстраполяцию всегда проверяют на target length, а не считают бесплатной.

BERT - encoder-only и masked language modeling, хорош для классификации и embeddings; GPT - decoder-only и next-token prediction, естественен для генерации; T5 - encoder-decoder и формулирует задачи как text-to-text. При генерации температура делит logits перед softmax: низкая делает распределение более острым и ответ стабильнее, высокая увеличивает разнообразие и риск ошибок. $T$ должно быть положительным; практические значения часто около 0-1, но зависят от сервиса. Top-k оставляет $k$ наиболее вероятных токенов, top-p берёт минимальное множество с суммарной вероятностью не менее $p$, поэтому адаптируется к уверенности модели. Beam search хранит несколько лучших префиксов и оптимизирует вероятность последовательности, но дорог, увеличивает latency и часто даёт шаблонные ответы, поэтому в чатах чаще используют temperature + top-p/top-k. Для кода и фактологии температуру обычно снижают, но не подменяют этим проверку фактов.

## 5. ⚙️ Fine-tuning и быстрый inference

Full fine-tuning меняет все веса и даёт максимум свободы, но требует много VRAM и может вызвать forgetting. Adapters, prompt/prefix tuning и LoRA меняют только малую часть параметров. В LoRA базовую матрицу $W$ замораживают и обучают низкоранговую дельту:

$$\Large y=Wx+\frac{\alpha}{r}ABx$$

$W$ - исходные веса, $A$ и $B$ - маленькие обучаемые матрицы, $r\ll d$ - rank, $\alpha$ - масштаб дельты. Вместо $d^2$ параметров обучают примерно $2dr$. Обычно адаптируют Q/V (иногда все attention и MLP projections), начинают с rank порядка 4-16 для простой задачи и повышают для сильного domain shift, но выбирают по validation. На inference дельту можно merge-нуть в $W' = W + \alpha AB/r$, чтобы не платить дополнительный compute; не merge-ят, когда нужно динамически переключать несколько adapters или базовые веса квантизованы/общие.

QLoRA хранит замороженный backbone в 4-битном виде, часто NF4, а обучает LoRA-adapters в более высокой точности; double quantization дополнительно сжимает scale. Это экономит память, но не означает «всё обучение в int4»: оптимизатор и adapters имеют свои состояния и precision. Квантование для inference переводит веса/активации в int8/int4: PTQ быстрее применить к готовой модели, QAT точнее при сложном режиме; static использует calibration ranges, dynamic считает их на лету, weight-only экономит память, но не все операции. После квантования обязательно проверяю task quality, numerical parity, long-context и реальные latency/RAM, потому что выигрыш зависит от kernel/hardware.

Distillation обучает student повторять распределение teacher, а не только hard label. Вероятности несут «тёмное знание»: teacher показывает, что два класса похожи, хотя правильный один; температура делает это распределение более информативным. KV-cache хранит Key/Value прошлых токенов на каждом decoder layer, чтобы на новом шаге не пересчитывать всю историю. Он резко уменьшает повторный compute, но растёт с layers × context × heads × head_dim × batch и становится главным потребителем памяти. Paged attention/continuous batching в vLLM управляют этим кешем блоками, уменьшая фрагментацию и позволяя обслуживать много запросов.

Speculative decoding использует маленькую draft-модель: она предлагает несколько токенов, большая target-модель проверяет их параллельно и принимает корректный префикс. Ускорение появляется, только если draft достаточно часто угадывает и проверка действительно эффективна на target runtime; при плохом acceptance или маленькой модели основная выгода исчезает. Другие пути ускорения: batching/continuous batching, FlashAttention, kernel fusion, prefix caching, GQA/MQA, квантование, pruning/distillation, ONNX/TensorRT и специализированные serving engines - но каждый меняет компромисс quality, latency, memory и операционную сложность.

## 6. 🤖 Агенты: когда нужен выбор действий

LLM-агент - это LLM плюс state, tools, loop принятия решения и правила остановки. Он читает задачу и состояние, выбирает действие, вызывает инструмент, получает observation и решает следующий шаг. ReAct - распространённый паттерн, в котором reasoning и action чередуются: модель планирует, делает вызов поиска/калькулятора/RAG, видит результат и корректирует ход. В production внутренние reasoning traces не обязательно показывать пользователю и не стоит считать их единственным механизмом надёжности; важнее строгие tool schemas, permission boundaries, таймауты, лимиты шагов и валидация результата.

Workflow - заранее заданный детерминированный граф: например, классифицировать запрос → извлечь поля → поискать → сформировать ответ → проверить JSON. Агент сам выбирает маршрут и число шагов. Если путь известен, критичны latency/аудит/предсказуемость или ошибка дорого стоит, workflow лучше. Кроме ReAct есть Plan-and-Execute, router, supervisor/worker, multi-agent, reflection/critic. Они добавляют гибкость, но умножают latency, цену, пространство отказов и проблему наблюдаемости. LangGraph удобен для явного state graph, checkpoint и циклов, но агент можно реализовать обычным кодом/очередью: фреймворк не решает качество модели, tool safety и evaluation за инженера.

LLM для агента выбираю по целевым задачам и eval set: правильность tool calling/structured output, способность следовать policy, качество reasoning на нужной сложности, context, multilingual support, latency, цена, доступность self-hosting и observability. Для простого routing не нужна самая большая модель; для финансового или пользовательского действия важнее надёжность, подтверждение и fallback, чем эффектные рассуждения. Память делю на краткосрочный context текущего диалога, явный state workflow, эпизодическую long-term memory и retrieval из vector/SQL store. В память пишу только проверенные и полезные факты с TTL/источником, иначе система постепенно загрязняет собственный context нерелевантными или ложными выводами.

## 7. 🧪 Ассессоры, agreement и LLM-as-a-Judge

Для оценки классификатора диалогов внешними ассессорами формирую выборку не «случайно тысячу строк», а стратифицированно: по предсказанному классу/уверенности, редким и бизнес-критичным классам, языкам, источникам, времени и известным failure modes. Удаляю или маскирую PII, даю понятную инструкцию с границами классов, примерами, интерфейсом с достаточным контекстом и blind assignment. До основного раунда запускаю pilot, проверяю понимание rubric и корректирую неоднозначности; часть gold tasks и повторов нужна для контроля качества разметчика.

При тройном перекрытии сначала смотрю agreement в целом и по классам/ассессорам/времени: слишком быстрые ответы, систематический уклон к классу, низкое agreement на конкретном intent - это разные проблемы. Majority vote прост и годится при похожем качестве разметчиков и чётких метках. Weighted vote учитывает надёжность, а Dawid-Skene статистически оценивает latent true label и confusion matrix каждого annotator; он полезен при неодинаковом качестве, но не заменяет качественную инструкцию. Для двух разметчиков используют Cohen's kappa, для нескольких - Fleiss' kappa, Krippendorff's alpha гибче при пропусках и разных типах шкал. Kappa корректирует случайное согласие, но может быть низкой при сильном class imbalance даже при высоком raw agreement, поэтому всегда показываю confusion matrix, prevalence и примеры несогласия.

LLM-as-a-Judge использует одну модель для оценки ответа другой по rubric: например factuality, completeness, style или pairwise preference. Она дешево масштабируется, помогает быстрым итерациям и может видеть нюансы, не покрытые строковым совпадением. Риски - position bias, verbosity bias, self-preference, чувствительность к prompt, утечки judge в evaluated model и плохая корреляция с человеком на edge cases. Я валидирую judge на независимом human-labeled наборе: считаю agreement/correlation, bias по длине и позиции, стабильность к перестановке вариантов и разным prompts, затем калибрую rubric, few-shot примеры и пороги. Полностью отказываться от людей нельзя: люди нужны для gold set, аудита drift/bias, новых сценариев и high-stakes решений; LLM judge - ускоритель, а не источник абсолютной истины.

## 8. 🏗️ Инфраструктурный блиц: как связать компоненты

Redis обычно используют как быстрый in-memory cache: results retrieval, rate limits, session/state, короткий feature cache. Postgres - транзакционные сущности, права доступа, конфигурация, метаданные; ClickHouse - аналитические события и большие агрегаты с быстрыми колонночными запросами. Kafka - журнал событий и буфер между producer/consumer: она позволяет асинхронно строить ingestion, evaluation и feature pipeline. При at-least-once сообщение может прийти повторно, поэтому consumer должен быть idempotent, а offset фиксируют так, чтобы не терять обработанные события. gRPC использует protobuf и HTTP/2, поддерживает streaming и строгие контракты, поэтому часто удобен для внутренних низколатентных сервисов; REST проще для внешнего публичного API и отладки.

Docker делает окружение воспроизводимым: образ, pinned зависимости, entrypoint, конфигурация через secrets/env, но не заменяет orchestration, observability и безопасность образов. Git/Git Flow фиксирует историю кода; в ML также нужны версии данных, config, seed и model artifact. Triton Inference Server удобен для serving разных backend-ов с dynamic batching, model repository и metrics; vLLM специализируется на LLM-serving с paged KV-cache и continuous batching; ONNX нужен для переносимого оптимизированного графа, особенно вне Python runtime. Multi-GPU training требует понимать data parallel/DDP, градиентную синхронизацию, распределение batch, gradient accumulation, checkpointing и коммуникационное узкое место.

На вопрос «с чем работал» лучше не притворяться. Я отвечаю по схеме: уровень опыта, решённая задача, ключевой trade-off, как мерил результат и что сделал бы иначе. Аналогично с ТЗ для ассессоров: сильный ответ включает цель разметки, определение label taxonomy, примеры/контрпримеры, правила ambiguous cases, PII-политику, sampling, QA и способ агрегировать разметку. Это показывает, что разметка для тебя - часть ML-системы, а не внешняя механическая услуга.
