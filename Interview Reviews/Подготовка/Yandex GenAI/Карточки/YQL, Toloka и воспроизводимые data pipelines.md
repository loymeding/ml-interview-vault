# YQL, Toloka и воспроизводимые data pipelines

> [!abstract] Суть
> Внутренние инструменты заранее полностью не выучить; важно понимать распределённый query/data pipeline, качество крауда и provenance каждого датасета.

## 0. Сначала простая картина

Эта карточка не пытается выучить внутренние команды Yandex наизусть. Её цель — дать понятную модель работы: взять большие сырые данные, преобразовать их запросом, отправить часть примеров людям на проверку, собрать labels и сохранить результат так, чтобы другой человек мог повторить процесс.

YQL можно представить как SQL для распределённого мира. Обычный SQL часто мысленно работает с одной базой, а распределённый запрос выполняется на множестве машин. Из-за этого важны не только правильные фильтры и join, но и стоимость пересылки данных между машинами (shuffle), размеры промежуточных таблиц и детерминированность результата.

Toloka или другой crowd-сервис — это способ организовать много небольших человеческих проверок. Но «отправить задания» недостаточно: нужны понятная инструкция, контрольные примеры, повторная разметка части заданий, правила отбраковки и версия схемы. Provenance связывает итоговую таблицу с исходными данными, кодом, параметрами запуска и временем.

Дальше мы сначала разбираем роль YQL в pipeline, затем смотрим пример запроса, после чего обсуждаем крауд и чек-лист воспроизводимости. Так техническая часть соединяется с тем, что реально проверяют на аналитическом собеседовании.

### Словарь перед стартом

- **Distributed query** — запрос, вычисления которого выполняются на нескольких машинах.
- **Shuffle** — пересылка строк между машинами для объединения или группировки.
- **Label** — сохранённая человеческая или автоматическая оценка примера.
- **Provenance** — история происхождения и преобразований данных.

## 1. YQL как распределённый SQL-подобный слой

YQL — declarative language для запросов к распределённым хранилищам и системам обработки. Концептуально он близок к SQL, но запрос является программой, которая может строить граф вычислений и запускать цепочку операций на больших таблицах.

Нужно понимать:

- joins и стоимость shuffle;
- window functions;
- nested structures и JSON/YSON;
- цепочки подзапросов;
- UDF и Python/C++ extensions;
- partitioning и parallel execution;
- schema evolution;
- чтение логов за период без полного сканирования.

> [!tip] Переход от возможностей YQL к рабочему сценарию
> Список функций сам по себе мало полезен. Посмотрим, как из сырых событий получить срез задач, который можно отправить на проверку и затем использовать в эксперименте.

## 2. Пример аналитического запроса

Задача: найти срезы запросов, где модель часто вызывает неправильный tool.

Логически pipeline:

1. Отфильтровать период и нужную модель.
2. Нормализовать task/skill labels.
3. Развернуть список tool calls.
4. Сопоставить calls с expected tool.
5. Посчитать error rate по skill и версии модели.
6. Сохранить агрегаты и sample ids для ручного аудита.

Нельзя ограничиваться агрегатом: для каждого подозрительного среза нужны ссылки на исходные traces.

## 3. Toloka/крауд

Контур проекта:

~~~text
task definition -> instructions/examples -> qualification
-> control tasks -> overlap/consensus -> audit -> aggregation
~~~

Качество проекта начинается с хорошего task interface:

- данные видны в нужном контексте;
- критерии атомарны;
- examples покрывают спорные случаи;
- чувствительные данные скрыты;
- ответы сохраняются с версией rubric.

> [!tip] Переход от результата к доверию
> Таблица с labels ещё не является хорошим датасетом. Чтобы доверять ей через месяц и передать её коллеге, нужно сохранить происхождение, версии и параметры каждого шага.

## 4. Reproducibility checklist

- version dataset and split;
- version query/code and input snapshot;
- сохранить schema, provenance и фильтры;
- логировать model/judge/rubric versions;
- иметь rerunable pipeline и held-out set;
- фиксировать стоимость и объём обработки;
- сохранять sample ids для ручной проверки.

Если результат нельзя воспроизвести на том же snapshot, это не надёжный аналитический артефакт.

## 5. Практика

Прочитать в YQL docs SELECT, JOIN, window functions и JSON/YSON. Затем описать тот же pipeline в локальном Python/SQL или Dagster/Prefect: raw data → фильтры → labels → report.

Цель — показать переносимость принципов, а не имитацию закрытой инфраструктуры.

## Типичные ошибки

- **Считать YQL обычным SQL:** игнорируется распределённая стоимость операций.
- **Сохранять только агрегаты:** невозможно сделать error analysis.
- **Не версионировать rubric:** labels разных запусков несопоставимы.
- **Не хранить provenance:** невозможно доказать происхождение data.
- **Отдавать весь quality control одной автоматике:** сложные случаи требуют human audit.

## Вопросы для интервью

> [!question] Что нужно сохранить для воспроизводимости датасета?
> Snapshot/version источника, query/code, фильтры, schema, model/judge/rubric versions, seed и список исходных sample ids.

> [!question] Что важнее знать про Toloka до выхода на работу?
> Не кнопки интерфейса, а дизайн задания, квалификацию, контрольные примеры, overlap, aggregation и аудит качества.

> [!question] Зачем хранить raw traces, если есть aggregate metric?
> Aggregate показывает, где есть проблема; raw traces позволяют понять почему и собрать целевые данные.

## Проверка себя

- Спроектировать pipeline агрегации tool errors.
- Назвать пять источников nondeterminism.
- Объяснить, зачем нужны raw traces и sample ids.
- Составить quality control loop для крауд-проекта.
