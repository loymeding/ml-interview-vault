# 🌿 Git и Git Flow — развёрнутые ответы

> [!abstract] Как отвечать на интервью
> У Git полезно начинать не со списка команд, а с модели данных: Git хранит историю снимков проекта, а ветки и `HEAD` - это лёгкие ссылки на коммиты. Тогда различия между `merge`, `rebase`, `reset` и `revert` становятся логичными, а не заученными.

---

## 1. Базовая модель Git: snapshot, index и commit

**Git - распределённая система контроля версий.** Каждый commit - это неизменяемый снимок состояния отслеживаемых файлов плюс метаданные: автор, сообщение, время и ссылки на родительские коммиты. На практике Git не копирует все файлы при каждом коммите: неизменившиеся объекты переиспользуются. Главное для интервью: Git мыслит историей состояний, а не «файлами в облаке».

Перед коммитом есть три зоны. `working directory` - файлы, которые я сейчас редактирую; `staging area` или index - осознанно подготовленная версия следующего коммита; локальный repository - уже зафиксированная история. `git add` переносит *текущую версию конкретных изменений* в index, а `git commit` создаёт commit именно из index. Поэтому можно изменить два файла, но в один commit включить только один из них. `HEAD` обычно указывает на текущую ветку, а та - на её последний commit.

`git status` показывает состояние файлов относительно index и последнего commit; `git diff` показывает изменения working tree относительно index; `git diff --staged` - то, что уже войдёт в следующий commit. `.gitignore` предотвращает добавление ещё неотслеживаемых файлов, но не отменяет уже созданный commit: для уже tracked-файла нужно отдельно убрать его из index через `git rm --cached`.

## 2. Ветки, merge, rebase и cherry-pick

**Ветка - это просто подвижная ссылка на commit, а не копия проекта.** Локальная `main` и `origin/main` различаются: первая - моя ветка в локальном репозитории, вторая - сохранённое локально представление состояния удалённой ветки после `fetch` или `pull`. Поэтому по `origin/main` удобно увидеть, что опубликовано на сервере, но в неё напрямую я обычно не коммичу.

`merge` объединяет две линии истории, сохраняя их топологию; если ветка `main` не ушла вперёд после создания feature-ветки, получится fast-forward merge без отдельного merge commit. `rebase` берёт мои коммиты и «переигрывает» их поверх нового основания: история становится линейной, но идентификаторы коммитов меняются. Я использую `rebase` для своей локальной feature-ветки перед PR, а для уже опубликованной ветки, с которой работают коллеги, предпочитаю `merge`: переписывать им общую историю опасно.

`squash merge` сворачивает серию рабочих коммитов PR в один аккуратный commit в `main`: это удобно, когда промежуточные «fix tests» и «wip» не нужны в основной истории. `cherry-pick` переносит конкретный commit в другую ветку; типичный случай - точечно забрать bug fix в release-ветку, не таща за ним всю feature-ветку.

## 3. Конфликты: причина, разрешение и профилактика

**Конфликт не означает поломку Git.** Он означает, что Git не может безопасно выбрать одну версию, потому что две ветки изменили пересекающийся участок файла или одна изменила файл, который другая удалила. В файле появляются маркеры `<<<<<<<`, `=======`, `>>>>>>>`; нужно понять бизнес-смысл обеих правок, собрать корректный итоговый вариант, удалить маркеры, выполнить `git add`, а затем закончить операцию: `git commit` для merge или `git rebase --continue` для rebase.

Неудачный merge до создания коммита можно отменить через `git merge --abort`; неудачный rebase - через `git rebase --abort`. Конфликтов больше в long-lived branches, потому что они долго расходятся с `main`. Рабочая профилактика: маленькие PR, частая синхронизация с `main`, ясное владение файлами и декомпозиция больших изменений. Не стоит разрешать конфликт механически, выбирая «ours» или «theirs», не прочитав обе стороны: можно тихо потерять функциональность.

## 4. Отмена изменений: restore, reset, revert и reflog

**Эти команды работают с разными слоями Git.** `git restore` возвращает файл в working directory или снимает его со staging; это удобная локальная операция. `git reset` двигает указатель текущей ветки и, в зависимости от режима, может изменить index и рабочие файлы. `git reset --soft HEAD~1` отменяет commit, но оставляет изменения staged; стандартный `--mixed` оставляет их в файлах, но убирает из stage; `--hard` выбрасывает незакоммиченные изменения и потому опасен.

Для уже отправленного в общую ветку коммита безопаснее `git revert <sha>`: Git создаёт *новый* commit, который логически отменяет старый, и не переписывает историю коллег. Если что-то кажется потерянным после reset или rebase, сначала смотрю `git reflog`: он хранит недавние положения `HEAD`. Найдя нужный SHA, можно создать от него новую ветку или вернуть текущую ветку. Перед `reset --hard` на важной работе я либо делаю временную ветку, либо убеждаюсь, что изменения действительно не нужны.

## 5. Remote workflow, PR и CI

**`git fetch` скачивает новую историю с remote, но не меняет мою рабочую ветку.** `git pull` по сути делает `fetch`, а затем `merge` или `rebase` - это определяется настройками и флагами. `git push` отправляет локальные коммиты на remote; сервер отклонит non-fast-forward push, если удалённая ветка уже содержит чужие коммиты, которых у меня нет. Сначала забираю и интегрирую изменения, затем пушу снова.

Pull request / merge request - это не просто кнопка merge, а точка проверки изменения: корректность логики, тесты, миграции, безопасность, производительность, наблюдаемость и влияние на контракт. CI запускает автоматические линтеры, тесты, сборку и иногда деплой в окружение. Protected branch запрещает прямой push, force-push или merge без ревью и успешных checks. Чтобы обновить свою feature-ветку, я делаю `fetch`, затем либо `rebase origin/main` для личной ветки, либо `merge origin/main` - если история уже общая.

## 6. Git Flow, trunk-based development и feature flags

**Git Flow разделяет разработку и релизы несколькими долгоживущими ветками.** Обычно `main` отражает выпущенный код, `develop` - интеграционную ветку, от неё отходят `feature/*`; перед релизом создают `release/*`, а срочные исправления в production - в `hotfix/*` от `main` с последующим переносом в `develop`. Это дисциплинирует команды с редкими версионными релизами и длительной стабилизацией.

Минус Git Flow - накопление расхождений, сложные merge и дорогая интеграция. При частых деплоях часто лучше trunk-based development: короткие ветки, маленькие PR, частая интеграция в `main`. Незавершённую функциональность скрывают feature flags, а не держат месяцами в отдельной ветке. На интервью важно показать, что Git Flow не догма: стратегию выбирают по частоте релизов, размеру команды, требованиям к релизным веткам и зрелости CI/CD.

## 7. Теги, версии и релизы

**Tag - имя, закреплённое за конкретным commit.** Lightweight tag - просто ссылка; annotated tag хранит автора, дату и сообщение, его обычно используют для релизов. Git-тег удобен как неизменяемая точка, из которой воспроизводятся код и зависимости релиза. В Semantic Versioning версия имеет вид `MAJOR.MINOR.PATCH`: MAJOR меняется при несовместимом API, MINOR - при обратно совместимой функциональности, PATCH - при исправлениях.

В ML-проекте одной метки кода недостаточно. Для воспроизводимости я связываю Git SHA или tag с версией Docker image, конфигурацией, версией данных и артефактом модели в registry. Тогда можно ответить не только «какая модель сейчас в production», но и «какой именно код, датасет и параметры её породили».

## 8. Git в ML/Data Science

**В Git стоит хранить код, конфиги, схемы, небольшие тестовые данные, документацию и метаданные экспериментов.** Большие датасеты, чекпойнты и бинарные модели плохо подходят обычному Git: репозиторий раздувается, история медленно клонируется, а Git не оптимизирован для множества больших бинарных дельт. Для них выбирают DVC, S3/object storage, MLflow/artifact registry; Git LFS может подойти для умеренного числа крупных файлов, но не заменяет полноценное хранилище данных.

Хороший PR с изменением ML-пайплайна содержит не только код: что поменялось в признаках или данных, как обеспечена обратная совместимость, результаты offline-evaluation, что станет primary metric и какие guardrail-метрики будут мониториться после выкатывания. В каждом эксперименте фиксирую `commit_hash`, конфиг, seed, версию данных и окружение. Seed не гарантирует абсолютную повторяемость на любой GPU и библиотеке, но без него воспроизведение случайного пайплайна становится ещё хуже.
