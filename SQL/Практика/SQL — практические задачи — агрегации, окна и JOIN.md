# 🧪 SQL - практические задачи: агрегации, окна и JOIN

> [!abstract] Как тренироваться
> Сначала проговори логику и ограничения, затем пиши SQL. На собеседовании важны два вопроса: «что именно считает запрос?» и «что произойдёт на большой таблице?»

---

## 🧭 Карта задач

1. Кандидатный ключ, частоты имени и мода возраста на 100 млн строк.
2. Средний интервал между последовательными заказами.
3. Заполненность признаков по отчётным датам.
4. Средний чек в последние семь дней активности клиента.
5. Минимальная и максимальная кардинальность `LEFT JOIN`.

## 1. 👤 Таблица на 100 млн строк: ключ, частоты и мода

### Условие

Есть таблица `people(id, name, age)` примерно на 100 млн строк. Неизвестно, является ли `id` первичным ключом. Нужно проверить уникальность `id`, для каждой строки получить число появлений её `name` и найти самый частый возраст.

### 1.1 Проверка кандидатного ключа

```sql
SELECT
    COUNT(*) AS total_rows,
    COUNT(id) AS non_null_ids,
    COUNT(DISTINCT id) AS distinct_ids,
    COUNT(*) = COUNT(id)
        AND COUNT(*) = COUNT(DISTINCT id) AS is_candidate_key
FROM people;
```

`COUNT(*)` считает все строки, `COUNT(id)` - только не-`NULL` идентификаторы, `COUNT(DISTINCT id)` - уникальные значения. Если они совпали, данные сейчас удовлетворяют свойствам **кандидатного ключа**: `id` уникален и не пуст. Это не доказывает, что в схеме объявлен `PRIMARY KEY`: для этого в PostgreSQL смотрят ограничения и индексы в системном каталоге.

> [!warning] Нюанс 100 млн строк
> `COUNT(DISTINCT)` обычно потребует полного прохода и тяжёлой агрегации. Для разовой проверки запрос корректен, но в production сначала проверяют метаданные/уникальный индекс, а затем фиксируют инвариант через `PRIMARY KEY` или `UNIQUE NOT NULL`, а не пересчитывают таблицу регулярно.

### 1.2 Число одинаковых имён

Если число нужно вывести, физическую колонку добавлять не надо: это естественно считается оконной функцией.

```sql
SELECT
    id,
    name,
    age,
    COUNT(*) OVER (PARTITION BY name) AS name_count
FROM people;
```

`PARTITION BY name` формирует окно строк с одним именем; `COUNT(*)` считает размер окна, но не схлопывает строки, как сделал бы `GROUP BY`. Это правильный вариант для отчёта или витрины. На 100 млн строк он всё равно потребует группировки/сортировки по `name`, поэтому повторяющийся расчёт лучше вынести в отдельную агрегатную таблицу или materialized view:

```sql
CREATE MATERIALIZED VIEW people_name_counts AS
SELECT name, COUNT(*) AS name_count
FROM people
GROUP BY name;
```

Массовый `UPDATE` с коррелированным подзапросом из исходного решения будет дорогим, а колонка быстро устареет после `INSERT`, `DELETE` и изменения имени.

### 1.3 Самый частый возраст

```sql
SELECT
    age,
    COUNT(*) AS people_count
FROM people
WHERE age IS NOT NULL
GROUP BY age
ORDER BY people_count DESC, age ASC
FETCH FIRST 1 ROW WITH TIES;
```

Это ищет моду распределения возраста. `WITH TIES` возвращает все возраста с одинаковой максимальной частотой. Если нужен один детерминированный ответ, используют `LIMIT 1` и вторичную сортировку. Отдельно нужно договориться, считать ли `NULL` отдельной категорией или исключать, как в этом запросе.

## 2. 🛒 Средний интервал между последовательными заказами

### Условие

Есть `orders(order_id, date_time, amount, customer_id)` и `customer(customer_id, age)`. Для каждого клиента нужно вычислить средний интервал в днях между **соседними по времени** заказами.

### Решение через `LAG`

```sql
WITH ordered_orders AS (
    SELECT
        customer_id,
        order_id,
        date_time,
        LAG(date_time) OVER (
            PARTITION BY customer_id
            ORDER BY date_time, order_id
        ) AS previous_order_at
    FROM orders
)
SELECT
    customer_id,
    AVG(
        EXTRACT(EPOCH FROM (date_time - previous_order_at)) / 86400.0
    ) AS avg_interval_days
FROM ordered_orders
WHERE previous_order_at IS NOT NULL
GROUP BY customer_id;
```

`LAG` берёт предыдущую дату внутри клиента, поэтому для заказа `i` считается интервал только с заказом `i-1`. Вторичная сортировка по `order_id` делает порядок стабильным при одинаковом timestamp. `EXTRACT(EPOCH ...)/86400.0` - PostgreSQL-способ получить дни; в другой СУБД может потребоваться `DATEDIFF`.

Наивный self-join `o1.date_time > o2.date_time` для этой задачи неверен: он образует **все пары** заказов клиента, а не соседние. При трёх заказах туда попадут интервалы `1→2`, `2→3` и `1→3`, то есть среднее будет другим. Таблица `customer` нужна лишь если выводим её поля или хотим показать клиентов с менее чем двумя заказами через `LEFT JOIN`.

## 3. 📅 Заполненность признаков в динамике

### Условие

Есть таблица `report_table(report_dt, id, feature1, feature2)`, где `report_dt` - отчётная дата на конец месяца, а `id` не `NULL`. Нужно отслеживать заполненность признаков.

### Решение

```sql
SELECT
    report_dt,
    COUNT(*) AS total_records,
    COUNT(feature1) AS filled_feature1,
    COUNT(feature2) AS filled_feature2,
    COUNT(feature1)::numeric / NULLIF(COUNT(*), 0) AS feature1_fill_rate,
    COUNT(feature2)::numeric / NULLIF(COUNT(*), 0) AS feature2_fill_rate,
    1 - COUNT(feature1)::numeric / NULLIF(COUNT(*), 0) AS feature1_missing_rate,
    1 - COUNT(feature2)::numeric / NULLIF(COUNT(*), 0) AS feature2_missing_rate
FROM report_table
GROUP BY report_dt
ORDER BY report_dt;
```

`COUNT(feature1)` считает только не-`NULL`, а `COUNT(*)` - все строки. Поэтому их отношение - **fill rate**, доля заполненных значений. Выражение `1 - COUNT(feature1) / COUNT(id)` из исходного решения - это не completion rate, а missing rate. `::numeric` предотвращает целочисленное деление, `NULLIF` защищает от деления на ноль.

Для полноценного контроля качества также выводят абсолютное число пропусков, изменение к прошлому месяцу через `LAG` и отдельно определяют, считается ли пустая строка пропуском. Иначе одна доля без размера витрины может вводить в заблуждение.

## 4. 🧾 Средний чек за последние 7 дней активности клиента

### Условие

Есть `cheque(uid, created_at, "sum", shop_id, customer_id)`. Нужно вывести покупателя, его средний чек за последние семь дней **относительно последней покупки клиента** и дату последней покупки.

### Решение для персонального семидневного окна

```sql
WITH last_purchase AS (
    SELECT
        customer_id,
        MAX(created_at) AS last_purchase_at
    FROM cheque
    GROUP BY customer_id
)
SELECT
    ch.customer_id,
    AVG(ch."sum") AS average_check_last_7d,
    lp.last_purchase_at
FROM last_purchase AS lp
JOIN cheque AS ch
    ON ch.customer_id = lp.customer_id
   AND ch.created_at >= lp.last_purchase_at - INTERVAL '7 days'
   AND ch.created_at <= lp.last_purchase_at
GROUP BY
    ch.customer_id,
    lp.last_purchase_at;
```

Сначала находим последнюю покупку каждого клиента, затем оставляем все чеки персонального семидневного окна. Исходный вариант соединялся только со строкой, где `created_at = max_purchase_date`, поэтому усреднял один последний чек, а не неделю; в нём также был несуществующий alias `c` и ненужный join с `shop`.

Формулировка «за последнюю неделю» иногда означает глобальное окно от текущей даты. Тогда фильтр будет `created_at >= CURRENT_TIMESTAMP - INTERVAL '7 days'`, но в результат попадут только недавно активные клиенты. Это нужно уточнить до написания SQL.

## 5. 🔗 Сколько строк вернёт `A LEFT JOIN B`?

### Условие

Таблица `A` содержит 10 строк, таблица `B` - 50. Какое минимальное и максимальное число строк может вернуть `A LEFT JOIN B`?

### Ответ

**Минимум - 10 строк.** `LEFT JOIN` сохраняет каждую строку левой таблицы хотя бы один раз; при отсутствии пары справа правые поля будут `NULL`.

**Максимум без ограничений на ключи - 500 строк**, то есть `10 × 50`. Это возможно, если каждая строка `A` совпадает с каждой строкой `B` по условию соединения: например, ключ дублируется во всех строках обеих таблиц. `LEFT JOIN` не защищает от размножения: результат определяет кратность ключей, а не только тип join.

Если дополнительно известно, что каждая строка `B` совпадает не более чем с одной строкой `A`, например ключ `A` уникален, максимум равен 59: все 50 строк `B` могут совпасть с одной строкой `A`, а ещё 9 строк `A` останутся без пары. Если совпадения есть для всех 10 строк `A`, максимум будет 50. Поэтому сильный ответ на интервью: «минимум 10, максимум зависит от кардинальности; без ограничений 500».

> [!warning] Типичная ошибка
> Нельзя сложить размеры таблиц и получить 60. JOIN не `UNION`: одна строка слева может соединиться со многими справа, а дубли с обеих сторон дают декартово размножение внутри ключа.

## 🎙️ Что проговорить интервьюеру

- `COUNT(DISTINCT)` валидирует текущие данные, но не создаёт и не доказывает ограничение `PRIMARY KEY` в схеме.
- Для «предыдущей записи» сначала вспоминай `LAG`, а не self-join всех пар.
- Уточняй временное окно: последние семь календарных дней или семь дней относительно события клиента.
- До ответа про число строк после JOIN спроси об уникальности ключей и кардинальности связи.
