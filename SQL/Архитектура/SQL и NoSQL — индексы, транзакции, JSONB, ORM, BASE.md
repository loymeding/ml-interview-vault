# SQL и NoSQL — индексы, транзакции, JSONB, ORM, BASE

> [!abstract] Суть
> SQL-собеседования часто проверяют не синтаксис, а понимание механизмов: B-tree ускоряет диапазоны, уровни изоляции управляют аномалиями чтения, JSONB даёт индексацию полуструктурированных данных, ORM lazy loading может вызвать N+1, а NoSQL часто выбирает BASE ради доступности и масштабирования.

## Ответ

### 1. B-tree индекс и `BETWEEN`

B-tree хранит ключи в отсортированном виде. Для условия:

```sql
WHERE created_at BETWEEN '2026-01-01' AND '2026-01-31'
```

База:
1. быстро находит начало диапазона в дереве за $O(\log n)$;
2. последовательно проходит листья индекса до конца диапазона;
3. читает только подходящие строки или ссылки на строки.

Hash-index хорош для equality lookup (`id = 42`), но плохо подходит для диапазонов, потому что hash не сохраняет порядок ключей.

### 2. Read Committed vs Serializable

**Read Committed**: транзакция видит только committed данные. Но два одинаковых SELECT внутри одной транзакции могут увидеть разные результаты, если другая транзакция успела закоммитить изменения.

Не защищает полностью от:
- non-repeatable read;
- phantom read;
- write skew.

**Serializable**: результат должен быть таким, как будто транзакции выполнились последовательно в некотором порядке. Это самый строгий уровень изоляции.

Цена:
- больше блокировок или конфликтов;
- возможны abort/retry;
- ниже throughput.

### 3. `ROW_NUMBER()`

`ROW_NUMBER()` нумерует строки внутри окна.

```sql
WITH ranked AS (
  SELECT
    user_id,
    order_id,
    created_at,
    ROW_NUMBER() OVER (
      PARTITION BY user_id
      ORDER BY created_at DESC
    ) AS rn
  FROM orders
)
SELECT *
FROM ranked
WHERE rn = 1;
```

Так можно оставить последнюю запись по каждому пользователю.

### 4. JSON vs JSONB в PostgreSQL

`JSON` хранит исходный текст JSON. Он сохраняет форматирование и порядок ключей, но каждый запрос требует парсинга.

`JSONB` хранит разобранное бинарное представление:
- быстрее поиск по полям;
- можно индексировать GIN-индексами;
- ключи нормализуются;
- порядок ключей и форматирование не сохраняются.

Когда `JSON` может быть лучше:
- нужно сохранить исходный текст как был;
- данные почти не запрашиваются по внутренним полям;
- важен порядок/дубликаты ключей в исходном документе.

### 5. Lazy loading в ORM

Lazy loading — связанная сущность загружается не сразу, а при первом обращении.

Проблема N+1:

```python
users = session.query(User).all()  # 1 query
for user in users:
    print(user.orders)             # N дополнительных queries
```

На маленьких данных незаметно, на production может превратиться в сотни/тысячи запросов.

Решения:
- eager loading (`joinedload`, `selectinload`);
- явные joins;
- batch loading;
- профилирование SQL.

### 6. BASE в NoSQL

BASE:
- Basically Available;
- Soft state;
- Eventual consistency.

NoSQL-системы часто выбирают BASE, когда важнее:
- горизонтальное масштабирование;
- высокая доступность;
- устойчивость к сетевым partition;
- низкая latency.

Компромисс: данные могут временно быть несогласованными, но со временем сходятся.

Связь с CAP: при сетевом разделении распределённая система выбирает между consistency и availability. Многие NoSQL-системы отдают приоритет availability и eventual consistency.

## Формула / Схема

**Упрощённая стоимость range scan по B-tree:**

$$\Large O(\log n + k)$$

где:
- $n$ — число ключей в индексе;
- $k$ — число найденных строк диапазона;
- $\log n$ — найти начало диапазона;
- $k$ — пройти подходящие элементы.

**Порядок работы `ROW_NUMBER`:**

```text
PARTITION BY -> делит строки на группы
ORDER BY -> задаёт порядок внутри группы
ROW_NUMBER -> выдаёт 1, 2, 3...
```

## Короткий пример

Если таблица заказов имеет индекс `(user_id, created_at)`, запрос "последний заказ пользователя" может быстро найти нужный диапазон по `user_id` и порядок по `created_at`. Но если фильтр оборачивает колонку в функцию, индекс может не использоваться без functional index.

## Типичные ошибки

- **Ожидать, что индекс ускорит любой запрос:** низкая селективность или функция над колонкой могут помешать.
- **Использовать lazy loading в цикле:** классическая N+1 проблема.
- **Путать JSONB с обычным JSON:** JSONB быстрее для запросов, но не сохраняет исходное форматирование.
- **Считать Serializable бесплатным:** строгая изоляция может приводить к retry и снижению throughput.
- **Думать, что BASE значит "без гарантий":** гарантии есть, но они другие: availability и eventual consistency вместо строгой немедленной согласованности.

## Каверзные вопросы

> [!question] Почему `ROW_NUMBER()` нельзя использовать напрямую в `WHERE` того же SELECT?
> Логически `WHERE` выполняется раньше оконных функций. Нужно использовать CTE/подзапрос и фильтровать `rn` снаружи.

> [!question] Почему B-tree подходит для `BETWEEN`, а hash-index нет?
> B-tree сохраняет порядок ключей и поддерживает range scan. Hash распределяет ключи псевдослучайно и порядок не хранит.
