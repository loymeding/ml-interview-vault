# Оценка VLM — зрительное восприятие, multi-image, reasoning и tool use

> [!abstract] Суть
> VLM оценивают не одной метрикой «правильно ответила на вопрос по картинке». Нужно отделить зрительное восприятие от рассуждения, работу с несколькими изображениями от запоминания одного, выбор инструмента от интерпретации результата. Иначе невозможно понять, где модель действительно выросла и какие данные нужны для следующей версии.

> [!tip] VLM — это «зрение плюс язык», и ошибки бывают на разных этажах
> **VLM (Vision-Language Model)** получает одновременно изображение и текст. **OCR** — распознавание текста на картинке. **Multi-image** — задача, где нужно сопоставить несколько изображений. **Reasoning** — рассуждение на основе уже воспринятых данных. Если модель неверно прочитала цену на чеке, ошибка произошла в зрении/OCR; если прочитала цену верно, но неправильно сложила суммы — это ошибка рассуждения. Лечить их одними и теми же данными бессмысленно.

> [!example] Декомпозиция, которая помогает выбрать улучшение
> На вопросе по двум фотографиям товара модель может: не заметить вторую фотографию; заметить обе, но перепутать объекты; всё увидеть, но выбрать неподходящий товар; выбрать верный товар, но вызвать неправильный инструмент. Каждая ветка требует своего решения: больше multi-image данных, явный формат сравнения, обучение рассуждению или ограничение схемы вызова API.

## 1. Что такое задача для модели со зрением и языком

VLM (Vision-Language Model) получает текст, одно или несколько изображений, иногда файлы и результаты инструментов, затем отвечает или действует. Возможные навыки:

- распознать объекты, текст и атрибуты;
- понять пространственные отношения;
- сравнить два или больше изображений;
- найти отличие до/после редактирования;
- объяснить график, схему или документ;
- выполнить многошаговое визуальное рассуждение;
- решить, нужен ли web search, OCR, crop или другой tool;
- использовать результат инструмента в финальном ответе.

Вопрос «какой цвет у машины?» проверяет восприятие. «На каком из трёх фото тот же предмет после редактирования и соответствует ли результат инструкции?» уже проверяет multi-image matching, память, следование инструкции и reasoning.

## 2. Декомпозиция ошибок VLM

| Уровень | Пример ошибки |
|---|---|
| Восприятие | Не увидела объект или прочитала не тот текст |
| OCR | Перепутала цифру, дату, знак или язык |
| Связывание изображений | Взяла деталь с первого изображения и отнесла ко второму |
| Пространственное рассуждение | Неверно поняла «слева от», «перед», «выше» |
| Логическое рассуждение | Визуальные факты верны, но вывод неверен |
| Следование инструкции | Не использовала все картинки или пропустила условие |
| Tool selection | Не вызвала OCR/поиск, когда без него нельзя ответить |
| Tool interpretation | Вызвала tool правильно, но неверно прочитала ответ |
| Формат/безопасность | Выдала неподходящий формат или уверенно придумала деталь |

Таксономия особенно важна в multi-image. Иначе «ошибка VLM» не говорит, нужны ли данные на восприятие, reasoning или tool use.

## 3. Как спроектировать набор задач для VLM

Карта покрытия VLM должна содержать:

- число изображений: 1, 2, 3+;
- тип визуального материала: фото, схема, график, документ, экран приложения;
- качество: чёткое, размытое, частично закрытое, мелкий текст;
- вид задачи: описание, сравнение, подсчёт, последовательность, поиск различий;
- наличие инструмента и его необходимость;
- язык текста на изображении;
- сложность рассуждения;
- риск: безопасный вопрос, деньги, privacy, вредный контент;
- отрицательные примеры: нужная информация отсутствует.

Набор должен включать вопросы, на которые **нельзя** честно ответить по изображению. Это проверяет способность модели сказать «не вижу достаточно данных», а не галлюцинировать.

## 4. Как проверить, что модель действительно использовала все изображения

Это отдельный challenge. Модель может ответить правильно, глядя только на первую картинку.

Подходы:

- контрафактуальные пары: заменить второе изображение так, чтобы правильный ответ изменился;
- swap test: поменять порядок изображений и проверить, меняется ли ссылка на них корректно;
- задания, где ответ невозможен без объединения фактов с разных картинок;
- указание на конкретные области/цитирование evidence;
- human audit траекторий рассуждения, не полагаясь на chain-of-thought как на истину.

Пример: пользователь просит выбрать фото, на котором объект изменён согласно референсу. В позитивном варианте референс совпадает, в контрафактуальном — отличается цвет. Если ответ не меняется, модель, вероятно, не использует референс.

## 5. Метрики

### Для задач с однозначным ответом

- accuracy;
- exact match после нормализации;
- F1 для нескольких объектов;
- OCR character/word error rate;
- IoU/grounding accuracy, если нужно указать область на изображении.

### Для рассуждений и открытых ответов

- human/judge correctness по rubric;
- полнота обязательных визуальных фактов;
- unsupported visual claim rate — доля утверждений, которых нет на изображении;
- качество отказа;
- pairwise preference.

### Для агентов, которые вызывают инструменты

- task success;
- верный выбор визуального инструмента;
- валидность tool arguments: crop, zoom, OCR region;
- success после tool call;
- число шагов, latency и cost;
- safety violations.

Показывайте macro-score по типам задач и worst-slice. Средняя accuracy может скрыть провал на мелком тексте или multi-image.

## 6. Роль публичных бенчмарков

Open-source наборы полезны для внешнего сравнения и идей, но не заменяют продуктовый benchmark. Проверяем:

- язык и культурный контекст;
- наличие multi-image и tools;
- реалистичность задач;
- качество labels;
- contamination;
- тип метрики;
- соответствие рискам Алисы.

Если public benchmark измеряет академические задачи по одной картинке, он мало говорит о том, справится ли Алиса с пользовательским запросом «сравни эти фото, найди похожий товар, проверь через поиск и объясни различия».

## 7. Пример VLM-agent case

Задача: «По двум фото комнаты и референсу подбери цвет штор, который подходит к интерьеру, найди варианты в каталоге и покажи три».

Проверяем:

1. Модель использовала обе фотографии и референс.
2. Верно извлекла важные визуальные признаки: палитра, освещение, стиль.
3. Если нужна фактическая доступность товара, вызвала каталог.
4. Не придумала свойства товара.
5. Предложила варианты, а не совершила покупку.
6. Объяснение связано с визуальными фактами и данными каталога.

Метрика «похоже на красивый ответ» не годится. Нужны визуальная корректность, каталожная корректность, соблюдение ограничений и user preference.

## 8. Данные для улучшения VLM

Если ошибка в восприятии — нужны разнообразные изображения, OCR, quality augmentation. Если в multi-image связывании — примеры с обязательным использованием разных источников и контрафактуальные пары. Если в tool use — траектории «увидел неопределённость → вызвал нужный инструмент → использовал результат».

После добавления данных проверяем target slice и broad VLM benchmark, чтобы не улучшить multi-image ценой деградации обычного OCR.

## 9. Типичные ошибки

- Считать VQA accuracy полной оценкой VLM.
- Не иметь no-answer и adversarial изображения.
- Не проверять, использовала ли модель все входы.
- Смешивать зрительную ошибку с логической.
- Давать модели tool output, который содержит скрытый ответ.
- Оценивать только публичный benchmark.
- Не учитывать стоимость и latency multi-image контекста.
