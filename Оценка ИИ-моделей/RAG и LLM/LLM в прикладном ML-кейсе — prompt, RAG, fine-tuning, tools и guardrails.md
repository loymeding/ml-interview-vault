# LLM в прикладном ML-кейсе — prompt, RAG, fine-tuning, tools и guardrails

> [!abstract] Суть
> На ML-интервью редко нужно доказать, что вы знаете название самой большой модели. Нужно выбрать способ улучшения под задачу: достаточно ли хорошего prompt, нужен ли поиск по внешним знаниям, стоит ли дообучать модель, нужны ли инструменты и как ограничить опасные действия.

## 1. Четыре разных способа улучшить систему

### Prompt engineering — инструкция модели

Меняем system prompt, формат ответа, примеры и правила отказа. Это самый быстрый путь для поведения, которое уже поддерживается моделью: тон, структура, обязательные поля, порядок действий. Минус — prompt может стать длинным и хрупким, а новые знания он не добавляет.

### RAG — поиск знаний во время запроса

Подходит для свежих или приватных документов, которые не хочется зашивать в веса модели. Данные обновляются через индекс, а ответ можно связать с источником. Нужны отдельная оценка retrieval и защита прав доступа.

### Fine-tuning — дообучение

Меняет поведение и стиль модели на наборе примеров. Полезно, когда много однотипных задач, нужен устойчивый формат или специальный язык. Это дороже в данных и вычислениях, может вызвать регрессии и не гарантирует свежесть фактов.

### Tools — внешние инструменты

Калькулятор, поиск, база товаров, OCR или API позволяют не просить LLM «угадывать». Но нужно оценивать не только текст, а выбор инструмента, аргументы, ошибки API, права и безопасность побочных действий.

## 2. Как выбрать подход на интервью

| Симптом задачи | Первое решение |
|---|---|
| Нужен другой стиль/формат | prompt + structured output |
| Нужны свежие внутренние факты | RAG |
| Много повторяющихся примеров и особый формат | fine-tuning |
| Нужен расчёт, поиск или изменение состояния | tool use |
| Есть несколько причин одновременно | каскад: prompt + RAG + tools, затем fine-tuning при наличии данных |

Важно назвать критерий остановки. Если prompt и RAG уже дают достаточное качество, fine-tuning может только увеличить стоимость и риск регрессий.

## 3. Модель и inference

Выбираю модель по тестам на собственном наборе, а не по общему leaderboard:

- качество на русском и нужном домене;
- следование инструкции и structured output;
- работа с длинным контекстом;
- tool calling;
- latency p95 и пропускная способность;
- цена токена и инфраструктуры;
- требования к приватности и размещению.

Если сервис должен отвечать быстро, можно сделать каскад: маленькая модель решает простые запросы, большая — только трудные. Если ответ критичен, добавляю проверку схемы, источников, арифметики и права на действие.

## 4. Оценка LLM-системы

Сначала формирую карту навыков: полезность, фактологичность, следование инструкции, корректный отказ, tool use, безопасность. Для каждого навыка — задачи с эталоном или rubric. Pairwise human evaluation и LLM-as-a-judge помогают сравнивать открытые ответы, но judge калибрую на свежей человеческой выборке.

Для LLM не забываю про:

- variance от temperature и seed;
- contamination тестового набора;
- промпт-инъекции из пользовательского текста или документов;
- конфликт источников;
- длинные диалоги и накопление ошибки;
- цену и задержку при нескольких вызовах.

## 5. Guardrails и безопасность

Guardrail — ограничение, которое не даёт системе сделать опасное действие. Примеры:

- read-only режим по умолчанию;
- явное подтверждение перед оплатой или удалением;
- whitelist доступных tools;
- JSON schema и валидация аргументов;
- маскирование персональных данных;
- лимит числа шагов и бюджета;
- fallback на человека или старую модель.

Guardrails проверяются отдельно и могут быть hard gate: высокий общий score не компенсирует действие без согласия пользователя.

## 6. Вопросы интервьюера

- Почему не решить задачу обычной классификацией?
- Что выбрать: RAG или fine-tuning?
- Как понять, что LLM действительно использовала источник?
- Как ограничить вызов API?
- Что делать, если ответ стал лучше, но в два раза дороже?
- Как тестировать prompt-инъекцию в документе?

## Эталонная формулировка

> «Сначала разделю, что нужно изменить: поведение, знания или действие. Для поведения начну с prompt, для свежих знаний — с RAG, для точного расчёта/изменения состояния — с tools, а fine-tuning добавлю только при устойчивом наборе примеров и доказанной пользе. Модель сравню на собственных задачах по качеству, tool use, latency и стоимости. Критичные действия ограничу схемой аргументов, правами, подтверждением пользователя и fallback; затем проверю offline, shadow и A/B».
