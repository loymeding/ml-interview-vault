# Пайплайн генерации данных для LLM и агентов — от задания до версии датасета

> [!abstract] Суть
> Масштабируемый пайплайн данных — это не «попросить сильную модель сгенерировать миллион примеров». Он должен создавать нужные сценарии, проверять их корректность и сложность, удалять дубликаты, сохранять происхождение каждого примера и замыкать обратную связь от ошибок модели к следующей версии датасета.

> [!tip] Пайплайн — это конвейер с проверками, а не одна генерация
> **Пайплайн (pipeline)** — последовательность воспроизводимых шагов: создать задания, получить эталоны, отфильтровать брак, проверить выборку, присвоить версию. **Происхождение примера (provenance)** — запись, откуда он взялся: из лога, от эксперта или от другой модели, какой промпт и фильтр к нему применили. **Аудит (audit)** — выборочная независимая проверка уже принятых данных. Эти записи нужны не для бюрократии: без них нельзя понять, почему новая версия датасета улучшила или ухудшила модель.

> [!example] Где здесь принимается решение
> Сильная модель может написать правдоподобный, но ложный эталон для юридического вопроса. Поэтому генератор не должен быть последней инстанцией: для числовой задачи можно выполнить кодовую проверку, для вызова API — проверить финальное состояние среды, для риска — отправить небольшой, но важный срез эксперту. Чем выше цена ошибки, тем меньше полагаемся на автоматическую генерацию.

## 1. Из чего состоит хороший конвейер данных

```text
карта навыков и целевых ошибок
→ генерация задания / выбор из логов
→ создание контекста или среды
→ генерация ответа / траектории
→ автоматическая валидация
→ judge и human audit
→ фильтрация, дедупликация, балансировка
→ версия датасета и документация
→ обучение и eval
→ error analysis
→ новая итерация генерации
```

У каждого шага есть собственные метрики. Нельзя проверить качество в конце одной общей метрикой: плохие задания, неверные эталоны и дубликаты уже могли испортить обучение.

## 2. Генерация заданий

Задания могут прийти из реальных логов, от экспертов или синтетического генератора. Для агента полезно генерировать не только текст, но и состояние среды:

```text
цель: «закажи продукты на ужин до 2 000 ₽»
пользователь: аллергия на орехи, адрес, предпочтения
каталог: доступность, цены, слоты доставки
ограничения: нельзя подтверждать заказ без согласия
```

Генератор должен контролировать оси сложности: число ограничений, конфликт условий, редкость товара, число нужных tools, наличие ошибки API, необходимость уточнения.

## 3. Генерация эталона

Для простого вопроса эталоном может быть ответ. Для агента — траектория или правило проверки финального состояния.

Источники эталона:

- эксперт;
- реальный успешный trace;
- сильная teacher-модель;
- поиск/планировщик;
- комбинация нескольких кандидатов с последующим judge/human review.

Teacher output не считается автоматически правильным. Он должен пройти schema validation, tool execution, constraint checker и выборочную человеческую проверку.

## 4. Автоматические проверки

До дорогой разметки отсеиваем очевидный мусор:

- невалидный JSON;
- неисполняемый tool call;
- финальное состояние не достигнуто;
- противоречие ограничениям;
- пустой или слишком короткий ответ;
- дубликат;
- PII/секрет;
- запрещённый контент;
- устаревшая версия API или документа.

Для agent tasks самый сильный автоматический сигнал — исполнение траектории в среде. Если она не добавляет нужный товар в корзину, красивое объяснение не спасает пример.

## 5. Автоматический оценщик и человеческая проверка выборки

Judge помогает оценить качество, сложность и разнообразие, но выборка обязательно проверяется людьми. Полезно выбирать для аудита не только случайные примеры, но и:

- высокий judge confidence;
- низкий confidence;
- расхождение двух judge;
- редкие сценарии;
- expensive/high-risk actions;
- новые генераторы и шаблоны.

Так можно обнаружить systematic failure, который не виден в среднем.

## 6. Балансировка и версии

После фильтрации датасет обычно перекошен в сторону простых успешных задач. Нужно явно задать target distribution по навыкам, сложности, языкам и риску.

Каждый пример хранит:

- `dataset_version`;
- `source` и генератор;
- `prompt_version`;
- дату;
- tags сценария и сложности;
- результат автоматических проверок;
- judge/human labels;
- лицензию и ограничения на использование.

Версия датасета — это манифест, по которому можно собрать тот же набор. Без него невозможно объяснить, почему новая модель изменилась.

## 7. Пример: данные для VLM-агента

Нужно научить модель редактировать изображение по инструкции с несколькими референсами.

Pipeline:

1. Генерируем задачу: входное изображение, референс, инструкция, ограничения на сохранение объекта.
2. Формируем tool environment: поиск референса, генерация, редактирование, VLM-проверка.
3. Teacher строит траекторию действий.
4. Проверяем, что изображение реально создано и соответствует техническим ограничениям.
5. VLM-judge оценивает instruction following, а human sample проверяет идентичность и артефакты.
6. Отбрасываем повторяющиеся или слишком лёгкие примеры.
7. Помечаем сложность: одно изображение/multi-image, число шагов, тип редактирования.
8. После обучения смотрим targeted benchmark и собираем новые ошибки для следующей итерации.

## 8. Типичные ошибки

- Генерировать данные без карты навыков.
- Давать генератору и judge’у один и тот же blind spot.
- Проверять только финальный текст, а не исполнимость траектории.
- Не хранить происхождение примера.
- Удалять «странные» редкие примеры, хотя это важный product slice.
- Не контролировать повторение шаблонов.
- Использовать output pipeline и как train, и как единственный eval.
