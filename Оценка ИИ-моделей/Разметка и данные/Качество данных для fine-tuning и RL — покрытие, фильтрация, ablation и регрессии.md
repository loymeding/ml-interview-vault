# Качество данных для fine-tuning и RL — покрытие, фильтрация, ablation и регрессии

> [!abstract] Суть
> Датасет — не просто количество примеров. Для обучения модели важны покрытие нужных навыков, корректность, сложность, разнообразие, отсутствие утечек и связь с конкретной ошибкой. Чтобы доказать пользу новых данных, нужно сравнить сопоставимые обучения и измерить не только целевой рост, но и регрессии.

> [!tip] Необязательно запоминать англоязычные названия — важна логика
> **Fine-tuning** — дообучение уже готовой модели на нужных примерах. **RL** — обучение с подкреплением, когда модель получает оценку результата, а не только готовый правильный ответ. **Ablation** — честный опыт «убрали один компонент и посмотрели, исчезло ли улучшение». **Data mixture** — состав смеси данных для обучения. Вопрос этой карточки простой: *какие именно примеры добавить, чтобы исправить наблюдаемую проблему и не сломать соседние навыки?*

> [!example] Практическая развилка
> Если агент путает аргументы инструмента поиска, не надо автоматически заливать в обучение миллион обычных диалогов. Сначала проверяем, что ошибка правда в понимании параметров, затем добавляем разнообразные правильные примеры именно этого вызова: с опечатками, неполными условиями, конфликтами фильтров. После этого сравниваем модель с этими данными и без них на *новых* задачах. Так данные становятся проверяемым лечением, а не надеждой.

## 1. Что означает «хороший датасет»

У качества данных несколько измерений:

| Измерение | Вопрос |
|---|---|
| Корректность | Верны ли ответы, действия и reward? |
| Покрытие | Есть ли все важные навыки и срезы? |
| Разнообразие | Не повторяем ли один шаблон тысячами формулировок? |
| Сложность | Есть ли простые, средние и сложные случаи? |
| Релевантность | Похожи ли данные на будущие продуктовые задачи? |
| Безопасность | Нет ли вредных/запрещённых паттернов? |
| Чистота | Убраны ли дубликаты, leakage, сломанные форматы? |
| Версионирование | Можно ли воспроизвести точный состав обучения? |

Большой synthetic dataset может быть грамматически красивым, но не содержать реальных конфликтов условий, ошибок API и неоднозначных запросов. Такой объём создаёт ложное ощущение покрытия.

## 2. От ошибки к данным

Нельзя собирать «ещё 100 000 примеров» без механизма. Начинаем с error taxonomy.

Пример:

> Агент теряет условие «доставка завтра», когда запрос содержит ещё бюджет и рейтинг.

Гипотеза: в данных мало задач с тремя и более ограничениями и проверкой каждого ограничения после tool call.

Новый набор должен содержать:

- разные формулировки ограничения;
- несколько конфликтующих фильтров;
- доступный и недоступный товар;
- правильное уточнение, когда условие невозможно;
- tool traces;
- негативные примеры нарушений;
- критерий успеха по каждому условию.

## 3. Фильтрация и дедупликация

Пайплайн качества обычно включает:

```text
сбор/генерация
→ schema validation
→ дедупликация по тексту и смыслу
→ safety/privacy filter
→ проверка answer/trajectory
→ оценка сложности и diversity
→ human/judge audit
→ версия датасета
```

Дедупликация важна не только для экономии. Тысяча почти одинаковых задач может переобучить модель на шаблон и завысить ощущение прогресса. Проверяют точные дубликаты, n-gram overlap, embedding similarity и повторение траекторий.

## 4. Смесь обучающих данных: почему нельзя добавить только новый тип примеров

В общем обучении смешиваются разные источники: диалоги, инструкции, tool-use, reasoning, safety, мультимодальные примеры. Если резко увеличить целевой срез, можно получить catastrophic forgetting — модель улучшится на нём, но забудет соседние навыки.

Поэтому нужно контролировать:

- долю каждого источника;
- качество и сложность источника;
- повторение примеров;
- языковой и доменный баланс;
- вероятность показа примера при обучении;
- влияние смеси на broad benchmark.

## 5. Как доказать, что улучшение дали именно новые данные

Минимальный корректный эксперимент:

1. Фиксируем baseline-модель, обучение, hyperparameters и evaluation protocol.
2. Формируем новую версию датасета с понятным отличием.
3. Обучаем candidate в сопоставимых условиях.
4. Проверяем target benchmark и broad regression suite.
5. Сравниваем версии статистически и по срезам.
6. Делаем ablation: убираем спорный источник или сравниваем несколько долей данных.
7. Смотрим стоимость — сколько разметки/compute потребовалось на единицу эффекта.

Ablation — это проверка вклада компонента. Если добавили и новые траектории, и новый prompt, и новую модель, нельзя честно сказать, что помогли именно данные.

## 6. Метрики качества данных

- coverage по карте навыков;
- доля задач с экспертной/человеческой проверкой;
- agreement разметчиков;
- доля невалидных/дубликатов;
- распределение сложности и длины;
- diversity кластеров;
- доля редких critical scenarios;
- contamination risk;
- proportion правильных траекторий;
- reward consistency;
- model gain per 1 000 примеров или рубль разметки.

Последняя метрика не должна вести к отбору только лёгких примеров. Иногда дорогие экспертные задачи необходимы для safety-gate.

## 7. Регрессии

После добавления данных нужно проверить:

- общую полезность;
- соседние навыки;
- безопасность;
- multilingual;
- формат и tool use;
- latency/cost, если модель изменилась;
- старые incident/regression sets.

Если target slice вырос с 40% до 70%, а базовое следование инструкции упало с 95% до 86%, решение зависит от важности обоих сценариев. Нужна явная политика, а не усреднение score.

## 8. Типичные ошибки

- Мерить качество датасета только числом строк.
- Добавлять данные без гипотезы о причине ошибки.
- Оценивать на данных, близких к обучающим.
- Не хранить версию и происхождение примера.
- Не делать ablation.
- Праздновать target gain и не смотреть broad regressions.
- Считать synthetic data автоматически дешёвой и качественной.

## Проверка себя

- Какие данные соберёте, если VLM путает два изображения в одном запросе?
- Как отличить эффект нового датасета от эффекта новой базовой модели?
- Что означает высокий coverage, но низкая diversity?
- Почему нужен holdout, который не видит команда обучения?
