# Таксономия ошибок и проблемные срезы — как находить точки роста модели

> [!abstract] Суть
> Средний score показывает, насколько модель хороша в среднем. Таксономия ошибок показывает, **почему** она ошибается и какое улучшение даст наибольшую пользу. Хорошая таксономия связывает пример ошибки, класс, тяжесть, частоту, вероятную причину и действие: данные, prompt, tool, архитектуру или продуктовую политику.

> [!tip] Таксономия — это не список красивых названий ошибок
> **Таксономия ошибок** — согласованный способ раскладывать неудачные примеры по классам. **Срез (slice)** — подгруппа задач, например «длинные документы на русском» или «заказы с ограничением бюджета». **Операциональная категория** — такая, по которой два аналитика на конкретном примере обычно примут одинаковое решение. Смысл не в том, чтобы назвать ошибку «reasoning», а в том, чтобы после разбора было понятно, что менять: данные, инструкцию, инструмент или правила продукта.

> [!example] От находки к действию
> Допустим, в 30% неудач с товарами модель выбирает правильный инструмент, но передаёт бюджет строкой «до ста тысяч» вместо числа. Это не абстрактная «слабость агента», а класс «неверное преобразование параметра». Для него можно добавить проверку формата, примеры в обучающие данные или ограничить схему вызова API. Если же модель не понимает саму цель пользователя, эти меры не помогут — нужна другая точка роста.

## 1. От «модель ошибается» к полезному анализу

Плохой отчёт: «модель ошиблась в 18% задач».

Полезный отчёт:

> «Из 18% неуспешных задач 7 п.п. приходятся на неверный выбор инструмента в сценариях с несколькими ограничениями; это высокий риск, потому что агент может выбрать неподходящий товар. Вероятная причина — недостаток траекторий с конфликтующими условиями. Рекомендуем собрать 2 000 таких задач, добавить tool-level reward и повторить targeted benchmark».

Такой вывод уже говорит команде, что делать.

## 2. Как строить таксономию

Начинаем не с 100 классов, а с 5–10 различимых верхнеуровневых категорий. Для Alice AI Agents:

| Класс | Что означает |
|---|---|
| Понимание запроса | Потеряно намерение, ограничение или контекст |
| Планирование | Неправильный порядок шагов или пропущен шаг |
| Выбор tool | Вызван не тот сервис/метод |
| Аргументы tool | Сервис выбран верно, но параметры неверны |
| Интерпретация результата | Tool ответил правильно, модель сделала ложный вывод |
| Ограничения и безопасность | Нарушен бюджет, право, согласие пользователя |
| Финальный ответ | Действия верны, но объяснение неверно/неполно |
| Формат | Невалидный JSON, неверный шаблон, нарушен контракт |
| Корректный отказ | Агент отказался, хотя мог решить, либо наоборот |

Для VLM добавятся: визуальное восприятие, OCR, multi-image связывание, пространственное рассуждение, tool use и формат. Для генерации изображений: несоответствие инструкции, потеря идентичности, артефакт, safety, плохое редактирование.

## 3. Категории должны быть проверяемыми на конкретном примере

«Плохое рассуждение» слишком широко. Лучше описать критерий:

> «Ошибка интерпретации tool output: все нужные API вызваны, но в ответе утверждается свойство, которого нет в возвращённых полях».

У каждой категории должны быть:

- определение;
- пример и контрпример;
- правило при нескольких ошибках;
- тяжесть;
- возможные действия;
- связь с benchmark tag.

Один пример может иметь первичную и вторичную ошибку. Первичная — первая ошибка в цепочке, которая привела к провалу. Это помогает не обвинять финальный текст, если причина была в неверном запросе к API.

## 4. Срезы: где искать проблему

Срез — заранее осмысленная группа задач:

- тип сценария;
- язык;
- сложность;
- число шагов;
- редкий tool;
- новый пользователь/регион;
- длина контекста;
- multi-image;
- важность/риск;
- версия данных или шаблона.

Среднее качество может расти, а critical slice падать. Например, общая успешность агента 80%, но только 42% на задачах с подтверждением оплаты. Это важнее, чем ещё +1 п.п. в простом поиске.

## 5. Приоритизация точки роста

Полезная формула для первого ранжирования:

```text
priority ≈ frequency × severity × fixability × strategic_value
```

- **frequency:** как часто ошибка встречается;
- **severity:** сколько вреда несёт;
- **fixability:** есть ли понятный рычаг улучшения;
- **strategic value:** важен ли навык для продукта сейчас.

Высокая частота не всегда побеждает. Ошибка в 0,1% финансовых задач может блокировать rollout.

## 6. Практический цикл разбора ошибок

```text
выбор репрезентативной и targeted выборки
→ разметка ошибок по таксономии
→ расчёт частоты и тяжести
→ просмотр конкретных примеров
→ гипотеза о причине
→ действие: данные / prompt / tool / policy / модель
→ новый targeted benchmark
→ повторная приёмка и проверка регрессий
```

Важно не делать вывод о причине только по названию класса. «Tool error» может происходить из-за плохого описания API, отсутствия данных, неверного планирования или prompt injection. Таксономия локализует проблему, но гипотеза причины требует проверки.

## 7. Пример: проблемный срез Алисы

В agent benchmark’е новая модель в среднем выросла с 68% до 72% task success. Error analysis показывает:

| Срез | A | B | Главная ошибка |
|---|---:|---:|---|
| Поиск одного товара | 83% | 88% | почти нет |
| Несколько фильтров | 65% | 70% | потеря одного условия |
| Недоступный товар | 61% | 74% | стало лучше с fallback |
| Подтверждение действия | 80% | 52% | действие без согласия |

Средний рост нельзя принять без оговорок. Последняя строка — high-severity регрессия. Гипотеза: RL-данные награждают завершение задачи, но недостаточно штрафуют необратимое действие без согласия. Проверка: targeted set с явным/неявным согласием и анализ reward. Исправление: добавить constraint-checker и данные с правильным уточняющим вопросом.

## 8. Типичные ошибки

- Делать таксономию после того, как уже выбран «виновник».
- Смешивать причину и симптом в одном классе.
- Смотреть только доли ошибок без числа задач.
- Игнорировать редкие high-severity случаи.
- Делать сотни post hoc срезов и верить случайному провалу.
- Не связывать класс ошибки с действием команды.
- Проверять улучшение только общим benchmark’ом.

## Проверка себя

- Как отличить ошибку планирования от ошибки tool arguments?
- Какой срез добавите для VLM с несколькими изображениями?
- Почему первичная ошибка полезнее последней видимой ошибки?
- Как доказать, что новый датасет исправил именно нужный класс?
