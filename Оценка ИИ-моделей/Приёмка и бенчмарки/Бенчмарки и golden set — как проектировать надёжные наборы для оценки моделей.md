# Бенчмарки и golden set — как проектировать надёжные наборы для оценки моделей

> [!abstract] Суть
> Benchmark — это не просто файл с вопросами и ответами. Это измерительный инструмент, который должен представлять важные пользовательские задачи, иметь понятный эталон, быть защищённым от утечки в обучение и позволять повторить сравнение моделей. Golden set — особенно тщательно проверенная часть такого инструмента, на которой принимают важные решения.

> [!tip] Сначала переведём термины
> **Бенчмарк (benchmark)** — «экзамен» для модели: не только задания, но и правила проверки, метрики и условия запуска. **Эталонный набор (golden set)** — его наиболее надёжная часть, где примеры и оценки вручную перепроверены. **Регрессия (regression)** — возвращение уже исправленной ошибки. Держите в голове простую мысль: мы создаём не датасет «для красоты», а измерительный прибор. У прибора должны быть известны границы применимости и погрешность. Более полный перевод остальных слов — в [[🧾 Словарь терминов — LLM, VLM, агенты и оценка]].

> [!example] Как это выглядит в решении
> Если команда говорит: «Новая версия прошла 80% benchmark’а», первая профессиональная реакция — не радоваться числу, а уточнить: *80% каких пользовательских задач, относительно какого эталона и не научилась ли модель именно этим примерам?* Ответы на эти вопросы определяют, можно ли выпускать модель, а не само круглое число.

## 1. Почему случайных логов недостаточно

Если взять 10 000 случайных запросов Алисы, получатся частые простые вопросы. Они полезны для оценки общего трафика, но могут не содержать:

- сложные многошаговые задачи;
- редкие, но опасные сценарии;
- новый продуктовый навык;
- запросы с несколькими ограничениями;
- вопросы без правильного ответа;
- edge cases — пограничные случаи;
- важные языки, регионы и устройства.

Модель может получить высокий средний score и быть бесполезной в задачах, ради которых её обучали. Поэтому benchmark проектируют от **карты пользовательских сценариев**, а не от того, что случайно есть в логах.

## 2. Бенчмарк, тестовый и эталонный наборы

| Понятие | Простое значение |
|---|---|
| Test set | Набор примеров, на котором измеряют модель |
| Benchmark | Test set + правила задачи + метрики + протокол запуска + интерпретация |
| Golden set | Наиболее надёжная, вручную проверенная часть benchmark’а с качественными эталонами |
| Holdout | Закрытая часть набора, которую не используют для ежедневной оптимизации |
| Regression set | Набор известных ошибок, который должен проверяться при каждом релизе |

Golden set не обязан быть огромным. Лучше 500 тщательно выверенных сложных задач с хорошим rubric, чем 50 000 примеров с сомнительными labels.

## 3. Сначала определяем измеряемый навык

До сбора заданий нужно ответить:

> Какое свойство модели мы называем «качеством» в этом сценарии?

Например, «агент умеет заказать продукты» — слишком широко. Разделим:

- понял ли пользовательскую цель;
- учёл ли ограничения: бюджет, аллергии, доставка;
- выбрал ли правильные API;
- передал ли корректные аргументы;
- не совершил ли необратимое действие без подтверждения;
- достиг ли финального состояния корзины;
- объяснил ли выбор;
- корректно ли отказался, если задача невыполнима.

Это обычно называют **валидностью измерения (construct validity)**: бенчмарк действительно измеряет нужный навык, а не удобную, но бесполезную замену. Если считать только «ответ содержит название товара», мы не измерим способность выполнить заказ. На практике перед сбором задач стоит выписать одно предложение вида: «считаем, что система справилась, когда …». Оно защищает команду от метрики, которую легко улучшить, но которая не означает успех для пользователя.

## 4. Карта покрытия

Создаём матрицу сценариев. Для агента Маркета:

| Ось | Примеры значений |
|---|---|
| Тип цели | поиск, сравнение, покупка, возврат |
| Сложность | один фильтр, несколько ограничений, конфликт условий |
| Доступность | товар есть, нет в наличии, доставка недоступна |
| Данные | точный артикул, разговорный запрос, опечатка |
| Риск | безопасный совет, платёж, юридическое ограничение |
| Пользователь | новый, постоянный, разные регионы |
| Инструменты | один API, последовательность API, ошибочный API |

Не нужно заполнять все возможные ячейки равномерно. Приоритет задают частота, ценность и цена ошибки. Например, редкая ошибка списания денег важнее тысячи вариаций приветствия.

## 5. Единица задания

Для обычной LLM задачей может быть `prompt → answer`. Для VLM — `изображения + инструкция → ответ`. Для агента этого мало:

```text
начальное состояние среды
+ запрос пользователя
→ последовательность действий
→ финальное состояние
+ ограничения и допустимые действия
```

Нужно явно хранить:

- идентификатор задачи и версию;
- сам запрос;
- контекст, изображения или файлы;
- права пользователя;
- дату, на которую актуальны данные;
- ожидаемый итог или rubric;
- допустимые альтернативные решения;
- уровень сложности и риск;
- срезы для отчёта.

## 6. Эталон: один правильный ответ бывает не всегда

Для арифметики можно хранить точный ответ. Для открытого вопроса полезнее rubric: обязательные факты, недопустимые ошибки, допустимые варианты стиля.

Для агента может существовать несколько корректных траекторий. Поэтому не стоит требовать побайтного совпадения с единственным эталонным путём. Проверяем:

- достигнуто ли целевое состояние;
- соблюдены ли ограничения;
- не выполнено ли запрещённое действие;
- разумно ли число шагов;
- были ли необязательные, но безопасные отклонения.

Golden trajectory — хороший пример пути, а не всегда единственная правда.

## 7. Как собирать задания

Источники можно комбинировать:

- реальные логи с деидентификацией;
- задачи, созданные экспертами;
- краудсорсинговые варианты формулировок;
- синтетическая генерация с последующей проверкой;
- найденные инциденты и прошлые ошибки;
- открытые benchmark’и после критической проверки.

Каждый источник вносит bias. Логи показывают реальность, но могут повторять старую модель и не включать будущие функции. Эксперты покрывают риск, но иногда пишут неестественные запросы. Синтетика масштабируется, но может быть слишком «школьной» и похожей на генератор.

## 8. Версии, повторяемость и утечка тестовых данных

У benchmark’а должны версионироваться:

- сами задания;
- rubric и labels;
- среда и API snapshots;
- генератор/системный prompt;
- judge-модель и её prompt;
- код агрегации метрик;
- дата запуска и seed.

**Утечка тестовых данных (leakage)** — попадание информации из будущего или теста в обучение/настройку. Для LLM добавляется **загрязнение теста (contamination)**: тестовый вопрос или очень похожий пример мог попасть в предварительное обучение, дообучение или настройку промпта. В такой ситуации модель получает высокий балл не потому, что освоила навык, а потому, что уже встречала ответ.

Защиты:

- разделение train/dev/test до генерации данных;
- дедупликация по тексту и смысловой близости;
- закрытый holdout;
- свежие задания после cutoff модели;
- шаблоны и перефразированные варианты;
- отслеживание происхождения примера;
- запрет оптимизировать на hidden test;
- периодическое обновление benchmark’а.

Нельзя полностью доказать отсутствие contamination в большой базовой модели, но можно уменьшить риск и честно описать ограничения.

## 9. Размер набора: зачем нужны разные «экзамены»

Количество задач определяется не желанием получить «круглую тысячу», а вариативностью, желаемой точностью и важностью срезов. Если нужно отдельно принять модель по 20 сценариям, в каждом должно быть достаточно задач для уверенного вывода.

Полезно разделить набор:

- smoke set — несколько десятков быстрых проверок каждого commit;
- regression set — известные ошибки и критичные случаи;
- dev set — для ежедневной работы команды;
- acceptance set — для решения о релизе;
- hidden holdout — для честной финальной оценки;
- online-like sample — свежие реальные запросы.

## 10. Пример: benchmark для Алисы-путешественника

Пользователь просит спланировать поездку с бюджетом, датами, визовыми ограничениями и интересами. Что попадёт в набор?

| Сценарий | Что проверяем |
|---|---|
| Обычный запрос | Понимание цели и полезный план |
| Противоречивые условия | Уточняющий вопрос вместо выдумки |
| Нет билетов | Корректный fallback и альтернативы |
| Изменение цены | Использование свежего инструмента |
| Несколько городов | Планирование и последовательность действий |
| Ограничение по визе | Безопасность и фактологическая аккуратность |
| Запрос с фото | VLM и связь визуального контекста с планом |
| Не хватает данных | Честный отказ или запрос уточнения |

Эталоном будет не один текст маршрута, а проверка ограничений, tool calls, ссылок на данные и итоговой полезности.

## 11. Как понять, что бенчмарк действительно полезен

Признаки хорошего benchmark’а:

- изменение score связано с заметными изменениями в ручном разборе ошибок;
- набор ловит известные регрессии;
- важные срезы не скрыты средним;
- разные оценщики понимают rubric похоже;
- модель нельзя «выучить наизусть» простым prompt-tuning;
- результаты достаточно стабильны между запусками;
- offline score имеет хотя бы частичную связь с online outcome.

Если benchmark показывает постоянный рост, а пользователи не замечают улучшения, вероятно, он перестал измерять нужную ценность.

## 12. Типичные ошибки

- Называть benchmark’ом случайную выгрузку логов.
- Использовать единственную общую метрику.
- Не включать no-answer, safety и редкие критические сценарии.
- Давать единственный reference там, где корректны разные ответы.
- Проверять только public benchmark и не иметь продуктового набора.
- Позволять команде много раз подгонять модель под закрытый test.
- Не версионировать данные, rubric и среду.
- Не измерять coverage и не знать, какие сценарии отсутствуют.
