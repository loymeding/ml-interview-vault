# Платформа и процесс приёмки моделей — версии, воспроизводимость, очередь оценок и release workflow

> [!abstract] Суть
> Даже сильные метрики бесполезны, если результат нельзя повторить, команды запускают разные наборы, а решение о релизе живёт в личных сообщениях. Evaluation platform делает приёмку предсказуемым продуктом: хранит артефакты, запускает измерения, собирает human/judge оценки, считает статистику и оставляет audit trail решения.

> [!tip] Здесь не про «сложную платформу ради платформы»
> **Платформа оценки (evaluation platform)** — общий конвейер, который берёт конкретную версию системы, прогоняет её по известным заданиям и сохраняет, что именно произошло. **Воспроизводимость** означает: другой человек через месяц может повторить запуск и понять, откуда взялось число. **Release workflow** — согласованный путь изменения от заявки до решения «выпускать/не выпускать». Это защита от ситуации, когда результат есть в чьём-то ноутбуке, но его нельзя проверить.

> [!example] Минимальная полезная версия
> Не нужно сразу строить большую внутреннюю систему. Начать можно с таблицы версий, файлов с заданиями, одного запускаемого скрипта и папки с результатами. Платформа становится нужна, когда моделей, наборов и оценщиков много: ручное сопоставление перестаёт быть надёжным, а цена ошибочного релиза растёт.

## 1. Какие сущности нужно версионировать

Приёмка должна быть воспроизводима как эксперимент. Минимальные объекты:

- model artifact / endpoint;
- system prompt и decoding parameters;
- tool schemas и snapshots среды;
- benchmark, golden set и regression set;
- данные, изображения, документы и права доступа;
- judge model и rubric prompt;
- human instruction и version разметки;
- код runner и агрегации;
- метрики, thresholds и release policy;
- дата, seed, hardware/region при необходимости.

Если из этого меняется хотя бы один компонент, это новая конфигурация оценки. Нельзя сравнивать score разных benchmark/judge версий как одну временную линию без bridge run.

## 2. Архитектура: как проходит одна проверка от модели до решения

```text
model registry / candidate request
          ↓
evaluation orchestrator
          ↓
task store + benchmark versions + environment snapshots
          ↓
batch runners / agent simulators / VLM inference
          ↓
raw traces, tool logs, outputs, latency, cost
          ↓
automatic checks + LLM judges + human labeling queue
          ↓
metrics store + paired statistics + error taxonomy
          ↓
acceptance report + release gate + audit log
          ↓
staged rollout and online monitoring
```

Не нужно на интервью рисовать Kafka и Kubernetes без нужды. Важно объяснить поток данных, версии, права доступа, параллельность, fallback и аудит.

## 3. Очередь приёмки

В большой организации кандидатов много, а эксперты ограничены. Нужны SLA и риск-ориентированная очередность.

| Тип релиза | Минимальный набор |
|---|---|
| Малый prompt fix | Smoke + targeted regression + latency |
| Новый fine-tuning | Target benchmark + broad regression + judge/human sample |
| Новая базовая модель | Полная acceptance suite + safety + эксперты + rollout plan |
| Новый tool | Environment benchmark + tool safety + API/fallback checks |
| Новый VLM skill | Multimodal set + multi-image + human visual eval |

Ресурсы не распределяются поровну. High-risk релиз получает больше экспертной разметки и stricter gate.

## 4. Воспроизводимость и журнал проверки

Для каждого run сохраняем:

- `run_id`;
- все версии;
- список задач и их IDs;
- raw model outputs;
- tool traces;
- judge/human judgments;
- метрики и CI;
- список исключённых задач с причиной;
- итоговый вердикт и того, кто его утвердил.

Это позволяет ответить на вопросы через месяц: «почему релиз выпустили?», «какой набор ловил регрессию?», «на чём откалиброван judge?».

## 5. Связующая проверка между офлайном и продуктом

Если обновили benchmark, judge или инструкцию разметчика, старые и новые scores могут стать несопоставимыми. Bridge evaluation — запуск старой и новой линейки на общей фиксированной выборке. Он показывает, какое изменение score вызвано измерителем, а какое — моделью.

Без bridge команда может ошибочно подумать, что модель улучшилась, хотя просто judge стал мягче.

## 6. Роли и процесс

| Роль | Ответственность |
|---|---|
| ML-команда | Описывает изменение, предоставляет candidate и гипотезу |
| Аналитик приёмки | Проектирует замер, статистику, отчёт и риск-анализ |
| Эксперт/асессор | Проверяет rubric и сложные результаты |
| Инженер платформы | Runner, данные, версии, безопасность, масштабирование |
| Продукт/владелец риска | Утверждает trade-off и rollout policy |

Важно заранее договориться, кто имеет право сделать exception к gate. Иначе аналитик получает давление «выпусти, мы же почти прошли» без прозрачной ответственности.

## 7. Метрики самой платформы оценки

- время от candidate до заключения;
- стоимость оценки релиза;
- доля запусков, которые можно повторить;
- покрытие обязательных suites;
- доля регрессий, найденных offline до rollout;
- agreement judge/human;
- число инцидентов после «зелёной» приёмки;
- доля задач с потерянным audit trail.

Цель платформы — не максимизировать число запущенных тестов, а быстро и надёжно снижать риск плохого релиза.

## 8. Типичные ошибки

- Хранить финальный score, но не raw outputs и версии.
- Разрешать командам менять benchmark для удобного результата.
- Не разделять быстрые smoke-проверки и дорогую acceptance.
- Не иметь политики для противоречивых метрик.
- Делать human review узким bottleneck без риск-приоритизации.
- Не строить bridge при смене judge/benchmark.

## Проверка себя

- Какие артефакты нужны, чтобы повторить agent eval через три месяца?
- Как изменится процесс для нового tool и для простого prompt fix?
- Почему audit trail важен не только для дебага?
- Как определить, что judge update изменил линейку измерения?
