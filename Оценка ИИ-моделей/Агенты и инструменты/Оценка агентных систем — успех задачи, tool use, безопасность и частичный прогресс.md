# Оценка агентных систем — успех задачи, tool use, безопасность и частичный прогресс

> [!abstract] Суть
> Агент отличается от чат-бота тем, что меняет внешнее состояние через инструменты. Поэтому красивого финального ответа недостаточно. Мы оцениваем: понял ли агент цель, выбрал ли допустимые действия, корректно ли работал с API, достиг ли результата, не нарушил ли ограничения и насколько дорого ему это обошлось.

> [!tip] У агента есть итог и путь к нему
> **Task success** — успех пользовательской задачи: достигнуто ли нужное конечное состояние. **Tool use** — как агент пользуется инструментами: выбрал ли правильный, передал ли допустимые параметры, не сделал ли лишнего. **Частичный успех** означает, что полезная часть выполнена, но цель не достигнута полностью. Например, агент нашёл подходящие товары, но не задал обязательный уточняющий вопрос и поэтому не должен оформлять заказ.

> [!example] Как не дать метрике обмануть себя
> Агент может написать «Я подобрал три ноутбука» и выглядеть убедительно, хотя вызвал поиск без ограничения по цене. Поэтому проверяем не только текст, а финальную корзину, журнал действий и соблюдение правил. При этом не требуем ровно один путь: он может сначала искать, потом уточнить бюджет или наоборот — важны допустимость и результат.

## 1. Единица оценки агента

Для обычного LLM-вопроса единица часто выглядит так: `prompt → answer`.

Для агента:

```text
начальное состояние среды
+ задача пользователя
→ действия и tool calls
→ наблюдения от инструментов
→ финальное состояние
+ финальный ответ пользователю
```

Пример: «Подбери продукты для ужина до 2 000 ₽ и добавь их в корзину, но не подтверждай заказ».

Успех — не фраза «я добавил продукты», а фактическое состояние корзины: нужные товары есть, бюджет соблюдён, заказ не подтверждён.

## 2. Из чего складывается успех задачи

| Слой | Что проверяем |
|---|---|
| Понимание цели | Все явные и неявные ограничения извлечены? |
| План | Правильный ли порядок шагов? |
| Выбор инструмента | Нужный API вызван в нужный момент? |
| Аргументы | Корректны ли параметры API? |
| Использование результата | Верно ли модель прочитала tool output? |
| Состояние | Достигнуто ли нужное финальное состояние? |
| Безопасность | Нет ли запрещённого/необратимого действия? |
| Эффективность | Нет ли лишних шагов, стоимости и задержки? |
| Коммуникация | Понятно ли пользователю, что сделано и что нужно подтвердить? |

Нельзя заменить эту карту одним `success = 0/1`. Бинарный успех нужен для бизнеса, но для улучшения модели необходимо знать, где именно путь сломался.

## 3. Метрики

### Финальный успех

`Task success rate` — доля задач, где достигнуто нужное состояние и соблюдены обязательные ограничения.

### Частичный успех

В реальности задача может быть выполнена на 70%: агент нашёл товары и учёл бюджет, но забыл проверить доставку. Полезна взвешенная схема:

```text
partial_score = Σ(weight_constraint × constraint_satisfied)
```

Вес доставки, оплаты или согласия пользователя может быть выше веса второстепенного предпочтения.

### Правильность работы с инструментами

- tool selection accuracy;
- valid argument rate;
- tool execution success;
- доля лишних вызовов;
- доля вызовов, нарушающих policy.

### Разумная цена и число шагов

- число шагов;
- latency;
- стоимость токенов и API;
- число повторных попыток;
- длина траектории относительно разумного baseline.

Минимальное число шагов не всегда цель: безопасное уточнение добавляет шаг, но улучшает качество.

### Безопасность

- действие без согласия;
- выход за бюджет;
- утечка данных;
- вызов недоступного инструмента;
- опасная рекомендация;
- неспособность остановиться при неуверенности.

Safety чаще является guardrail: небольшое ухудшение не компенсируется средним ростом task success.

## 4. Учитываем разные типы задач

| Тип задачи | Что будет успехом |
|---|---|
| Поиск | Найден релевантный объект и показаны подтверждённые свойства |
| Сравнение | Учтены критерии, вывод опирается на данные |
| Оформление | Правильное состояние создано после подтверждения |
| Планирование | План выполним и покрывает ограничения |
| Диагностика | Верно выбрана причина или следующий инструмент |
| Нет решения | Агент корректно отказался/эскалировал |

Одна метрика не должна делать модель «смелой» там, где правильный ответ — попросить уточнение.

## 5. Пример: агент Маркета

Задача: «Найди смартфон до 50 000 ₽, с рейтингом от 4,7, доставкой завтра. Покажи три варианта и не оформляй заказ».

Проверяем:

1. Извлечены ли бюджет, рейтинг, доставка, число вариантов и запрет на заказ.
2. Вызван ли поиск с подходящими фильтрами.
3. Проверена ли дата доставки в конкретный адрес.
4. Получены ли данные для трёх разных товаров.
5. Не придуманы ли характеристики, которых нет в API.
6. Не вызван ли `confirm_order`.
7. Подходит ли итоговый ответ пользователю.

Даже при правильном финальном списке агент может быть небезопасен, если начал оформлять заказ без разрешения.

## 6. Автоматическая и человеческая оценка

Автоматически легко проверить:

- финальное состояние;
- schema/API validity;
- бюджет и ограничения;
- число шагов;
- запрещённые действия.

Человеку или judge сложнее, но нужно оценивать:

- разумность выбора из нескольких допустимых путей;
- полноту объяснения;
- понимание неоднозначной цели;
- качество уточняющего вопроса;
- смысловую ошибку в интерпретации результата.

Хороший benchmark совмещает оба слоя.

## 7. Несколько правильных траекторий

Не нужно требовать единственного маршрута. Агент может сначала спросить уточнение или сначала запросить детали товара — оба пути могут быть корректны.

Оцениваем инварианты:

- достигнута цель;
- соблюдены ограничения;
- запрещённые действия отсутствуют;
- инструмент использован валидно;
- стоимость не превышает лимит;
- пользователь не введён в заблуждение.

Golden trajectory остаётся полезна как демонстрация и источник данных, но не должна быть единственным критерием оценки.

## 8. Типичные ошибки

- Оценивать только финальный текст.
- Награждать завершение действия без проверки согласия пользователя.
- Штрафовать любую длинную траекторию, даже если она безопасно уточняет задачу.
- Не фиксировать состояние среды и версии API.
- Смешивать ошибку среды с ошибкой агента.
- Игнорировать failure recovery — способность корректно реагировать на ошибку инструмента.
