# Агентные системы — вызов инструментов, MCP и тестирование

> [!abstract] Зачем нужна эта карточка
> Агент — это не просто языковая модель, которая написала красивый ответ. Модель может выбрать действие, вызвать поиск или API, прочитать результат, изменить план и повторить цикл. Чтобы тестировать такую систему, нужно понимать весь путь: от решения модели до фактического изменения состояния. Ниже сначала разберём механику вызова инструментов, затем MCP, а в конце соберём практический подход к оценке.

> [!tip] Быстрое повторение перед собеседованием
> - Модель обычно не обращается к API напрямую. Она возвращает структурированный запрос на вызов инструмента, а оркестратор валидирует его и выполняет.
> - После результата инструмента оркестратор добавляет observation (наблюдение) в историю и снова вызывает модель. Цикл заканчивается финальным ответом, лимитом шагов, ошибкой или безопасной остановкой.
> - Function calling — способ конкретного провайдера передать модели схемы функций. MCP — открытый протокол, который стандартизирует обнаружение и вызов tools, resources и prompts между приложением и серверами.
> - В MCP host управляет приложением и моделью, client держит отдельное соединение с одним server, а server предоставляет инструменты и данные.
> - Для MCP важны два разных сбоя: protocol error (неверный JSON-RPC-запрос или неизвестный tool) и tool execution error (сам инструмент не смог выполнить операцию).
> - Инструмент описывается именем, понятным описанием, inputSchema и при возможности outputSchema. В destructive-операциях нужны подтверждение, права и идемпотентность.
> - Тестируем не только финальный текст: проверяем состояние среды, аргументы инструментов, запрещённые действия, восстановление после ошибок, стоимость и задержку.
> - Judge полезен для смысловой оценки, но состояние, права, схема и безопасность должны проверяться детерминированными кодом и правилами.

> [!info] Словарь без лишних англицизмов
> **Agent (агент)** — система, которая сама выбирает несколько шагов и может менять внешнее состояние. **Tool (инструмент)** — разрешённое действие: поиск, чтение файла, расчёт, изменение корзины. **Orchestrator (оркестратор)** — код, который связывает модель, инструменты, память и правила безопасности. **Tool call** — структурированная просьба вызвать инструмент. **Observation** — результат, который инструмент вернул модели. **Function calling** — формат, в котором модель предлагает вызов функции. **Schema** — формальное описание допустимых полей и типов. **MCP** — протокол взаимодействия приложений с серверами, которые предоставляют инструменты, ресурсы и шаблоны промптов. **Host** — приложение-контейнер. **Client** — соединитель host с одним MCP server. **Server** — процесс или сервис, который предоставляет capabilities (возможности).

## 1. Чем агент отличается от обычного чат-бота

У обычного чат-бота единица работы часто выглядит так:

~~~text
сообщение пользователя → модель → текстовый ответ
~~~

У агента появляется внешний мир, который можно читать и менять:

~~~text
задача
  ↓
модель выбирает действие
  ↓
оркестратор проверяет действие
  ↓
инструмент обращается к API или среде
  ↓
результат возвращается модели
  ↓
модель продолжает план или отвечает пользователю
~~~

Пример:

> «Найди смартфон до 50 000 рублей с доставкой завтра, покажи три варианта и не оформляй заказ».

Агенту нужно:

1. извлечь бюджет, дату, количество вариантов и запрет на оформление;
2. вызвать поиск товаров;
3. проверить наличие и доставку именно для нужного адреса;
4. выбрать три допустимых варианта;
5. ответить, не вызывая оформление заказа.

Финальная фраза «нашёл три смартфона» ничего не доказывает. Нужно проверить фактическую корзину, параметры поиска, дату доставки и отсутствие запрещённого вызова.

## 2. Полный цикл вызова инструмента

Рассмотрим один шаг подробно.

### Шаг 1. Host готовит контекст

Приложение передаёт модели:

- сообщение пользователя;
- системные правила;
- историю предыдущих шагов;
- список доступных инструментов;
- схемы аргументов и ограничения;
- иногда текущее состояние среды.

Список инструментов — это часть входа модели. Плохое описание инструмента может привести к ошибке даже у сильной модели.

### Шаг 2. Модель выбирает: ответить или вызвать tool

Модель не исполняет Python и не открывает HTTP-соединение сама. Она генерирует специальную структурированную часть ответа:

~~~json
{
  "type": "tool_call",
  "name": "search_products",
  "arguments": {
    "query": "смартфон",
    "max_price": 50000,
    "delivery_date": "2026-09-01",
    "limit": 20
  }
}
~~~

В некоторых API это поле называется tool_calls, function_call или иначе. Названия отличаются, смысл один: модель предложила действие, а не выполнила его.

### Шаг 3. Оркестратор валидирует вызов

До выполнения нужно проверить:

- существует ли такой tool;
- соответствуют ли аргументы JSON Schema;
- имеет ли пользователь нужные права;
- не нарушает ли действие policy;
- не является ли операция опасной;
- не превышен ли лимит шагов, бюджета или времени;
- нужен ли явный запрос подтверждения.

Важно: описание от модели не является разрешением. Разрешение определяется кодом приложения и правами пользователя.

### Шаг 4. Адаптер выполняет действие

Оркестратор вызывает конкретную функцию, HTTP-клиент, SQL-запрос или MCP client. Здесь должны быть:

- timeout;
- авторизация от имени правильного пользователя;
- ограничение размера результата;
- логирование;
- обработка временных ошибок;
- идемпотентный ключ для повторяемых операций.

### Шаг 5. Результат нормализуется

Сырый ответ API не стоит бездумно передавать модели. Адаптер:

- удаляет секреты и лишние поля;
- приводит ошибки к единому формату;
- ограничивает длину;
- добавляет источник и время актуальности;
- возвращает структурированный результат.

~~~json
{
  "ok": true,
  "items": [
    {
      "id": "p-17",
      "title": "Модель X",
      "price": 47990,
      "delivery_date": "2026-09-01"
    }
  ],
  "next_action": "filter_or_compare"
}
~~~

### Шаг 6. Observation добавляется в историю

Оркестратор добавляет результат как сообщение от инструмента, а не как новое сообщение пользователя. Модель получает возможность рассуждать дальше, но не должна считать содержимое инструмента безусловно истинным: API может вернуть ошибку, устаревшие данные или текст с prompt injection.

### Шаг 7. Модель продолжает или завершает задачу

Она может:

- вызвать следующий инструмент;
- повторить вызов с исправленными аргументами;
- задать уточняющий вопрос;
- честно сообщить, что данных недостаточно;
- сформировать финальный ответ.

Остановка должна быть явной. Нужны максимальное число шагов, общий timeout, лимит стоимости и аварийная остановка.

### Мини-трасса одного вызова

Полезно представить не только идею, но и сообщения, которые реально проходят через host:

~~~text
1. user      → «Какая погода в Казани?»
2. assistant → tool_call(id=call-1, name=get_weather, arguments={city: «Казань»})
3. host      → проверка схемы, прав и policy; вызов адаптера
4. tool      → tool_result(id=call-1, content={temp: 18, condition: «облачно»})
5. assistant → «В Казани сейчас 18 °C, облачно»
~~~

На шаге 2 модель ещё ничего не узнала о погоде и ничего не изменила. Фактический внешний эффект возникает только на шаге 3–4. Поэтому в тесте полезно хранить минимум три результата: что предложила модель, что разрешил оркестратор и что действительно сделал инструмент. Если два инструмента вызваны параллельно, `id` нужен, чтобы не перепутать их ответы.

## 3. Function calling и MCP — не одно и то же

Эти понятия часто смешивают.

### Function calling

Function calling — это механизм API конкретной LLM-платформы:

1. приложение передаёт модели описание функций;
2. модель возвращает имя функции и JSON-аргументы;
3. приложение само вызывает функцию;
4. приложение передаёт результат обратно модели.

Он решает формат обмена с одной моделью, но не отвечает на вопросы:

- как обнаружить функции разных команд;
- как подключить удалённый сервер;
- как договориться о возможностях;
- как передавать ресурсы и prompts;
- как единообразно тестировать инструменты.

Удобно разделять уровни:

| Уровень | Что стандартизирует | Кто обычно отвечает за выполнение |
|---|---|---|
| Прямой API | только HTTP/SDK-контракт сервиса | код приложения |
| Function calling | как LLM предлагает имя функции и JSON-аргументы | оркестратор приложения |
| MCP | как host подключает server, обнаруживает tools/resources/prompts и обменивается сообщениями | MCP client и MCP server |

### MCP

MCP стандартизирует слой подключения:

- как host находит доступные server;
- как server сообщает tools, resources и prompts;
- как описывается input/output schema;
- как передаются JSON-RPC-сообщения;
- как выбирается транспорт;
- как обрабатываются ошибки и отмена.

Типичный host всё равно может преобразовать MCP tools в формат function calling конкретной LLM. Поэтому MCP не заменяет вызов инструмента моделью: он стандартизирует каталог и канал, а решение «какой tool вызвать» всё равно принимает модель или оркестратор.

## 4. Как выглядит оркестратор

Упрощённый цикл можно представить так:

~~~python
def run_agent(task, model, tools, max_steps=8):
    messages = [{"role": "user", "content": task}]

    for step in range(max_steps):
        response = model.generate(
            messages=messages,
            tool_schemas=tools.schemas(),
        )

        if response.final_text is not None:
            return response.final_text

        for call in response.tool_calls:
            validate_tool_call(call, tools, messages)
            result = tools.execute(
                name=call.name,
                arguments=call.arguments,
                timeout=2.0,
            )
            messages.append({
                "role": "assistant",
                "tool_call": call.to_dict(),
            })
            messages.append({
                "role": "tool",
                "tool_call_id": call.id,
                "content": sanitize_tool_result(result),
            })

    raise AgentTimeout("maximum number of steps reached")
~~~

В production здесь ещё нужны:

- policy engine перед опасным действием;
- авторизация и аудит;
- дедупликация повторного вызова;
- cancellation;
- трассировка каждого шага;
- ограничение токенов и размера observation;
- отдельный checker конечного состояния.

Смысл примера не в конкретном SDK, а в разделении ответственности: модель предлагает, оркестратор решает, инструмент исполняет, checker проверяет.

## 5. Как проектировать хороший инструмент

Инструмент — это контракт между моделью и кодом. Чем яснее контракт, тем меньше ошибок выбора и аргументов.

### 5.1. Имя и описание

Плохой вариант: search.

Лучше:

~~~text
search_available_products
Ищет товары, которые доступны для доставки в указанный город.
Не оформляет заказ и не меняет корзину.
Если бюджет неизвестен, не подставляет его самостоятельно.
~~~

В описании полезно явно указать:

- что делает инструмент;
- что он не делает;
- единицы измерения;
- обязательные поля;
- ограничения и возможные ошибки;
- когда его нельзя вызывать.

### 5.2. Input schema

Схема должна отсеивать технически невозможные значения:

~~~json
{
  "type": "object",
  "additionalProperties": false,
  "properties": {
    "query": {
      "type": "string",
      "minLength": 1,
      "description": "Что ищем"
    },
    "max_price": {
      "type": "integer",
      "minimum": 1,
      "description": "Максимальная цена в рублях"
    },
    "limit": {
      "type": "integer",
      "minimum": 1,
      "maximum": 50
    }
  },
  "required": ["query"]
}
~~~

Schema проверяет форму данных, но не бизнес-смысл. Например, она не поймёт, что дата доставки уже прошла или что пользователь не имеет доступа к магазину.

### 5.3. Output schema

Если результат структурированный, полезно описать и его:

~~~json
{
  "type": "object",
  "properties": {
    "items": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "id": {"type": "string"},
          "title": {"type": "string"},
          "price": {"type": "number"}
        },
        "required": ["id", "title", "price"]
      }
    }
  },
  "required": ["items"]
}
~~~

Клиент может проверить, что сервер действительно вернул ожидаемую структуру. Для анализа это лучше, чем парсить свободный текст.

### 5.4. Read-only и destructive tools

Полезно разделять инструменты по риску:

| Вид | Пример | Правило |
|---|---|---|
| Только чтение | поиск, просмотр профиля | можно выполнять автоматически при наличии прав |
| Изменение состояния | добавить в корзину, создать черновик | логировать, проверять права и идемпотентность |
| Необратимое действие | оплатить, удалить файл, отправить письмо | подтверждение пользователя и отдельный policy check |

Аннотация readOnly или destructive — это подсказка клиенту, а не механизм безопасности. Сервер всё равно должен сам проверить права и параметры.

## 6. Ошибки: что именно пошло не так

Разные ошибки требуют разной реакции.

### Protocol error

Запрос нарушает протокол:

- неизвестное имя инструмента;
- невалидный JSON;
- отсутствует обязательный параметр;
- неверный тип сообщения;
- неподдерживаемая capability.

Обычно оркестратор не должен бесконечно повторять такой вызов. Нужно исправить схему, prompt или код клиента.

### Tool execution error

Инструмент найден и аргументы имеют правильную форму, но операция не выполнена:

- API вернул 404 или 500;
- нет товара в наличии;
- база временно недоступна;
- пользователь не имеет доступа;
- значение не прошло бизнес-проверку.

Такую ошибку можно вернуть модели как observation с флагом ошибки. Тогда агент иногда способен исправить аргументы или выбрать другой путь.

~~~json
{
  "isError": true,
  "content": [
    {
      "type": "text",
      "text": "Товар недоступен для доставки в этот город"
    }
  ]
}
~~~

### Timeout и cancellation

Для каждого tool call нужен собственный timeout и общий deadline эпизода. При превышении времени:

1. прекращаем ждать;
2. отменяем запрос, если транспорт поддерживает отмену;
3. фиксируем timeout отдельно от обычной ошибки;
4. решаем, безопасен ли повтор;
5. не оставляем пользователя в состоянии «операция, возможно, выполнилась».

### Повторный вызов

Retry безопасен не всегда. Для чтения каталога обычно можно повторить запрос. Для оплаты или создания заказа нужен идемпотентный ключ и понимание, выполнилась ли первая попытка.

## 7. Планы, циклы и параллельные вызовы

### Один вызов

Подходит для простого запроса: калькулятор, перевод единиц, получение курса.

### Последовательный план

Каждый следующий tool зависит от результата предыдущего:

~~~text
найти товар → проверить доставку → добавить в корзину → попросить подтверждение
~~~

Здесь важно тестировать состояние после каждого шага, а не только финальный ответ.

### Параллельные вызовы

Если шаги независимы, оркестратор может вызвать их параллельно:

~~~text
получить профиль пользователя ─┐
получить историю заказов ──────┼→ собрать рекомендацию
получить доступные скидки ─────┘
~~~

Проверяйте:

- ограничение числа одновременных вызовов;
- отмену остальных задач после критической ошибки;
- порядок и идентификаторы результатов;
- отсутствие гонок при изменении общей корзины.

### ReAct-подобный цикл

Модель чередует внутреннее решение, действие и наблюдение. В production не нужно обязательно сохранять скрытые рассуждения. Для оценки достаточно журнала действий, аргументов, результатов и конечного состояния.

## 8. Что такое MCP

Model Context Protocol — открытый протокол, который позволяет приложениям подключать внешние данные и действия единообразным способом. По смыслу он похож на стандартизированный разъём: приложение и сервер могут быть написаны разными командами, но договариваются о формате сообщений и возможностях.

MCP строится поверх JSON-RPC. Это означает, что сообщения имеют метод, параметры, идентификатор запроса и результат или ошибку. Точная версия протокола развивается, поэтому в production фиксируют версию SDK и проверяют совместимость.

### 8.1. Host, client и server

~~~text
Host
├── LLM и пользовательский интерфейс
├── policy, подтверждения, память и общий оркестратор
├── MCP client A ─── MCP server каталога
├── MCP client B ─── MCP server файлов
└── MCP client C ─── MCP server аналитики
~~~

- **Host** — приложение-контейнер, например чат или IDE. Оно управляет моделью, соединениями, контекстом и разрешениями.
- **MCP client** — компонент host, который держит отдельное соединение с одним server и переводит внутренние вызовы в MCP-сообщения.
- **MCP server** — локальный процесс или удалённый сервис, который предоставляет инструменты и данные. Он не обязан содержать LLM и обычно не видит всю историю разговора.

Изоляция важна: серверу файлов не нужно видеть токены, историю покупок или инструменты другого сервера.

### 8.2. Три основных примитива

| Примитив | Кто обычно управляет | Пример |
|---|---|---|
| Tool | модель через host | поиск товара, выполнение расчёта |
| Resource | приложение | содержимое файла, схема БД, документ |
| Prompt | пользователь/приложение | готовый шаблон «суммируй документ» |

Инструмент — действие, resource — контекст, prompt — заготовка инструкции. Не следует превращать все данные в tools: чтение большого документа часто логичнее представить ресурсом.

## 9. Как MCP обнаруживает и вызывает инструменты

### 9.1. Discovery и capabilities

При подключении client узнаёт, какие функции поддерживает server. Сервер может сообщить поддержку tools, resources, prompts, notifications и других расширений. Клиент должен учитывать только заявленные возможности.

Если каталог большой, ответ может приходить частями: клиент получает `nextCursor` и запрашивает следующую страницу. Если сервер сообщает, что список изменился, host должен обновить локальный каталог, иначе модель продолжит вызывать уже удалённый или изменившийся tool.

В актуальной спецификации базовые HTTP-запросы самодостаточны и несут версию протокола и capabilities. Старые реализации используют отдельный initialize handshake. На интервью достаточно сказать: клиент и сервер согласуют версию и поддерживаемые возможности до обычных вызовов; детали зависят от версии протокола.

### 9.2. Получение каталога tools

Упрощённый запрос:

~~~json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/list",
  "params": {}
}
~~~

Упрощённый ответ:

~~~json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "tools": [
      {
        "name": "search_products",
        "description": "Ищет товары по каталогу",
        "inputSchema": {
          "type": "object",
          "properties": {
            "query": {"type": "string"}
          },
          "required": ["query"]
        },
        "outputSchema": {
          "type": "object",
          "properties": {
            "items": {"type": "array"}
          },
          "required": ["items"]
        }
      }
    ]
  }
}
~~~

Host может преобразовать этот каталог в формат, который понимает конкретная LLM. Если server подключился позже или изменил список, клиент обновляет каталог и версионирует его в трассировке.

### 9.3. Вызов tools/call

~~~json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "search_products",
    "arguments": {
      "query": "смартфон"
    }
  }
}
~~~

Успешный результат может содержать обычный текст, изображения, ссылки на ресурсы и structuredContent (структурированный JSON):

~~~json
{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "content": [
      {
        "type": "text",
        "text": "Найдено 12 товаров"
      }
    ],
    "structuredContent": {
      "items": [
        {"id": "p-17", "price": 47990}
      ]
    },
    "isError": false
  }
}
~~~

Тестировщик должен отдельно проверить content, structuredContent и isError. Нельзя предполагать, что текстовый результат всегда содержит полный JSON.

### 9.4. Почему важен ID запроса

JSON-RPC id связывает ответ с конкретным вызовом. Это особенно важно при параллельных запросах и повторных попытках. В трассировке храните:

- episode_id;
- request_id;
- имя server;
- имя tool;
- аргументы после удаления секретов;
- время отправки и получения;
- результат или код ошибки.

## 10. Транспорты MCP

Транспорт отвечает за то, как байты доходят до server; смысл сообщений остаётся тем же.

### stdio

Host запускает server как дочерний процесс. Сообщения идут построчно через stdin/stdout.

Плюсы:

- удобно для локальных инструментов;
- не нужен открытый порт;
- естественная изоляция процесса.

Критическое правило: stdout должен содержать только корректные MCP-сообщения. Обычный print для отладки может сломать протокол; логи отправляют в stderr.

### Streamable HTTP

Server работает как самостоятельный HTTP-сервис с одним MCP endpoint. Клиент посылает POST, а ответ приходит JSON или потоковыми событиями, если это поддерживается.

Плюсы:

- удалённый сервис;
- несколько клиентов;
- горизонтальное масштабирование;
- стандартная HTTP-инфраструктура.

Нужны:

- аутентификация;
- проверка Origin и защита от DNS rebinding;
- ограничение размера тела;
- timeout и cancellation;
- rate limiting;
- журналирование.

Старый HTTP+SSE transport встречается в совместимых клиентах, но для новых реализаций ориентируются на Streamable HTTP. Перед собеседованием полезно уточнить, какую версию поддерживает конкретный SDK.

## 11. Минимальный MCP server на Python

API Python SDK меняется, поэтому версию пакета нужно фиксировать. Ниже пример для актуальной ветки v2: сервер создаётся через `MCPServer`, а типы аргументов и docstring автоматически превращаются в описание инструмента.

~~~python
from mcp.server import MCPServer

mcp = MCPServer("Catalog")

@mcp.tool()
def search_products(query: str, max_price: int | None = None) -> dict:
    """Ищет доступные товары и не меняет корзину."""
    items = search_in_catalog(query, max_price=max_price)
    return {"items": items}

@mcp.resource("catalog://status")
def catalog_status() -> str:
    return "catalog is available"

if __name__ == "__main__":
    mcp.run()  # по умолчанию stdio
~~~

Что делает SDK:

- регистрирует функцию как tool;
- берёт имя и docstring для описания;
- строит input schema из type hints;
- запускает выбранный транспорт (`stdio` по умолчанию);
- сериализует результат в MCP-ответ.

Но бизнес-проверки остаются на разработчике server: права, лимиты, SQL-инъекции, секреты и корректность результата.

Для HTTP тот же server запускают через `mcp.run(transport="streamable-http", port=3001)`. В v1 и некоторых сторонних обёртках встречается `FastMCP`; это не другая идея протокола, а другой API SDK. Не стоит копировать команду запуска вслепую без фиксации версии.

## 12. Как тестировать MCP server отдельно от LLM

Сначала проверяйте server напрямую. Это быстрее и даёт точные ошибки.

### 12.1. Unit-тест обработчика

Обычная функция поиска тестируется без MCP:

~~~python
def test_search_products_respects_price_limit(fake_catalog):
    result = search_products("phone", max_price=50000)
    assert all(item["price"] <= 50000 for item in result["items"])
~~~

### 12.2. Contract-тест протокола

Проверьте, что:

- tool появляется в tools/list;
- имя стабильно;
- inputSchema содержит required и ограничения;
- outputSchema совпадает с реальным результатом;
- невалидные аргументы дают понятную ошибку;
- неизвестный tool не выполняется;
- isError выставляется для ошибки выполнения;
- structuredContent соответствует схеме.

Если server публикует resources или prompts, добавьте такие же проверки для `resources/list`/`resources/read` и `prompts/list`/`prompts/get`: URI или имя должно быть стабильным, результат — доступным только в разрешённом объёме, а ошибки — предсказуемыми. Это важно, потому что агент может получить инструкцию не только через tool, но и через подключённый ресурс или шаблон prompt.

### 12.3. In-memory client

Python SDK предоставляет in-memory способ соединить client и server без subprocess и порта. Это удобно для CI:

~~~python
import pytest
from mcp import Client

@pytest.mark.anyio
async def test_search_tool():
    async with Client(mcp) as client:
        result = await client.call_tool(
            "search_products",
            {"query": "phone", "max_price": 50000},
        )
        assert result.structured_content["items"]
~~~

Конкретные поля результата зависят от версии SDK, поэтому контрактный тест должен быть привязан к зафиксированной версии.

## 13. Уровни тестирования агента

### Уровень 1. Тест инструмента

Проверяем функцию и её ошибки без модели. Это самый детерминированный слой.

### Уровень 2. Тест оркестратора

Подменяем модель заранее записанными tool calls:

~~~text
модель предложила search_products
→ оркестратор проверил аргументы
→ tool вернул результат
→ результат добавлен в историю
→ следующий вызов получил правильный контекст
~~~

Так можно проверить лимиты шагов, retry, timeout, cancellation и policy без случайности LLM.

### Уровень 3. Тест среды и checker

Запускаем эпизод в виртуальной среде с фиксированным состоянием. Checker проверяет финальное состояние и обязательные ограничения. Например, корзина должна содержать нужные товары, бюджет не превышен, заказ не подтверждён.

### Уровень 4. End-to-end с моделью

Запускаем реальную LLM на наборе задач. Здесь измеряем выбор инструмента, аргументы, планы и смысл ответа. Один и тот же сценарий может потребовать нескольких прогонов из-за стохастичности модели.

### Уровень 5. Нагрузочные и safety-тесты

Проверяем p95 latency, параллельные сессии, лимиты, утечки данных, prompt injection, опасные действия и отказоустойчивость.

## 14. Как формировать задачу и среду

Хороший тестовый эпизод хранит не только текст задания:

~~~json
{
  "episode_id": "market-042",
  "task": "Найди ноутбук до 90000 рублей и добавь один вариант в корзину. Не оформляй заказ.",
  "initial_state": {
    "user_id": "u-7",
    "city": "Казань",
    "cart": [],
    "balance": 100000
  },
  "allowed_tools": [
    "search_products",
    "get_delivery",
    "add_to_cart"
  ],
  "forbidden_tools": [
    "confirm_order",
    "pay"
  ],
  "success_conditions": [
    "cart_has_one_matching_product",
    "price_le_90000",
    "order_not_confirmed"
  ]
}
~~~

Такой формат позволяет:

- сбросить среду перед запуском;
- воспроизвести ошибку;
- сравнить две модели на одинаковом состоянии;
- отличить ошибку агента от ошибки API;
- считать частичный прогресс.

Не требуйте одну конкретную траекторию, если несколько путей приводят к безопасному результату. Проверяйте инварианты: цель, ограничения, права, отсутствие запрещённых действий и корректность состояния.

## 15. Метрики агентных систем

### Финальный успех

~~~text
task_success_rate =
успешные эпизоды / все завершённые эпизоды
~~~

Успех должен определяться checker-кодом, а не только финальной фразой.

### Корректность инструментов

- tool selection accuracy — выбран допустимый инструмент;
- argument validity rate — аргументы прошли схему и бизнес-проверки;
- tool execution success — вызов реально выполнился;
- invalid call rate — доля неверных вызовов;
- forbidden action rate — доля запрещённых действий.

### Восстановление

~~~text
recovery_rate =
эпизоды, завершившиеся успехом после временной ошибки
/
эпизоды, где была временная ошибка
~~~

Отдельно считаем, сколько повторов потребовалось и не создал ли retry дубликат заказа.

### Эффективность

- среднее и p95 число tool calls;
- число шагов до успеха;
- latency всей задачи;
- стоимость токенов и внешних API;
- длина и размер observations;
- доля досрочно остановленных эпизодов.

Минимум шагов не всегда лучше. Уточняющий вопрос может увеличить длину траектории, но снизить риск ошибки.

### Безопасность

- действие без подтверждения;
- доступ к чужому tenant;
- утечка PII или секретов;
- обход фильтра;
- выполнение запрещённого SQL;
- игнорирование policy;
- отсутствие безопасного отказа.

Safety-метрики обычно являются guardrails: рост успеха не компенсирует критический рост опасных действий.

### Частичный успех

Для сложной задачи задаём веса обязательных условий:

~~~text
partial_score =
0.4 × цель
+ 0.3 × бюджет
+ 0.2 × доставка
+ 0.1 × формат ответа
~~~

Вес оплаты, доступа или безопасности должен быть больше веса косметического формата. Не превращайте partial score в замену бинарному business success: он нужен для диагностики точек роста.

## 16. Трассировка и наблюдаемость

Для каждого эпизода храните одну сквозную trace:

~~~text
episode_id
├── model_version, prompt_version, tool_catalog_version
├── user task и хэш начального состояния
├── turn 0: model response
│   └── tool_call: name, arguments, policy decision
├── tool execution: server, request_id, latency, result/error
├── state snapshot after action
├── turn 1: следующая модель
└── final state, checker result, final answer
~~~

Не записывайте в открытом виде пароли, токены, полные персональные данные и секретные документы. Аргументы можно маскировать или хешировать, сохраняя отдельные безопасные поля для анализа.

Поля, которые особенно полезны:

- версия модели и промпта;
- версия среды и схем tools;
- request_id и episode_id;
- время каждого шага;
- размер входа и результата;
- коды ошибок;
- решение policy;
- state hash до и после;
- итог checker;
- стоимость и количество токенов.

## 17. Что именно ломается и как это диагностировать

| Симптом | Возможная причина | Как проверить |
|---|---|---|
| Модель не вызывает нужный tool | неясное описание или лишние инструменты | contract-тест каталога, минимальный prompt |
| Выбран правильный tool, но неверные поля | слабая schema или неоднозначные единицы | schema validation и негативные примеры |
| Tool выполнился, задача не решена | ошибка в плане или использовании observation | разбор траектории и состояния |
| Успех вырос, но опасные действия тоже | отсутствует policy/confirmation gate | safety-набор и forbidden-action rate |
| Модель зацикливается | нет лимита шагов или неинформативная ошибка | fault injection, max_steps, recovery logs |
| После retry два заказа | операция неидемпотентна | повторный вызов в тестовой среде |
| Агент видит лишние данные | слишком широкий контекст или ACL после retrieval | тест с чужим tenant и проверка trace |
| MCP tool не появляется | capability/discovery/schema ошибка | tools/list, версия протокола, SDK logs |
| stdout MCP server повреждён | отладочный print попал в протокол | запуск subprocess и проверка каждой строки JSON-RPC |
| Средняя latency хорошая, p95 плохая | хвостовые таймауты и тяжёлые tools | нагрузочный тест по типам задач |

## 18. Безопасность MCP и инструментов

MCP даёт доступ к данным и выполнению действий, поэтому серверу нельзя доверять только на основании его описания.

Проверяйте:

1. **Авторизацию.** Каждая операция выполняется от имени конкретного пользователя, а не от общего сервисного аккаунта без ограничений.
2. **Изоляцию.** Server получает только нужный контекст и не видит всю историю разговора.
3. **Prompt injection.** Текст документа или результат поиска может содержать инструкцию «игнорируй правила». Это данные, а не системная команда.
4. **SSRF и path traversal.** URL, пути к файлам и SQL-параметры проходят отдельную валидацию.
5. **Destructive actions.** Оплата, удаление и отправка требуют отдельного подтверждения.
6. **Секреты.** Токены не попадают в prompt, tool result и обычные логи.
7. **Rate limit и timeout.** Один агент не должен занять все соединения или бесконечно вызывать дорогой API.
8. **Output sanitization.** Результат инструмента ограничивается по размеру и очищается от лишних полей.
9. **Audit.** Все вызовы можно восстановить по trace.

Полезный red-team сценарий: положить в описание товара или PDF текст, который пытается заставить агента вызвать оплату. Правильная система рассматривает его как содержимое документа и не меняет policy.

## 19. Мини-кейс: агент Алисы для Маркета

Задача:

> «Подбери три ноутбука для работы с Python до 90 000 рублей, с доставкой завтра в Казань. Добавь лучший вариант в корзину, но не оформляй заказ».

### Декомпозиция

1. Извлечь бюджет, город, дату, назначение, количество и запрет на оплату.
2. Вызвать search_products с query и max_price.
3. Получить характеристики и delivery options.
4. Отфильтровать неподходящие варианты.
5. Обосновать выбор.
6. Вызвать add_to_cart ровно один раз.
7. Проверить состояние корзины.
8. Вернуть ответ и явно сказать, что заказ не оформлен.

### Что проверяем

- поиск не вышел за бюджет;
- доставка относится к Казани;
- характеристики не придуманы;
- в корзине ровно один подходящий товар;
- confirm_order и pay не вызывались;
- повторный запуск из того же состояния идемпотентен;
- при ошибке доставки агент предлагает другой вариант или задаёт вопрос.

### Какие тестовые варианты нужны

- обычный сценарий с тремя подходящими товарами;
- ни одного товара до бюджета;
- конфликт цены и доставки;
- пустой результат поиска;
- timeout каталога;
- tool output с вредной инструкцией;
- пользователь просит оформить заказ без подтверждения;
- пользователь пытается получить товар другого tenant.

## 20. Как принимать решение по версии агента

Перед сравнением версий зафиксируйте:

- список задач и версии среды;
- каталог инструментов и схемы;
- модель, prompt и параметры генерации;
- правила checker и safety;
- число прогонов на сценарий;
- главную метрику и guardrails;
- допустимую стоимость и p95 latency.

Пример release gate:

~~~text
task_success_rate не ниже baseline
forbidden_action_rate не выше порога
argument_validity_rate не ниже baseline
recovery_rate не ухудшился
p95 latency и стоимость в SLA
критические сценарии безопасности не имеют регрессии
~~~

Если новая модель стала чаще достигать цели, но хотя бы иногда выполняет оплату без подтверждения, общий релиз нельзя принимать. Сначала исправляют policy, инструменты или обучение и повторяют оценку.

## Вопросы для собеседования

> [!question] Модель сама вызывает API?
> Нет. Она предлагает структурированный tool call. Host или оркестратор проверяет его, вызывает адаптер/API и возвращает результат модели.

> [!question] Зачем MCP, если уже есть function calling?
> Function calling задаёт формат вызова для конкретной LLM-платформы. MCP стандартизирует обнаружение и подключение независимых серверов, их tools, resources, prompts, схемы и транспорт. Host может преобразовать MCP-каталог в function calling.

> [!question] Чем tool execution error отличается от protocol error?
> Protocol error означает, что сообщение или вызов нарушил протокол. Tool execution error означает, что корректно найденный инструмент не смог выполнить бизнес-операцию. Вторая ошибка может быть полезным observation для recovery.

> [!question] Почему нельзя проверять агента только по финальному ответу?
> Текст может выглядеть правильно, хотя агент превысил бюджет, вызвал запрещённый tool или не изменил нужное состояние. Нужны trace и checker конечного состояния.

> [!question] Что тестировать в MCP server без LLM?
> tools/list, схемы, tools/call, валидацию аргументов, structuredContent, isError, права, timeout, cancellation и корректность transport framing.

> [!question] Можно ли требовать одну golden trajectory?
> Обычно нет. Разные последовательности могут быть одинаково безопасными и успешными. Фиксируют обязательные инварианты и допустимые варианты поведения.

> [!question] Как тестировать prompt injection в tool output?
> Поместить вредную инструкцию в документ или ответ API и проверить, что она не меняет policy, не приводит к секретному вызову и корректно отображается как данные.

## Практика

1. Напишите оркестратор с max_steps, timeout и отдельными ошибками протокола и выполнения.
2. Сделайте mock-инструмент, который один раз возвращает timeout, затем успешный результат. Проверьте recovery и отсутствие бесконечного retry.
3. Опишите tool через inputSchema и outputSchema, добавьте негативные тесты.
4. Поднимите локальный `MCPServer` (или `FastMCP` для зафиксированной v1) с одним read-only tool и проверьте его через Inspector или in-memory client.
5. Соберите 20 эпизодов для Маркета: обычные, пустые, конфликтные, опасные и с ошибками сети.
6. Посчитайте task success, forbidden action rate, valid argument rate, recovery rate и p95 latency.
7. Добавьте prompt injection в результат поиска и докажите тестом, что агент не вызвал оплату.
8. Сравните две версии модели по одинаковым состояниям и постройте таблицу регрессий.
