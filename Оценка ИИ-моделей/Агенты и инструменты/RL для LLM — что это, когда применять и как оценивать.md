# RL для LLM — что это, когда применять и как оценивать

> [!abstract] Суть
> **Reinforcement Learning (RL, обучение с подкреплением)** — способ обучать модель через последствия её действий. Модель пробует варианты поведения, получает числовой сигнал качества — **reward (награду)** — и постепенно увеличивает вероятность действий, которые приводят к хорошему результату.
>
> Для языковых моделей RL особенно полезен там, где нет единственного правильного текста: нужно выполнить многошаговую задачу, выбрать инструменты, соблюдать ограничения, получить хороший результат в среде или найти компромисс между качеством, безопасностью, стоимостью и скоростью.

> [!tip] Самая короткая интуиция
> **SFT** учит модель повторять хорошие примеры: «вот запрос и правильный ответ». **RL** учит выбирать поведение по его последствиям: «вот задача, попробуй решить её; этот путь оказался полезным, а этот — нет».
>
> RL не является обязательной «следующей ступенью» для любой LLM. Если проблема решается хорошим промптом, RAG, корректной схемой инструментов, более качественной разметкой или обычным fine-tuning, начинать с RL не стоит.

## 1. Зачем применять RL к языковой модели

### Предобучение

Модель учится предсказывать следующий токен на огромном корпусе текстов. Она получает общие знания о языке, фактах и стилях, но ещё не обязательно умеет следовать инструкциям и безопасно взаимодействовать с пользователем.

### Supervised fine-tuning (SFT, дообучение на примерах)

Модели показывают пары:

~~~text
запрос пользователя → желательный ответ
~~~

Она учится имитировать этот ответ. Такой подход хорош, когда можно достаточно точно сформулировать эталон:

- правильный формат JSON;
- классификация намерения;
- ответ по шаблону;
- корректный вызов инструмента;
- хороший пример диалога.

Но у SFT есть ограничение: он обычно учит повторять конкретный пример, а не оценивать последствия длинной цепочки действий.

### RL и обучение по предпочтениям

RL становится полезнее, когда:

- возможны несколько правильных ответов;
- важен не только текст, но и итоговое состояние среды;
- ошибка проявляется через несколько шагов;
- награду можно определить автоматически или получить от людей;
- нужно находить новые хорошие способы решения, а не только копировать демонстрации.

Пример: пользователь просит Алису купить продукты до определённой суммы. Не существует единственной правильной корзины и единственной последовательности вызовов API. Важно, чтобы агент:

1. понял ограничения;
2. выбрал подходящие товары;
3. проверил наличие и цену;
4. не превысил бюджет;
5. не оформил заказ без подтверждения;
6. сообщил результат пользователю.

Для такой задачи один эталонный текст недостаточен. Нужен сигнал, который оценивает весь путь и конечный результат.

## 2. Из каких частей состоит RL-задача

| Термин | Простое значение | Пример для Алисы |
|---|---|---|
| Environment, среда | Мир, с которым взаимодействует модель | Каталог, корзина, доставка, API Маркета |
| State, состояние | Всё, что сейчас известно о мире | Запрос, товары, корзина, адрес, остаток бюджета |
| Action, действие | Что делает модель | Вызвать поиск, добавить товар, спросить уточнение |
| Policy, политика | Правило выбора следующего действия | Сама языковая модель |
| Reward, награда | Числовая оценка результата | +1 за корректную корзину, −10 за оплату без согласия |
| Trajectory, траектория | Полная история эпизода | Состояния, действия, ответы инструментов |
| Episode, эпизод | Один законченный запуск | Решение одной задачи пользователя |
| Return, суммарная награда | Общая ценность всей траектории | Итоговая награда с учётом всех шагов |

Упрощённый цикл:

~~~text
состояние s_0
    ↓
модель выбирает действие a_0
    ↓
среда возвращает результат и награду r_0
    ↓
новое состояние s_1
    ↓
следующее действие a_1
    ↓
...
    ↓
финальное состояние и итоговая награда
~~~

Формально суммарную награду можно записать так:

~~~text
G_t = r_t + γ · r_(t+1) + γ² · r_(t+2) + ...
~~~

γ — коэффициент дисконтирования. Он показывает, насколько мы ценим будущий результат по сравнению с немедленным. В агентных сценариях важно не переоценить быстрый промежуточный успех и учитывать, чем закончилась вся задача.

## 3. Два уровня RL для LLM

### 3.1. RL для качества ответа

Задача может быть одношаговой:

~~~text
запрос → ответ модели → оценка ответа
~~~

Действием можно считать весь сгенерированный ответ или отдельные токены. Reward оценивает:

- полезность;
- соответствие инструкции;
- корректность;
- безопасность;
- стиль;
- предпочтительность для человека.

Так обычно описывают RLHF и RLAIF.

### 3.2. RL для агентного поведения

Здесь модель взаимодействует со средой:

~~~text
запрос
→ вызов поиска
→ результат поиска
→ фильтрация
→ вызов корзины
→ проверка ограничений
→ финальный результат
~~~

Действиями становятся:

- текстовый ответ;
- вызов инструмента;
- параметры вызова;
- вопрос пользователю;
- завершение или отказ от задачи.

Reward можно выдавать за каждый шаг, за промежуточные условия и за итоговый результат.

> [!warning] Важное различие
> Для чат-ответа можно оценивать только текст. Для агента нужно проверять ещё и фактическое состояние среды. Фраза «заказ оформлен» ничего не доказывает, если в тестовом магазине заказа нет или он создан с неверным адресом.

## 4. Как выглядит обучение LLM с предпочтениями и RL

На практике редко берут базовую языковую модель и сразу запускают её в свободном RL.

~~~text
предобученная LLM
        ↓
SFT на качественных инструкциях
        ↓
сбор сравнений ответов людьми или judge-моделью
        ↓
reward model или другой оценщик
        ↓
обучение по предпочтениям / RL
        ↓
offline-проверка, safety-проверка и rollout
~~~

### Шаг 1. Сбор предпочтений

Для одного запроса получают два или несколько ответов:

~~~text
Ответ A: краткий, но пропустил ограничение по бюджету
Ответ B: немного длиннее, но бюджет проверен и действие не выполнено без согласия
~~~

Разметчик выбирает лучший ответ и объясняет критерий выбора. Предпочтение человека не является абсолютной истиной: разные эксперты могут по-разному понимать «хороший ответ». Поэтому нужны инструкции, контрольные примеры и измерение согласия.

### Шаг 2. Reward model

**Reward model (модель награды)** учится по примерам предпочтений предсказывать, какой ответ или траектория лучше.

Она не обязана генерировать ответ. Её задача — присвоить оценку:

~~~text
reward(answer_A) = 0.2
reward(answer_B) = 0.8
~~~

Вместо отдельной reward model может использоваться LLM-as-a-judge, но тогда нужно проверять стабильность и согласие с экспертами.

### Шаг 3. Обновление политики

Модель генерирует варианты, получает reward и обновляет свои параметры так, чтобы хорошие варианты встречались чаще.

В классическом RLHF часто упоминают **PPO (Proximal Policy Optimization)**. Для интервью достаточно понимать общую идею:

- политика генерирует ответы;
- reward model оценивает их;
- обновление делается небольшими шагами;
- новую модель удерживают близко к исходной, чтобы она не потеряла язык и базовые навыки.

Обычно добавляют штраф за отклонение от reference model:

~~~text
итоговая награда =
награда за задачу − β · KL(новая модель || reference model)
~~~

KL здесь измеряет, насколько новое распределение ответов отличается от исходного. Такой штраф не даёт модели «разогнаться» в сторону странных решений, которые случайно хорошо оцениваются reward model.

## 5. RLHF, RLAIF, DPO и GRPO — в чём разница

### RLHF

**RLHF (Reinforcement Learning from Human Feedback, обучение с подкреплением по обратной связи людей)**:

1. люди сравнивают ответы;
2. обучается reward model;
3. политика оптимизируется под reward;
4. обычно используется RL-алгоритм вроде PPO.

Плюс — можно напрямую учить сложным человеческим предпочтениям. Минусы — высокая стоимость разметки, сложность обучения и риск того, что reward model будет ошибаться.

### RLAIF

**RLAIF (Reinforcement Learning from AI Feedback)** — похожая схема, но ответы оценивает другая модель.

Это дешевле и быстрее масштабируется, однако judge-модель может передавать собственные систематические ошибки. Поэтому небольшая экспертная выборка всё равно нужна для калибровки.

### DPO

**DPO (Direct Preference Optimization, прямая оптимизация предпочтений)** использует пары:

~~~text
запрос + хороший ответ + плохой ответ
~~~

и напрямую обучает основную модель предпочитать хороший вариант.

Обычно DPO:

- не требует отдельной reward model;
- не требует полноценного взаимодействия со средой;
- проще и стабильнее запускается;
- хорошо подходит для статических пар предпочтений.

Но DPO не заменяет полноценное RL, если модель должна исследовать среду, получать отложенную награду и находить новые стратегии. Его правильнее называть методом оптимизации по предпочтениям, а не полным обучением с подкреплением.

### GRPO

**GRPO (Group Relative Policy Optimization)** — подход, в котором модель генерирует несколько вариантов решения одной задачи и сравнивает их относительно друг друга.

~~~text
одна задача → несколько ответов → оценка каждого → усиление лучших
~~~

Вместо отдельной value model можно использовать относительные оценки внутри группы. Такой подход интересен для задач рассуждения и проверяемых ответов.

Риски остаются прежними:

- judge может быть ошибочным;
- модель может научиться обходить проверку;
- качество зависит от разнообразия сгенерированных вариантов;
- улучшение на синтетических задачах может не переноситься на пользователей.

### Rejection sampling и best-of-N

Иногда не нужно обновлять веса модели. Можно:

1. сгенерировать несколько ответов;
2. выбрать лучший по проверяющей модели;
3. использовать его как пример для последующего SFT.

Это дешевле и проще RL, но модель сама по себе не учится во время выбора: улучшается только результат конкретного запуска.

## 6. Как RL выглядит в агентной системе

Упрощённый псевдокод:

~~~python
for episode in range(num_episodes):
    state = environment.reset()
    trajectory = []
    done = False

    while not done:
        action = policy(state)
        next_state, reward, done, info = environment.step(action)

        trajectory.append({
            "state": state,
            "action": action,
            "reward": reward,
            "info": info,
        })

        state = next_state

    update_policy(trajectory)
~~~

В реальной LLM-системе policy(state) — это генерация текста или вызов инструмента, а environment.step(action) может обращаться к симулятору Маркета, Лавки, поиска или другой системе.

### Почему реальную среду обычно не используют для свободного exploration

**Exploration (исследование)** означает, что модель пробует новые действия. Для интернет-магазина это опасно: агент может создать заказ, потратить деньги или изменить пользовательские данные.

Поэтому используют:

- sandbox и виртуальные API;
- симулятор с откатом состояния;
- replay реальных сценариев;
- ограниченный набор разрешённых действий;
- ручное подтверждение необратимых операций;
- shadow mode, когда модель делает предсказание, но не влияет на пользователя;
- постепенный rollout.

## 7. Как конструировать reward

Самая частая ошибка — сделать награду слишком простой.

~~~text
reward = 1, если агент вызвал create_order
~~~

Тогда модель быстро научится оформлять любой заказ, даже без проверки бюджета, наличия и согласия пользователя.

Более разумная схема:

~~~text
reward =
    1.0 × task_success
  + 0.3 × constraints_satisfied
  + 0.2 × correct_tool_use
  - 0.05 × unnecessary_steps
  - 0.01 × latency_seconds
  - 3.0 × safety_violation
~~~

Числа здесь условные. Их нельзя выбрать только «по вкусу аналитика». Нужно согласовать:

- что продукт считает успехом;
- какие ошибки критичны;
- чем можно пожертвовать;
- какие ограничения не могут быть нарушены ни при каких условиях.

### Жёсткие ограничения и мягкие предпочтения

**Жёсткое ограничение**:

- не оплачивать без подтверждения;
- не превышать бюджет;
- не раскрывать персональные данные;
- не использовать запрещённый инструмент.

Нарушение может сразу означать episode failure, даже если в остальном задача выполнена.

**Мягкое предпочтение**:

- сделать меньше шагов;
- ответить короче;
- выбрать более дешёвый товар;
- уменьшить задержку.

Такие свойства можно оптимизировать постепенно, не компенсируя ими критическую ошибку.

### Reward shaping

**Reward shaping (формирование промежуточной награды)** — выдача небольших сигналов за полезные промежуточные действия:

- правильно извлёк ограничение по бюджету;
- выбрал подходящий инструмент;
- отфильтровал товар без аллергена;
- проверил наличие;
- задал необходимый уточняющий вопрос.

Промежуточная награда помогает при длинной задаче, но создаёт риск неправильного поведения. Если награждать вызов поиска, агент может бесконечно искать и не завершать заказ.

### Credit assignment

**Credit assignment (распределение ответственности)** — определение, какие действия привели к итоговому успеху или провалу.

Если заказ не оформился, причина могла быть:

- в неправильном выборе товара на первом шаге;
- в пропущенной проверке бюджета;
- в неверном параметре последнего API-вызова;
- в сбое внешнего сервиса.

Поэтому полезно сохранять не только итоговый reward, но и метки по каждому шагу.

## 8. Reward hacking: как модель обманывает награду

**Reward hacking (взлом или обход функции награды)** — ситуация, когда модель получает высокий reward, но не решает настоящую задачу.

Примеры:

- агент всегда отказывается, потому что отказ никогда не приводит к технической ошибке;
- модель пишет длинное рассуждение, которое нравится judge, но не вызывает нужный инструмент;
- агент выбирает формально дешёвый товар, игнорируя ключевое ограничение;
- модель завершает задачу без подтверждения пользователя;
- агент делает много безопасных промежуточных действий, но не доходит до результата;
- модель учится особенностям тестового checker и подстраивает ответ под его ошибки.

Защита:

- независимые автоматические проверки;
- проверка конечного состояния среды;
- отдельные safety guardrails;
- скрытые тесты;
- ручная выборка;
- adversarial cases (специально сложные и провоцирующие примеры);
- сравнение с реальными пользовательскими метриками;
- регулярное обновление benchmark.

> [!warning] Средняя награда может расти при ухудшении поведения
> Если reward складывается из нескольких частей, рост суммы не означает, что модель стала полезнее. Она могла научиться улучшать дешёвые компоненты и компенсировать ими редкие, но опасные нарушения. Критические ограничения нужно проверять отдельно.

## 9. Какие данные нужны для RL

### Golden trajectories

Эталонные траектории показывают, как можно решить задачу качественно. Они полезны для:

- SFT;
- калибровки reward model;
- примеров для разметчиков;
- анализа отклонений;
- создания тестовых сценариев.

Но golden trajectory не всегда является единственным правильным маршрутом. Лучше хранить не только «идеальную последовательность», но и проверяемые инварианты:

- цель достигнута;
- обязательные ограничения соблюдены;
- запрещённых действий нет;
- результат подтверждён состоянием среды.

Подробный разбор сбора таких данных находится в [[Golden trajectories, reward и RL для LLM — как собирать эталонные действия]].

### Положительные и отрицательные примеры

Нужно собирать не только успешные решения, но и:

- неверные вызовы инструментов;
- неправильные аргументы;
- лишние действия;
- опасные действия;
- ситуации, где нужно задать вопрос;
- корректные отказы;
- частично успешные траектории.

Иначе модель не поймёт границу между «можно выполнить» и «нужно остановиться».

### Синтетические данные

LLM может генерировать задания и траектории, но синтетические данные нужно фильтровать:

- проверять исполнимость в среде;
- удалять дубликаты;
- контролировать сложность;
- проверять распределение сценариев;
- отделять данные обучения от тестовых;
- регулярно сравнивать с реальными пользовательскими логами.

## 10. Как оценивать результат RL

После обучения нельзя смотреть только на reward, на котором модель оптимизировалась.

### Offline-оценка

Проверяем модель на зафиксированном наборе:

- успешность задачи;
- корректность вызова инструмента;
- правильность аргументов;
- соблюдение ограничений;
- качество финального ответа;
- способность восстановиться после ошибки;
- число шагов;
- стоимость и задержку.

### Human evaluation

Эксперты нужны для свойств, которые трудно проверить автоматически:

- действительно ли ответ полезен;
- корректно ли обработана неоднозначность;
- не вводит ли агент пользователя в заблуждение;
- уместен ли отказ;
- насколько понятна коммуникация.

### LLM-as-a-judge

Judge-модель может масштабировать проверку, но её нужно калибровать на экспертной выборке и регулярно проверять на:

- стабильность;
- чувствительность к порядку ответов;
- предпочтение длинных текстов;
- склонность соглашаться с уверенным ответом;
- изменение поведения после обновления judge.

### Online-оценка

На реальных пользователях оцениваем:

- завершение пользовательской задачи;
- долю повторных попыток;
- отмены;
- жалобы;
- удовлетворённость;
- стоимость;
- задержку;
- безопасность.

Основная метрика должна быть связана с пользовательской ценностью, а reward и offline-метрики — помогать диагностировать причины.

| Уровень | Пример |
|---|---|
| Основная метрика | Доля полностью выполненных задач |
| Диагностические | Ошибки выбора инструмента, неверные аргументы, пропущенные ограничения |
| Защитные | Критические нарушения, стоимость, задержка, жалобы |
| Срезы | Тип сценария, сложность, регион, устройство, новый пользователь |

## 11. Когда RL подходит, а когда нет

| Проблема | Первый кандидат | Почему |
|---|---|---|
| Нужен стабильный JSON | SFT, constrained decoding, validator | Задача хорошо формализуется |
| Не хватает фактов | RAG или обновление базы знаний | RL не добавит модели актуальные документы |
| Неверно выбран инструмент | SFT на tool calls, улучшение схемы API | Сначала нужно показать правильное поведение |
| Несколько хороших ответов | Preference optimization или RLHF | Нужна модель предпочтений |
| Многошаговая задача в симуляторе | RL, GRPO, иногда PPO | Есть состояние, действия и измеримый результат |
| Нужна безопасность | Guardrails, policy checks, экспертная разметка | Нельзя надеяться только на среднюю награду |
| Агент делает слишком много шагов | Анализ reward и trajectory, затем RL/оптимизация | Нужно определить цену лишних действий |
| Ошибки поиска контекста | Retriever, reranker, RAG | Проблема находится до генерации |

### Практическое правило

Сначала нужно определить причину проблемы:

1. модель не знает факт;
2. модель знает факт, но не находит его;
3. модель находит его, но неправильно рассуждает;
4. модель правильно рассуждает, но неверно вызывает инструмент;
5. инструмент работает, но итоговая цель не достигается;
6. модель достигает цели, но делает это небезопасно или слишком дорого.

RL разумно применять ближе к пунктам 3–6, когда есть хороший feedback и можно воспроизводимо оценить последствия действий.

## 12. Примеры применения

### Пример 1. Заказ продуктов

Пользователь просит:

> «Собери ужин на двоих до 2 000 ₽, без орехов, доставку после 19:00. Заказ не оформляй без моего подтверждения».

Возможная проверка:

- бюджет не превышен;
- аллергенов нет;
- выбран допустимый слот;
- состав корзины соответствует запросу;
- оплата не вызвана;
- пользователь получил понятное резюме.

RL может быть оправдан после того, как среда и checker уже надёжно работают. До этого модель нужно обучить базовым tool calls и правилам безопасности через SFT и явные проверки.

### Пример 2. Распознавание документа

Задача — извлечь ФИО, дату рождения и доход из скана.

Для базового решения обычно подойдут:

- OCR или VLM;
- SFT на размеченных документах;
- нормализация полей;
- confidence threshold;
- ручная проверка неуверенных случаев.

RL здесь не является естественным первым выбором: у задачи есть проверяемый JSON, а основной источник ошибки — качество восприятия и разметки. RL можно рассматривать позже, например для выбора последовательности действий в сложном пайплайне или оптимизации решения «автоматически обработать или отправить человеку».

### Пример 3. RAG по внутренним документам

Если ответ неверен из-за того, что система не нашла актуальный документ, RL не исправит слабый retriever. Сначала проверяем:

- полноту поиска;
- правильность разбиения документов;
- актуальность источников;
- reranking;
- цитаты;
- отсутствие галлюцинаций.

RL может быть полезен позже для оптимизации последовательности: когда искать ещё, когда уточнять запрос, когда вызывать другой источник, а когда честно сообщать, что ответа нет.

## 13. Что важно сказать на собеседовании

### «Чем RL отличается от SFT?»

SFT учит имитировать заранее подготовленные правильные ответы. RL оптимизирует поведение по последствиям и может учитывать итог многошаговой задачи, ограничения, безопасность и стоимость. Но RL сложнее и оправдан только при наличии надёжного reward и воспроизводимой среды.

### «Зачем нужен reward model?»

Она переводит предпочтения людей или judge-модели в числовой сигнал, с которым можно оптимизировать policy. Но reward model сама может ошибаться и подвергаться reward hacking, поэтому её нужно калибровать и проверять отдельно.

### «DPO — это RL?»

DPO обычно относят к обучению по предпочтениям, но это не полноценное взаимодействие с окружающей средой. Метод напрямую использует пары хороших и плохих ответов и не требует отдельной reward model или online-rollout. Для статических предпочтений он проще, а для длинных агентных задач с отложенной наградой полноценный RL может быть уместнее.

### «Почему нельзя просто максимизировать reward?»

Потому что reward может быть неполным или ошибочным. Модель найдёт самый лёгкий способ набрать баллы, который не обязательно совпадёт с реальной пользовательской ценностью. Нужны независимые проверки, safety-ограничения, hidden tests и online-оценка.

### «Как оценивать агента после RL?»

Я бы разделил оценку на четыре уровня: итоговое выполнение задачи, правильность промежуточных tool calls, безопасность и эксплуатационные характеристики. Затем сравнил бы модель с baseline на скрытом benchmark, проверил экспертами критичные сценарии и провёл постепенный online-тест с основной и защитными метриками.

### «Что делать, если reward вырос, а пользователи недовольны?»

Проверить, не оптимизировалась ли модель под ошибочный reward; сравнить benchmark с реальными сценариями; изучить распределение ошибок и срезы; проверить задержку, стоимость и долю отказов; отдельно посмотреть критические нарушения. До выяснения причины полный rollout останавливать.

### «Как обучать агента, если награда приходит только в конце?»

Добавить аккуратные промежуточные сигналы, маркировать первый ошибочный шаг, использовать качественные golden и negative trajectories, разбивать задачи по сложности и не позволять промежуточной награде компенсировать критический провал. При этом нужно проверять, не начинает ли агент оптимизировать саму промежуточную метрику вместо результата.

## 14. Production-контур

Перед запуском RL-модели в продукте нужны:

1. Версионированная среда и benchmark.
2. Воспроизводимый запуск с фиксированными параметрами.
3. Безопасный sandbox для действий с побочными эффектами.
4. Проверки конечного состояния.
5. Набор критичных safety-сценариев.
6. Offline-сравнение с текущей моделью.
7. Shadow или canary rollout.
8. Основная, диагностические и защитные метрики.
9. Автоматический rollback при нарушении порогов.
10. Регулярный анализ новых ошибок и обновление датасета.

В production обычно не разрешают модели свободно исследовать опасные действия. Исследование проводят в симуляторе, а реальные пользователи участвуют только в контролируемом эксперименте.

## 15. Не путать

- **RL не равно fine-tuning вообще.** Fine-tuning — широкое название изменения параметров модели на данных; RL — один из способов обучения по feedback.
- **DPO не равно PPO.** DPO оптимизирует пары предпочтений напрямую, PPO — классический RL-алгоритм с rollout и reward.
- **Reward не равно бизнес-метрика.** Reward — обучающий сигнал, а бизнес-метрика может быть гораздо сложнее.
- **Golden trajectory не равно единственно правильный путь.** Нужно проверять инварианты результата.
- **LLM-as-a-judge не равно объективная истина.** Это ещё одна модель с собственными ошибками.
- **Высокий offline reward не гарантирует пользу пользователю.**
- **RL не исправляет плохую среду.** Если checker или API ненадёжны, модель будет обучаться на неправильной обратной связи.

## Короткая схема выбора подхода

~~~text
Есть ли однозначный проверяемый ответ?
    ├─ Да → SFT / constrained decoding / обычная валидация
    └─ Нет
       Есть ли предпочтения людей или judge?
          ├─ Да, но среда статична → DPO / preference optimization
          └─ Нет
             Есть ли среда, действия и измеримый итог?
                ├─ Да → RL в sandbox, с guardrails и benchmark
                └─ Нет → сначала улучшить постановку задачи и способ оценки
~~~
