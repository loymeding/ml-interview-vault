# Виртуальные среды и API для агентов — состояние, инструменты, воспроизводимость и симуляция

> [!abstract] Суть
> Виртуальная среда превращает продуктовую задачу в воспроизводимый тест: агент получает наблюдение, вызывает разрешённые API, меняет состояние и получает результат. Хорошая среда достаточно похожа на продукт, но безопасна, детерминирована и умеет автоматически проверять результат.

> [!tip] Представьте учебный симулятор, а не настоящий магазин
> **Виртуальная среда** — учебная копия нужной части продукта: у неё есть каталог, корзина, права и правила, но тестовый агент не может навредить реальному пользователю. **API** — технический способ попросить сервис выполнить действие. **Состояние (state)** — всё, что уже произошло и влияет на следующий шаг: содержимое корзины, остаток бюджета, выбранный адрес. **Детерминированность** означает, что при одинаковых входных данных среда ведёт себя одинаково. Она нужна, чтобы сравнивать модели честно.

> [!example] Почему это важно
> В тестовой среде агент добавил наушники в корзину — это просто изменение записи в памяти, которое легко проверить. В реальном сервисе тот же вызов мог бы поменять реальный заказ. Поэтому на интервью разумно начать с безопасной симуляции, а не с подключения агента к боевому API.

## 1. Зачем не использовать сразу реальный сервис

Реальный Маркет или Лавка меняется каждую секунду: цены, наличие, доставка и API. Агент может случайно оформить заказ, увидеть личные данные или получить разные ответы на одинаковую задачу. Невозможно честно сравнить две модели, если окружение изменилось между запусками.

Виртуальная среда даёт:

- фиксированное начальное состояние;
- безопасные mock API;
- детерминированный reset;
- запись всех действий;
- автоматический проверяющий финального состояния;
- controllable ошибки и edge cases;
- одинаковые условия для обучения и benchmark’а.

## 2. Из чего состоит среда: состояние, наблюдение, действие и результат

```text
state S_t
→ agent chooses action A_t
→ environment returns observation O_t and new state S_{t+1}
→ terminal success/failure/reward
```

Для корзины состояние может включать каталог, цену, наличие, пользователя, адрес, корзину, право на оплату и время. Наблюдение — то, что агенту разрешено увидеть. Нельзя отдавать агенту скрытый label успеха в tool output.

## 3. Проектирование инструментов, доступных агенту

Каждый инструмент имеет:

- имя и понятное описание;
- входную JSON-схему;
- типы и допустимые значения;
- права доступа;
- детерминированные ошибки;
- cost/latency, если это важно;
- возвращаемую структуру;
- audit log.

Пример:

```text
search_products(query, max_price?, min_rating?)
get_delivery(item_id, address_id)
add_to_cart(item_id, quantity)
confirm_order(cart_id)  # требует explicit_user_confirmation=true
```

Описание инструмента — часть поведения модели. Если оно неясное, agent failure может быть ошибкой интерфейса, а не модели.

## 4. Сброс, случайное зерно и снимки состояния

Для одинакового задания production и candidate должны увидеть одинаковое состояние. Нужны:

- `reset(task_id)`;
- snapshot каталога и пользователя;
- seed для случайности;
- версия среды и tool schemas;
- ограничение времени/числа шагов;
- лог всех state transitions.

Если версия API изменилась, benchmark сравнивает уже не только модели. Такой drift нужно отслеживать как изменение benchmark версии.

## 5. Насколько среда должна быть похожа на настоящий продукт

Слишком игрушечная среда позволяет агенту пройти benchmark шаблоном. Слишком близкая к production сложна, небезопасна и плохо воспроизводится.

Разумный компромисс:

- сохранять реальные правила и типичные ошибки;
- использовать обезличенные snapshots;
- моделировать важные ограничения: отсутствие товара, конфликт условий, сбой API, права;
- не моделировать всё, что не влияет на skill;
- валидировать среду на реальных traces.

## 6. Проверка результата

Environment checker должен проверять не только «корзина не пустая». Для задачи с ограничениями:

- все обязательные товары/свойства выполнены;
- бюджет не превышен;
- запрещённые товары отсутствуют;
- заказ не подтверждён без согласия;
- адрес/слот корректны;
- состояние консистентно.

Checker возвращает подробный failure code, чтобы error analysis понимал причину: `budget_violation`, `missing_constraint`, `unauthorized_confirmation`, `invalid_tool_argument`.

## 7. Ошибки инструментов и recovery

Реальный агент должен уметь переживать:

- временную ошибку API;
- пустой поиск;
- устаревший item_id;
- неполный ответ;
- rate limit;
- отказ доступа;
- конфликт состояния.

В benchmark’е эти ситуации нужно включать дозированно. Оцениваем, повторил ли агент допустимый запрос, выбрал ли альтернативу, запросил ли уточнение или честно остановился.

## 8. Python-аспект для интервью

В коде среда часто реализует интерфейс вроде:

```python
class Environment:
    def reset(self, task_id: str) -> Observation: ...
    def step(self, action: ToolCall) -> StepResult: ...
    def is_terminal(self) -> bool: ...
    def evaluate(self) -> EvaluationResult: ...
```

Не обязательно писать на интервью всю систему. Нужно объяснить, как вы отделите environment state, tool validation, checker, logging и task definition. Это делает код тестируемым и позволяет запускать тысячи эпизодов параллельно.

## 9. Типичные ошибки

- Давать агенту доступ к скрытой информации.
- Не делать reset и сравнивать модели на разном состоянии.
- Считать mock API истинной копией production без валидации.
- Не моделировать ошибки API.
- Проверять только итог, не логировать путь.
- Не ограничивать необратимые действия.
- Не версионировать schema инструментов.
