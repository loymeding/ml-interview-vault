# Структуры данных и алгоритмическая сложность

> [!abstract] Суть
> На собеседовании по структурам данных важно не просто помнить Big-O, а понимать, откуда берётся сложность: массив платит за resize и сдвиги, linked list — за поиск и плохую locality, dict/set — за хэширование, коллизии и load factor.

## Ответ

### 1. Big-O, worst-case и амортизированная сложность

Big-O описывает порядок роста времени или памяти при увеличении размера входа $n$.

| Обозначение | Интуиция | Пример |
|---|---|---|
| $O(1)$ | не зависит от размера | доступ к массиву по индексу |
| $O(\log n)$ | делим пространство поиска | binary search |
| $O(n)$ | один проход | поиск элемента в linked list |
| $O(n \log n)$ | эффективная сортировка | mergesort/quicksort average |
| $O(n^2)$ | вложенные циклы по данным | сравнение всех пар |

**Амортизированная сложность** — средняя стоимость операции на длинной серии операций. Например, `append` в динамический массив иногда вызывает дорогой resize за $O(n)$, но большинство добавлений стоят $O(1)$, поэтому средняя стоимость остаётся $O(1)$ amortized.

### 2. LinkedList

LinkedList хранит элементы в узлах, а каждый узел содержит значение и ссылку на следующий узел. В doubly linked list есть ещё ссылка на предыдущий узел.

У LinkedList нет `capacity` как у массива: память выделяется по узлам, а не единым непрерывным блоком.

| Операция | Сложность | Комментарий |
|---|---:|---|
| доступ по индексу | $O(n)$ | нужно идти по ссылкам |
| поиск значения | $O(n)$ | нет прямого индекса |
| вставка после известного узла | $O(1)$ | меняем ссылки |
| удаление известного узла | $O(1)$ для doubly list | если узел уже найден |
| вставка в начало | $O(1)$ | обновляем head |

Когда LinkedList выигрывает:
- частые вставки/удаления около уже известного узла;
- не нужно случайное обращение по индексу.

Когда проигрывает:
- плохая cache locality: узлы разбросаны по памяти;
- больше памяти на ссылки;
- поиск и доступ по индексу линейные.

Если на интервью спрашивают, сколько времени и памяти нужно, чтобы "развернуть" или построить linked list из $n$ элементов, базовый ответ такой:
- создать список из $n$ узлов — $O(n)$ времени и $O(n)$ памяти;
- пройти по всему списку — $O(n)$ времени и $O(1)$ дополнительной памяти;
- развернуть односвязный список in-place — $O(n)$ времени и $O(1)$ дополнительной памяти, потому что достаточно трех указателей: `prev`, `cur`, `next`.

### 3. ArrayList / динамический массив

ArrayList хранит элементы в непрерывном массиве. Есть:
- `size` — сколько элементов реально лежит;
- `capacity` — сколько элементов помещается без перевыделения.

Если `size == capacity`, массив расширяется: создаётся новый массив большей ёмкости, старые элементы копируются.

| Операция | Сложность | Комментарий |
|---|---:|---|
| доступ по индексу | $O(1)$ | адрес вычисляется напрямую |
| append | $O(1)$ amortized | иногда resize за $O(n)$ |
| вставка в середину | $O(n)$ | нужно сдвигать хвост |
| удаление из середины | $O(n)$ | нужно сдвигать хвост |
| поиск значения | $O(n)$ | если нет сортировки/индекса |

Почему `append` амортизированно $O(1)$: capacity обычно растёт с запасом, например в 1.5-2 раза. Один дорогой resize оплачивается многими дешёвыми добавлениями.

### 4. Dict / hash table

Dict реализуется через хэш-таблицу. Для ключа считается hash, по нему выбирается позиция в таблице.

Хорошая хэш-функция должна:
- быть детерминированной;
- равномерно распределять ключи;
- быстро считаться;
- давать одинаковый hash для равных объектов;
- иметь малую вероятность коллизий.

**Коллизия** — разные ключи попали в одну позицию или пробирующую цепочку. Разрешают её обычно через:
- chaining: список/бакет элементов в ячейке;
- open addressing: поиск следующей свободной позиции.

| Операция | Average | Worst-case |
|---|---:|---:|
| get/set/delete | $O(1)$ | $O(n)$ |
| membership | $O(1)$ | $O(n)$ |
| iteration | $O(n)$ | $O(n)$ |

Worst-case возникает при катастрофических коллизиях. На практике resize по load factor поддерживает таблицу разреженной.

### 5. Set

Set — это hash table без значений: хранятся только уникальные элементы. Элементы должны быть hashable.

| Операция | Сложность |
|---|---:|
| `x in s` | $O(1)$ average |
| `add/remove` | $O(1)$ average |
| `A | B` union | $O(|A| + |B|)$ |
| `A & B` intersection | $O(\min(|A|, |B|))$ average |
| `A - B` difference | $O(|A|)$ average |
| `A <= B` subset | $O(|A|)$ average |

Для intersection выгодно итерироваться по меньшему множеству и проверять membership в большем.

### 6. Базовые алгоритмические концепции

Что обычно ждут:
- уметь оценить время и память;
- видеть вложенные циклы и hidden linear scans;
- отличать average, worst-case и amortized;
- выбирать структуру данных под операции;
- понимать trade-off между скоростью, памятью и locality.

Примеры:
- нужно часто искать по ключу → dict/set;
- нужен порядок и доступ по индексу → array/list;
- много вставок в середину при известной позиции → linked list;
- нужен диапазонный поиск → дерево/отсортированная структура, не hash table.

**Медиана в несортированном массиве:**
- если отсортировать массив, сложность будет $O(n \log n)$ по времени и обычно $O(1)$-$O(n)$ по дополнительной памяти в зависимости от сортировки;
- если нужна только медиана, можно использовать Quickselect: average $O(n)$, worst-case $O(n^2)$;
- детерминированный median of medians дает worst-case $O(n)$, но на практике сложнее и с большей константой.

## Формула / Схема

**Амортизированная стоимость серии операций:**

$$\Large T_{\text{amortized}} = \frac{T_{\text{total}}(m \text{ operations})}{m}$$

где:
- $T_{\text{total}}$ — суммарная стоимость серии;
- $m$ — число операций;
- для динамического массива серия append даёт $O(1)$ amortized на операцию.

**Load factor hash table:**

$$\Large \alpha = \frac{n}{m}$$

где:
- $n$ — число элементов;
- $m$ — число ячеек таблицы;
- при слишком большой $\alpha$ растёт число коллизий, поэтому таблицу расширяют.

## Короткий пример

Если нужно хранить миллион user_id и быстро проверять, был ли пользователь в эксперименте, `set` подходит лучше списка: membership в set в среднем $O(1)$, а в list — $O(n)$.

Если нужно часто брать `events[i]`, динамический массив подходит лучше linked list: доступ по индексу $O(1)$ против $O(n)$.

## Типичные ошибки

- **Говорить, что append всегда $O(1)$:** корректнее — $O(1)$ amortized, потому что resize иногда стоит $O(n)$.
- **Считать LinkedList универсально быстрее массива:** на практике массив часто быстрее из-за cache locality.
- **Игнорировать worst-case dict:** среднее $O(1)$ не отменяет деградацию при плохом распределении hash.
- **Сравнивать set intersection без учёта размеров множеств:** обычно итерируются по меньшему set.
- **Всегда сортировать массив ради медианы:** это просто и часто допустимо, но не оптимально, если нужна только одна порядковая статистика.

## Каверзные вопросы

> [!question] Почему hash table плохо подходит для диапазонных запросов вроде `BETWEEN`?
> Hash разрушает порядок ключей. Можно быстро найти конкретный ключ, но нельзя эффективно пройти диапазон. Для диапазонов нужны B-tree/отсортированные структуры.

> [!question] Почему resize динамического массива не ломает амортизированное $O(1)$?
> Resize происходит редко. Если capacity растёт геометрически, суммарное число копирований на $n$ append остаётся $O(n)$, значит средняя стоимость одной операции — $O(1)$.
